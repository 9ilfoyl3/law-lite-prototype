# 二、产品概述

## 2.1 产品背景

AI辅助办案系统是面向基层检法司办案人员的核心办案辅助工作台，运行在政法专网内。系统围绕"案件管理 → 材料组织 → 文书生成 → 个人配置"主链路，将 AI 能力以表单化、图形化方式嵌入法官/检察官/司法局工作人员的日常案头工作，降低文书撰写与材料梳理的时间成本。

系统由**用户侧**和**管理后台**两部分组成：

- **用户侧**：办案人员日常使用的工作台，负责消费管理后台的配置并完成实际办案操作。
- **管理后台**：系统管理员进行系统级配置（用户、组织、案由、文书类型、要件、示例、指令等）的管理界面。

## 2.2 目标用户与角色

系统支持三种角色，登录时选择身份进入对应工作台：

| 角色                       | 登录入口            | 主要职责                             | 数据范围          |
| :----------------------- | :-------------- | :------------------------------- | :------------ |
| **普通用户**（法官/检察官/司法局工作人员） | 普通用户 Tab        | 案件管理、材料组织、文书生成、个人配置（我的要件/示例/指令） | 仅承办案件（本人为承办人） |
| **法院管理员**                | 管理员 Tab → 法院管理员 | 本法院用户管理、部门维护、案件监控                | 仅本法院          |
| **超级管理员**                | 管理员 Tab → 超级管理员 | 系统整体配置、全法院数据管理、组织维护              | 全部法院          |

> 原型演示支持三系统切换，实际一套环境只存在一种业务场景（原型中通过顶部切换按钮（法院 / 检察院 / 司法局）切换，切换后案由树、案字、文书类型/示例、要件、示例案件随之联动。）。

### 用户分层与生态构建

- **传统法官（河北、河南等）**：习惯列表 → 详情 → 左材料树 + 右操作台 + 浮层弹窗的 GUI 交互，不点开会话入口。
- **前沿法官（苏州、广州等）**：在用豆包和 WorkBody，喜欢会话形式，有额外能力需求。
- **产品策略**：核心 GUI 满足大多数（复制可复制场景，8 月聚焦法院 2.0 替代降运维）；开放能力平台（Artoo）服务头部法院创新。未来法官可基于 Artoo 创造 Skill，优秀法官的 Skill 反向沉淀为平台能力，形成"创新 + 业务"闭环。
- **Skill 边界**：流程性 Skill（指令约束）+ 功能性 Skill（本地/云空间 Office 操作、文件转换、第三方数据接口鉴权）。

## 2.4 设计原则

1. **对用户友好，隐藏技术复杂性**：Workflow、Token、模型上下文限制等技术概念对用户不暴露术语。用户感知"一步生成 / 分步生成"两个选项与步骤序列；材料量超限由 workflow 内部判断后以业务语言提示（如"材料量过大"）。
2. **表单化优先于对话式**：核心办案功能（生成文书、批量生成、案件维护）采用传统 GUI + 按钮实现；对话式仅用于文书精修等需要多轮交互的场景。
3. **数据分层并存**：系统内置 → 管理后台自定义 → 用户侧自定义，三层独立维护，文书生成时合并展示，用户自定义项加"我的"标识。
4. **业务抽象统一**：一套代码通过配置化适配法院/检察院/司法局，差异通过案由树、案字、文书类型等配置映射。
5. **产品定位：法官辅助工具，而非流程系统**：案号不作为系统唯一 ID 强绑定业务，改为案件名称作为主标识，案号通过 OCR 异步补充为业务字段。这样法官不再纠结"案号传不上去"（解析问题、案号被他人占用等问题彻底消除），上传即用；检察院、司法局等多业务系统无需再用法院案号做向量库索引转换，解耦后可独立适配。仍支持按案号命名压缩包上传，系统会自动取案号作为默认 ID，用户也可重新编辑。本质是"案号与业务解耦"，而非"取消案号"。
6. **交互语言一致性是核心体验**：法官习惯的范式是"左材料树 + 右操作台 + 浮层弹窗"，字体可读性、按钮位置、配置区样式等核心交互需保持一致，不能当作细节处理。

## 2.5 核心设计决策背景

1. **业务本质统一**：所有业务（法检司/政务）本质都是"材料 → 应用 → 文档"，一套产品只覆盖这一条主链路。
2. **能力底座三件套**：材料解析（多模态）+ 建库（结构化/文件/向量/图谱）+ 检索排序（多路召回 + 反思 ReAct），是所有应用的公共底座。
3. **后台编排 agentflow 化**：业务 API 由硬编码改为 agentflow 编排，输入输出不变、中间流程可持续优化与个性化，交付成本足够低。
4. **文书生成两模式一要件**：
   - 要件模式不作为百分百主线（重交付、跨地区不复用）。
   - 一步生成 = 只要结果；分步生成 = 需中间介入（步数不固定）。两者本质区别是"是否需中间介入"，而非"文字多少"。
   - 要件降为可选上限增项（问题清单 + 默认流程，用户自维护），解决通路之上的提分问题。
5. **Lite 版定位**：先替代法院应用版，做贴合业务的 GUI 应用端；个性化需求通过"快速任务"（agentflow）轻量化承载，不为此改 UI/硬编码。

## 3.2 统一布局规范

### 用户侧布局

采用**左侧导航+ 顶部栏+ 内容区**统一布局：

> 管理后台侧边栏菜单按登录角色动态过滤显示：超级管理员可见全部菜单，法院管理员仅可见用户管理、部门维护、案件管理。

## 3.3 数据分层架构

系统采用三层数据并存机制，文书生成时自动合并展示：

| 数据层         | 存储位置                 | 维护入口        | 用户侧标识      |
| :---------- | :------------------- | :---------- | :--------- |
| **系统内置**    | 代码常量（case-data.js）   | 产品预置        | 无标识        |
| **管理后台自定义** | localStorage.admin\* | 管理后台各模块     | 无标识（与内置合并） |
| **用户侧自定义**  | localStorage.my\*    | 我的要件/示例/指令 | "我的"徽章     |

**覆盖语义**：管理后台对内置项的编辑会生成自定义覆盖对象，整体覆盖同名内置项；停用内置项时生成 `enabled: false` 的覆盖对象，用户侧不展示。

## 3.4 技术架构分层

系统采用**应用层 + 能力层 + 组件层**三层架构：

- **应用层**：核心业务的 GUI 入口（列表/详情/操作台），硬编码实现，承载法院专项应用。V1.1 聚焦该层重构，应用层逻辑稳定后不会轻易改动。
- **能力层**：开放式的零散任务承载入口，分两块——
  - **Artoo 知识问答**：类 IMA 形式的自由问答；
  - **agentflow 确定性任务编排**：有确定输入输出的工作流任务。
    能力层不做意图识别自动路由，把选择权交给用户（快速任务走 agentflow，自由问答走 Artoo）。
- **组件层**：agentflow + Arto 作为核心组件。应用层所有后台 API 全部用 agentflow 实现，涉及知识检索的由 Artoo 提供。

**Lite与 Artoo 的定位分拆**：**Lite** 是应用平台（面向 B 端深流程），前端弱化为后台能力，替代所有前端 API；Artoo 是泛场景能力平台（可独立售卖），提供 RAG 增强、检索扩写、动作召回、反思 ReAct 等能力，针对法律/法条等文本做个性化分割。

**Artoo 性能与部署策略**：双卡跑 OCR + 知识库解析，均为异步；embedding / rerank / OCR 都可替换，兼容现有法院模型与最新模型；多召回可 3 路或 2 路，可布低配模型做降级；要件数量大幅下降后性能影响可控，深度问答可用流式输出缓解等待感知。

# 四、登录模块

## 4.1 登录页（login.html）

### 页面布局

- 居中卡片式登录框，渐变背景
- 顶部登录类型切换 Tab：普通用户 / 管理员
- 选择"管理员"时显示角色选择卡片：超级管理员 / 法院管理员
- 表单区：账号、密码、验证码
- 底部：记住我、忘记密码
- 演示账号快捷区（点击自动填入）

### 功能1：登录身份切换

- **功能描述**：用户选择登录身份类型，决定进入用户侧还是管理后台
- **输入**：点击 Tab 选择"普通用户"或"管理员"
- **交互规则**：
  - 选择"普通用户"：隐藏角色选择区，登录后跳转至用户侧聊天页
  - 选择"管理员"：显示角色选择卡片，登录后跳转至管理后台控制台
- **异常case**：无

### 功能2：管理员角色选择

- **功能描述**：管理员登录时选择具体角色，决定管理后台的菜单权限与数据范围
- **输入**：点击角色卡片选择"超级管理员"或"法院管理员"
- **交互规则**：
  - 超级管理员：系统级配置 + 全法院数据，可见全部管理后台菜单
  - 法院管理员：本法院用户 + 部门 + 案件，仅可见用户管理、部门维护、案件管理菜单
  - 角色权限写入 localStorage，管理后台侧边栏据此动态过滤
- **异常case**：无

### 功能3：账号密码登录

- **功能描述**：用户输入账号、密码、验证码完成登录
- **输入**：账号（文本）、密码（密码框，支持显示/隐藏切换）、验证码（4位字母数字）
- **交互规则**：
  - 验证码图片点击可刷新
  - 三个字段均为必填，任一为空时提示"请输入XXX"
  - 验证码不区分大小写，错误时清空验证码输入框并刷新图片
  - 登录成功后跳转至对应工作台
- **异常case**：
  - 验证码错误：提示"验证码错误"，刷新验证码
  - 账号密码错误：提示错误信息（原型阶段不校验真实性）

# 五、用户侧案件模块

## 5.1 案件管理（cases.html）

### 页面布局

- 顶部栏：页面标题"案件管理"
- 筛选区：案由类型筛选、关键词搜索
- 工具栏：列配置、新建案件、批量生成
- 案件表格：案件名称、案号、案由、当事人、材料数量、更新时间、操作栏
- 勾选案件后底部浮动批量操作栏

### 功能1：案件列表展示

- **功能描述**：展示当前业务系统下的全部案件，按更新时间倒序排列
- **输入**：业务系统类型
- **输出**：案件表格，首列为案件名称（点击新标签页打开案件文件页），含案字列
- **交互规则**：
  - 表格支持横向滚动
  - 点击案件名称：新标签页打开案件文件页
  - 点击材料数量：查看文件解析状态弹窗
  - 列配置：支持自定义显示列，默认显示最小列集（名称、更新时间、材料数量），表头与数据行视觉对齐
  - 已生成文书的案件：案件名称后挂蓝色徽章显示文书数量（不在材料数量列展示文书数）
- **异常case**：
  - 无案件时显示空状态，提供"新建案件"等入口
  - 解析异常材料：材料数量单元格显示黄色标签 + tooltip 显示异常份数

### 功能2：案件筛选与搜索

- **功能描述**：按案由类型和关键词筛选案件
- **输入**：案由类型、关键词（案件名/案号/当事人）
- **输出**：筛选后的案件列表
- **交互规则**：
  - 案由类型筛选
  - 不提供案件状态筛选项
- **异常case**：无匹配结果时显示空状态

### 功能3：新建/编辑案件

- **功能描述**：创建新案件或编辑已有案件基本信息
- **输入**：案件名称（必填）、案号、案由（树形选择）、当事人信息、案字
- **交互规则**：
  - 非必填字段标注"可选"，降低用户输入复杂度
  - 当事人标签随业务系统切换（原告/被告、嫌疑人/被害人、申请人/被申请人）
  - 案由选择采用三级树形选择器
  - **案字**：案字是判定案件阶段（一审/二审/再审）的依据，影响文书生成 workflow 选择，建议尽量填写；未填案字的案件在生成文书时需用户手动选择案件阶段（见 5.2 功能2.5）
- **异常case**：案件名称为空时提示"请输入案件名称"

### 功能4：生成文书（列表页入口）

- **功能描述**：从案件列表页发起文书生成，跳转至案件详情页进行一步生成
- **输入**：文书类型、文书示例、指令
- **AI处理逻辑**：
  - 跳转至案件详情页，由用户选择材料后触发生成
  - Token 超限判断由 workflow 内部处理，前端不做预估
  - workflow 超限返回异常时，前端展示异常提示
- **输出**：跳转至案件文件页，展示一步生成配置入口
- **交互规则**：
  - 点击"生成文书"弹出配置弹框
  - 弹框内选择文书类型、文书示例，填写指令
  - 不展示"当前模型"字段（模型由 Workflow 决定，用户侧无需感知；modelId 仍写入文书版本快照供留痕）
  - 不展示 Token 预估信息（由 workflow 内部判断）
  - **跳转后配置预填**：用户在列表页弹框选择的配置通过 `sessionStorage` 传递至详情页，详情页打开时自动预填（文书类型/示例/指令）+ 自动定位到一步生成 Tab + 自动勾选全部材料，用户只需点"生成"即可
- **按钮可用性规则**：
  - 案件材料全部解析完成（无 parsing 状态文件）时按钮可用
  - 案件存在解析中材料时按钮置灰，提示"材料解析中，请稍候"
  - 案件无材料（材料数量=0）时按钮置灰，提示"请先上传材料"
- **异常case**：
  - workflow 返回超限异常时，提示"材料量过大，当前流程不支持"（裁判文书类型可额外提示"可切换至分步生成"）

### 功能5：批量生成文书

- **功能描述**：勾选多个案件后批量发起文书生成，**统一配置一种文书类型**
- **输入**：勾选的案件列表、生成配置（文书类型/示例/指令）
- **交互规则**：
  - 勾选案件后底部浮动栏显示"批量生成"按钮
  - **文书类型统一配置**：批量生成只能选择一种文书类型，所有勾选案件使用同一文书类型
  - **模型字段**：批量生成配置弹框不展示"模型"字段（模型由所选文书类型一步生成 Workflow 决定，用户侧无需感知；modelId 仍写入每个案件的文书版本快照供留痕）
  - 配置阶段告知用户解析失败案件（黄色徽章 + 文案），提供策略选项：
    - 跳过异常案件
    - 仅用已识别材料生成
  - 执行阶段逐案件调用 workflow，**Token 超限判断由 workflow 内部处理**：
    - workflow 正常返回：标记成功
    - workflow 返回超限异常：标记 failed，提示"案件材料量过大，请进入案件详情页处理"
  - **批量队列限制**：提交前检查当前批量文书队列是否已满
    - 队列允许个数由管理后台"系统初始化配置"中的"批量文书队列允许个数"配置项决定
    - 若提交数量 + 队列已有数量 > 队列允许个数，提示"批量文书队列已满，当前剩余 N 个位置，请减少提交数量或稍后再试"，阻止提交
  - **异步执行 + 进度反馈**：
    - 批量生成为**异步队列任务**，提交后不阻塞用户操作列表页
    - 提交成功提示"已加入队列，N 个案件处理中"
    - 顶部栏增加"批量任务"入口，点击查看实时进度（成功/失败/处理中）
    - **执行中关闭全屏面板不中断任务**：任务在后台继续执行，提示"批量任务将在后台继续执行，可在顶部任务通知查看进度"
    - **任务通知面板**：进行中任务展示「查看进度」按钮，点击重新打开全屏面板查看实时队列（案件列表逐个从"排队等待"变为"生成中"再到"已完成"）；已完成任务展示「查看结果」按钮，跳转结果总览页
    - 执行完成后在"批量任务"入口展示结果汇总（成功 X 个、失败 Y 个）
- **异常case**：
  - 解析异常案件：配置阶段提前告知（非执行阶段）
  - workflow 返回超限异常：标记 failed，提示"案件材料量过大，请进入案件详情页处理"
  - 队列已满：阻止提交，提示剩余位置数量

### 功能2.5：案件阶段选择

- **功能描述**：在生成文书配置区提供「案件阶段」选择项，核心目的是确定走哪个 workflow。案件阶段是 workflow 分支判断的依据，同时决定前端分步生成步骤序列
- **输入**：案件案字（若已填）或用户选择
- **输出**：案件阶段值（一审 / 二审 / 再审，法院场景），传递给 workflow + 决定分步步骤序列
- **交互规则**：
  - **位置**：生成文书配置区（一步生成视图与分步生成视图共用），置于文书类型选择之前
  - **判断逻辑**（以案字作为有无结构化信息的判据）：
    - 案件**有案字**（=有结构化信息）→ 系统按案字→阶段映射自动判定，预填锁定不可改
    - 案件**无案字**（=无结构化信息）→ 用户必选案件阶段，不设默认值，未选不允许生成
  - **案字→案件阶段映射**（法院场景）：民初/刑初/行初→一审；民终/刑终/行终→二审；民再/刑再→再审；其他案字兜底处理待定
  - **取值集合**：按业务系统区分，法院为一审/二审/再审；检察院/司法局取值待定
  - **与分步生成关系**（两者都做）：
    - 前端：案件阶段决定分步步骤序列（一审→5 步：原告诉请/被告抗辩/争议焦点/事实认定/裁判结果；二审→6 步：原审查明认定/上诉人诉讼/被上诉人抗辩/争议焦点/事实认定/裁判结果）。分步步骤序列判断逻辑从"按案字判断"统一改为"按案件阶段判断"
    - 后端：案件阶段作为字段传给 workflow，由 workflow 判断走哪个分支流程
  - **不搞两个页面或两个 tab**：保持单一生成功能，仅通过字段传递给 workflow 走分支
- **异常case**：
  - 案件无案字且用户未选案件阶段时，【生成文书】按钮置灰，hover 提示"请先选择案件阶段"

### 功能3：一步生成文书

- **功能描述**：选择材料后一键生成文书，用户只交互一次，中间过程不可控（不代表只调一次模型，workflow 内部可以分拆处理）
- **输入**：已选材料、案件阶段、文书类型、文书示例、指令（模型由 Workflow 决定，用户侧不展示）
- **AI处理逻辑**：将全部已选材料拼接 → 调用 Workflow → **流式输出文书内容**（让用户感知在生成）
- **文书生成两步流程**：
  1. **第一步·按示例生内容**：AI 按所选文书示例的 `content`（内容参考文本）作为结构指引生成正文，替换原硬编码 4 段结构。示例描述了哪些内容板块/段落，AI 据此组织内容
  2. **第二步·套格式骨架**：根据当前匹配到的 workflowId，从 `adminWorkflowFormats[org][workflowId]` 取该 workflow 对应的格式骨架（带占位符），将第一步生成的内容按格式骨架套版（填充 {{courtName}}、{{caseNumber}}、{{plaintiffDefendantInfo}} 等占位符），最终文书符合排版约束；该 workflow 未配置格式骨架时直接输出第一步内容
- **输出**：生成的文书内容（套格式骨架后的最终版本）
- **交互规则**：
  - **案由要件引入**：当文书类型为判决书且该案由存在可用要件时，生成前弹出要件上下文确认弹框（单个大文本框），预填充所有要件的问题及参考答案（已有答案优先用已有答案，否则用 mock 答案）；用户可直接修改文本内容，确认后作为上下文传给大模型；弹框提供「取消」「不引入要件」「确认生成」三个按钮，用户可选择不引入要件直接生成
  - **不做 Token 超限前置判断**，直接调用 workflow
  - workflow 返回超限异常时展示提示（见异常 case）
  - **流式输出分两阶段**：
    - **思考过程阶段**：顶部展示「思考过程」区域，逐条呈现 AI 思考文案（阅读材料、分析诉求、审查证据、归纳焦点、匹配法条、组织理由等），每条约 420-800ms 间隔，带闪烁光标；思考过程仅在流式阶段展示，**不写入文书内容**
    - **正文渲染阶段**：思考完成后，文书正文按段落逐步渲染，每段约 500-900ms，整体约3秒，模拟真实 AI 流式返回
  - **流式输出期间**：右栏顶部【文书精修】【重新配置】按钮置灰禁用；输出区显示已输出字数、预计剩余时间、当前段落进度，缓解等待焦虑
  - **流式输出完成后**：自动切换为文档编辑器（DocEditor），用户可直接在编辑器内修改文书内容；编辑器提供排版工具栏（撤销/重做、加粗、斜体、下划线、标题、对齐、清除格式等），白色 A4 纸张样式，宋体/Noto Serif SC，行距 2 倍；【文书精修】【重新配置】按钮恢复可用
  - **输出过程不能取消，不提供取消按钮**
  - 生成后配置区折叠，文书展示区显示结果
  - 支持重新展开配置区修改后重新生成
  - **Tab 切换材料清空确认**：用户在一步生成/分步生成 Tab 间切换时，若当前 Tab 已选材料，弹确认框"切换生成方式将清空已选材料，是否继续？"，确认后清空当前 Tab 材料选择
- **异常case**：
  - workflow 返回超限异常：提示"材料量过大，当前流程不支持"（裁判文书类型可额外提示"可切换至分步生成"），并补充参考信息"当前材料约 X 万字，建议控制在 Y 万字以内"，提供"按材料类型筛选"快捷入口帮助用户定位大材料

### 功能4：分步生成文书

- **功能描述**：按步骤逐步生成文书，每步由用户手动触发。**仅裁判文书类型展示分步生成 Tab**，其他文书类型只有一步生成 Tab
- **本质**：分步生成是"大要件"平台（5 步固定清单），用户需要对中间环节把控、可看、可编辑
- **输入**：每步独立选择材料、案件阶段、文书类型、文书示例（模型由 Workflow 决定，用户侧不展示；分步生成不配置指令，用户只需选文书类型+示例即可开始生成）
- **AI处理逻辑**：
  - 步骤序列 V1.1 硬编码在前端（法院民商事场景固定 5-6 步，按案件阶段决定：一审 5 步 / 二审 6 步）
  - 每步对应一个独立的 API 调用（workflow 作为端到端 API）
  - 每步入参从页面表单取值（前端抓值，不查后台）
  - 每步生成完成后由用户手动点击下一步触发该步生成
  - 全部步骤完成后显示"生成文书"按钮
- **输出**：分步生成的文书内容
- **交互规则**：
  - **仅裁判文书类型展示分步生成 Tab**，其他文书类型不展示
  - **页面布局（Stepper + 单步视图）**：进入分步生成后，顶部展示水平 Stepper（按案件阶段：一审 5 步 / 二审 6 步），下方仅渲染当前选中步骤的完整内容（单步视图），替代早期手风琴式垂直堆叠
    - Stepper 所有节点（含未开始的 waiting 态）均可点击直接切换到任意步骤，无需按顺序逐个切换
    - 当前查看的步骤在 Stepper 上呈选中高亮样式（主题色 + 外环）；已完成步骤节点显示对勾
    - waiting 态：空内容区隐藏，关联材料区撑满剩余区域，【生成本步】按钮置底展示
  - **手动逐步触发**：不支持一进来自动一步步走，必须手动一个个点（因为每步材料不一样，用户需要审材料）
  - **选完材料后不自动触发生成**（用户可能调整材料），需手动点击"生成本步"按钮
  - **步骤输入模式（合规要求）分三类**：
    - **仅材料生成**（默认）：前四步（一审：原告诉请/被告抗辩/争议焦点/事实认定；二审：原审查明认定/上诉人诉讼/被上诉人抗辩/争议焦点）**仅展示"生成本步"按钮，不展示"直接输入"按钮**；未选材料时点击"生成本步"提示选择材料；done 状态展示"编辑/重新生成/内容优化"
    - **材料生成 + 直接输入**（`allowDirectInput`）：二审（案件阶段=二审）第 5 步「事实认定」**同时展示"生成本步"+"直接输入"按钮**，用户可选材料调 AI 生成，也可手动输入；done 状态展示"编辑/重新生成/内容优化"
    - **仅直接输入**（`manualOnly`，合规要求）：最后一步「裁判结果」裁判方向属法官主观意识，**waiting 状态直接展示输入框 + 友好提示（无需点击"直接输入"按钮，用户直接打字即交互），不展示"生成本步"按钮、不展示关联材料区、不调用 AI 生成**；done 状态仅展示"编辑"按钮，不展示"重新生成/内容优化"
  - 步骤名 V1.1 硬编码（如：原告诉请、被告抗辩、争议焦点、事实认定、裁判结果）
  - **子内容块拆分展示**：每步生成结果按"子块名："前缀自动拆分为独立只读卡片（左侧主题色竖线 + 加粗子块名 + 正文），子块不提供单独操作按钮（编辑走步骤级【编辑】整步编辑）；仅一块内容的步骤（事实认定、裁判结果）不套卡片，直接展示纯文本
    - 一审：步骤1 原告诉请（案件信息/诉请内容/诉请分析/证据分析）；步骤2 被告抗辩（抗辩内容/抗辩分析/证据分析）；步骤3 争议焦点（争议焦点及分析/庭审调查建议）；步骤4 事实认定（单块）；步骤5 裁判结果（单块，仅直接输入）
    - 二审：步骤1 原审查明认定（原审诉讼请求/原审查明事实/原审法院认为）；步骤2 上诉人诉讼（上诉人诉请内容/上诉人诉请分析/上诉人证据分析）；步骤3 被上诉人抗辩（被上诉人抗辩内容/被上诉人抗辩分析/被上诉人证据分析）；步骤4 争议焦点（争议焦点及分析/庭审调查建议）；步骤5 事实认定（单块）；步骤6 裁判结果（单块，仅直接输入）
  - **内容优化**（原"追问"统一改名，最多 3 轮）：
    - done 状态点击【内容优化】展开输入框，输入优化要求后提交
    - 原型 mock 阶段正式内容不改写；真实系统接入后，各子块"前缀："保留（块结构不变），块内文本替换为流程返回的改写后全文
    - **优化记录**（做过 1 轮即显示，折叠展示）：置顶「优化前原始内容」条目（预览 + 【回填】恢复最初内容）；以下每轮一条 = 用户输入的优化要求 + 该轮对应内容快照 + 【回填】【删除】
    - **回填语义**：各轮【回填】= 恢复该轮结束时的完整内容快照（数据层每轮记录优化前/优化后快照链，与本案要件逻辑一致）
  - 每步生成保留已完成节点的快照
  - 步骤间依赖：从页面表单取值，必填依赖项为空时阻止执行并提示"请先完成 XX 步骤"；选填依赖项为空时允许执行，传空值；**无前置依赖的步骤（如一审步骤1/2、二审步骤1）不显示依赖提示条**
  - **V1.1 步骤依赖关系**（后续可能变化）：
    - 步骤1 原告诉请：无前置依赖
    - 步骤2 被告抗辩：无前置依赖
    - 步骤3 争议焦点：**可选**依赖步骤1+步骤2 的返回内容（选填，为空时允许执行）
    - 步骤4 事实认定：依赖步骤3 的返回内容（必填）
    - 步骤5 裁判结果：**仅支持直接输入**（合规要求，不调用 AI 生成，无前置依赖）
  - "重新生成"逻辑上递归重置该步及之前所有已完成步骤（当前原型仅实现当前步重置）
  - 重新配置按钮默认回填最近一次历史文书快照（已选材料 + 模型/文书类型/示例/指令/生成方式）
- **异常case**：
  - workflow 返回超限异常：提示"「步骤名」材料量过大，请减少材料"

### 功能5：引入要件（可选 Plus 功能）

- **功能描述**：文书生成时引入要件作为可选上下文，**要件是可选 plus 功能**，可 0 个可多个
- **要件定义**：小要件 = query 问题列表 + 通用问答流程，走通用流程（调知识库召回），所有调用调同一个 API
- **三种要件类型**：
  1. **标准要件**：根据案件的案由案字确定的问题（系统预置）
  2. **我的要件**：用户维护的案由案字对应的问题（用户个人示例，"我的要件"页面管理）
  3. **个案要件**：根据某一个案子，用户自己编辑维护的（案件级别）
- **输入**：案由、案字、案件 ID
- **输出**：要件结果列表（用户可见、可确认、可编辑）
- **交互规则**：
  - 案件详情页采用**可折叠侧边抽屉**展示要件列表（默认收起，不占用主布局空间）
  - **本案要件入口位置**：材料树顶部固定条（`material-col-elements-bar`），位于材料树 header 下方、搜索框上方；材料多时无需滚动即可见；折叠材料树时入口随之隐藏
  - 入口按钮显示"本案要件 (N)"，N 为已配置要件数量；点击从右侧滑出抽屉展示要件列表
  - **抽屉宽度**：占页面 50%（`width: 50vw`，`min-width: 380px` 兜底小屏），方便用户同时查看左侧材料树与右侧要件列表
  - 要件问答流程用**弹窗交互**（`elementConfirmModal`），按要件答案状态分两种路径（v1.49 调整）：
    - **路径 A：有可用要件且有答案** → 直接弹大文本框确认弹框（简化版），展示所有要件的问题及参考答案（用已有答案），用户可修改后确认生成；底部按钮【取消】【不引入要件】【确认生成】
    - **路径 B：有可用要件但无答案** → 三步弹框：
      - **第一步（确认是否引入）**：提示是否引入案由要件；底部按钮【取消】【引入要件】
      - **第二步（选择要件）**：默认勾选所有可用要件，提示"引入要件后系统将针对每个问题预生成答案并整合到文书中，生成时间可能会稍长"；用户可取消不需要的要件；底部按钮【上一步】【引入要件】
        - 【上一步】返回第一步且保留第一步 state
        - **不提供"管理我的要件"链接**（案件详情页已有入口，避免重复）
        - 用户如需维护"我的要件"，可通过顶部全局导航进入"我的要件"页面
      - **第三步（大文本框确认答案）**：展示所有已选要件的问题及参考答案（预生成答案可修改），用户可修改或补充；底部按钮【上一步】【确认生成】
        - 【上一步】返回第二步且保留已勾选状态
    - **路径 C：无可用要件** → 不弹框，直接生成
  - 三种来源要件分别用蓝/绿/橙三色标签区分（标准要件=蓝、我的要件=绿、个案要件=橙）
  - 要件结果作为文书生成入参的**可选字段**传递
  - 个案要件持久化到 `localStorage.caseCustomElements_${caseId}`，问答答案持久化到 `localStorage.caseElements_${caseId}`，内容优化历史持久化到 `localStorage.caseElementsFollowUps_${caseId}`，下次进入恢复
  - **要件答案展示与操作**（参考分步生成步骤操作模式）：
    - 一键生成后，要件项下方直接展示答案内容（仅展示答案正文）
    - 答案下方提供三个操作按钮，仅在已生成答案后出现：
      - **编辑**：内联切换为文本框编辑当前答案，保存后更新（编辑区仅展示文本框与保存/取消按钮）
      - **重新生成**：基于当前要件重新调用 AI 生成答案，覆盖原答案
      - **内容优化**（原"追问"统一改名，最多 3 轮）：在答案下方展开输入框，输入优化要求后提交；**优化记录与分步生成逻辑一致**——做过 1 轮即折叠展示「优化记录」，置顶「优化前原始内容」条目（预览 + 【回填】恢复），每轮一条 = 优化要求 + 该轮优化前答案 + 【回填】【删除】，各轮【回填】= 恢复该轮结束时的完整答案快照（数据层记录 beforeAnswer/appliedAnswer 快照链）；原型 mock 阶段正式答案不改写，真实系统接入后替换为流程返回的改写后全文
  - **生成文书时与要件答案的联动**（一步生成、分步生成"生成文书"按钮均适用，v1.49 调整）：
    - 有可用要件**且有答案**：直接弹大文本框确认弹框（简化版），展示所有要件的问题及参考答案（已有答案用已有答案），用户可修改后确认生成
    - 有可用要件**但无答案**：弹两步弹框——第一步确认是否引入案由要件；第二步勾选具体要件（默认全选）+ 预生成答案可修改，确认后进入大文本框确认弹框
    - 无可用要件：直接生成，不弹框
- **异常case**：无要件时显示空状态

### 功能6：材料删除

- **功能描述**：删除案件中的材料
- **交互规则**：
  - 删除时选择"仅删除原始材料（保留已生成文书）"或"同时删除原始材料及已生成文书"
  - 批量删除支持多选

### 功能7：文书精修

- **功能描述**：对已生成的文书进行多轮对话式精修，支持选中段落单点改写、右侧对话栏结构化修改建议两种精修模式，精修结果另存为新版本
- **输入**：精修上下文（URL 参数传递 `caseId` + `versionId`），包含：
  - 当前文书正文内容
  - 关联个案的知识库（含用户前期卷宗总结、要件填写等输出）
  - 五步工作法与要件清单的结构化数据
- **系统处理逻辑**：
  - Agent 新会话自动带入上述三类上下文，用户无感知
  - Agent 绑定当前**全量文书内容**，避免仅基于局部片段生成内容
  - 所有对话回复强制采用结构化格式（原文锚点 + 修改说明 + 修改结果），不支持开放式问答或整篇重写
- **输出**：精修后的文书内容（另存为新版本追加到案件文书版本列表）
- **页面布局**：
  - 独立页面（`pages/document-polish.html`），新标签页打开
  - 左侧文书内容展示区 + 右侧对话式精修区，中间可拖动分隔条调整宽度
  - **左侧文书区接入文档编辑器（DocEditor）**：提供排版工具栏（撤销/重做、加粗、斜体、下划线、标题、对齐、清除格式等），白色 A4 纸张样式，宋体/Noto Serif SC，行距 2 倍，用户可直接编辑文书内容

#### 上下文信息区（三卡片）

右侧对话区顶部展示三张上下文状态卡片，体现"三类上下文自动引入、用户无感知"：

- **卡片1 - 文书来源**：展示文书标题 + 来源标签（"生成跳转" / "用户上传"）+ "已自动加载"标签
- **卡片2 - 个案知识库**：展示"已加载 N 份材料"+ "已自动加载"标签；无关联案件时显示"无关联案件，未加载"并置灰
- **卡片3 - 结构化数据**：展示"五步工作法 + 要件清单"+ "已自动加载"标签；无关联案件或无配置时显示对应空状态并置灰

#### 精修模式一：选中段落系统改写（单点快速修改）

**触发条件**：
- 编辑器非只读状态
- 用户在文书编辑器内用鼠标拖选一段文本后松开鼠标
- 纯空白或跨不连续段落选区不触发

**浮动工具条**：
- 选中文本后默认在选区下方弹出迷你工具条，下方空间不足时改到上方，含"✨ 系统改写"按钮
- 点击编辑器空白处或滚动页面时工具条消失

**改写卡片样式**：
- 卡片使用绝对定位浮层跟随选区，圆角（10px）+ 阴影 + 边框
- 卡片分为两个状态：输入态、结果态，根据交互阶段切换

**改写卡片交互流程（两态结构：先输入指令再生成）**：
1. 用户点击"系统改写"按钮后，弹出改写卡片，初始为**输入态**
2. **输入态（简洁横条，无标题栏、无关闭按钮）**：
   - 整体为一条输入框样式的横条：左侧 ✨ 图标 + 中间输入框（placeholder "输入优化指令"）+ 右侧向上箭头发送按钮
   - 隐藏卡片 header（不显示标题栏和关闭按钮）
   - 不展示原文片段、不展示黄色提示框
   - 空指令点击发送时提示"请输入改写指令后再发送"
3. 用户在输入框输入改写指令，点击发送按钮或回车后，卡片切换为**结果态**并显示"系统正在按指令改写"加载状态
4. **结果态（完整卡片，含标题栏）**：
   - **标题栏**：左侧 ✨ 图标 + 改写指令内容（如"增加被告电话：12345678909"，即用户输入的指令作为标题）+ 右侧关闭按钮（X）
   - **内容区**：直接展示改写结果文本（非 textarea，不可编辑），文本可换行
   - **底部提示**：灰色小字"内容由系统生成，仅供参考"
   - **操作按钮**：见下方"操作按钮"说明
   - 结果态不保留指令输入框，用户如需调整指令应点【重写】沿用当前指令重新生成，或关闭卡片重新选中文本启动新一轮改写

**操作按钮**：
- 【重写】：沿用当前指令重新生成一次改写结果
- 【复制】：复制修改结果到剪贴板
- 【插入】：插入到编辑器当前光标位置（保留原格式模板）
- 【替换原文】（蓝色主按钮）：定位选区原文并替换为修改结果，仅替换文本节点，保留段落格式

**格式保留规则**：
- 替换原文时，仅替换文本节点的 `textContent`，不修改 `<p>` / `<h2>` / `<h3>` / `<li>` 等容器标签及其样式
- 若修改结果含多段内容，按原文段落结构拆分后逐段替换；无法一一对应时，以插入方式兜底
- 替换完成后，被替换文本高亮闪烁 0.8 秒提示用户

**关联全案上下文**：改写时 Agent 上下文不仅包含选中的局部片段，还需自动带入全量文书、个案知识库、结构化数据，避免改写内容与整体逻辑冲突。

#### 精修模式二：右侧多轮对话结构化修改建议（复杂多点深度精修）

**交互流程**：
1. 用户在右侧输入框输入精修指令（如"将本院认为部分重写"）
2. 右侧出现用户消息气泡
3. 助手消息占位："分析中..." + 加载动画
4. 0.8s 后流式展示分析过程（每步间隔 0.6s）
5. 全部步骤展示完成后，0.5s 后自动折叠分析过程（保留展开入口）
6. 0.3s 后展示修改建议区域（顶部批量操作 + N 张修改点卡片，每张间隔 0.3s）

**分析过程区**：
- 可折叠面板，标题"已完成分析" + 展开/收起图标
- 步骤标题根据用户指令**动态变化**（如"梳理历史任务 / 明确用户需求 / 定位与检索 / 起草与完善"，或"读取文书结构 / 识别格式异常 / 生成格式修正建议"等）
- 流式展示时逐步展开，全部完成后自动折叠

**修改建议区结构**：
- 顶部批量操作：【全部插入】【全部撤销】
- 修改点卡片（当前阶段不分类，全部平铺展示）：
  - 序号 + 标题
  - 风险概述（红色文字）
  - 修改方案（蓝色文字）
  - 修改内容（默认展示"修订版"，可切换"清洁版"）
    - 修订版：以 `<del>` 红色删除线 + `<ins>` 绿色高亮展示差异
    - 清洁版：仅展示修改后的最终文本
  - 操作按钮：【定位原文】【撤销修订】【忽略】【插入】

**单点操作语义**：
- 【定位原文】：在左侧编辑器中查找原文锚点，滚动到位置并高亮闪烁；找不到时按钮置灰，hover 提示"原文位置已变化，无法定位"
- 【插入】：查找原文锚点，找到则替换（保留原格式）；找不到则按当前光标位置插入并提示；插入后卡片变绿、显示"已应用"标签
- 【撤销修订】：恢复到该条消息操作前的快照，再重新应用其他已应用的修改点
- 【忽略】：卡片置灰，显示"已忽略"标签，不可再操作

**批量操作语义**：
- 【全部插入】：依次应用所有未忽略的修改点；部分锚点失效时按光标处插入兜底，汇总提示"N 项成功插入，M 项因原文变化已插入到光标处"
- 【全部撤销】：恢复到该条消息所有操作前的快照，清除所有已应用标记（忽略的不恢复）

**状态管理**：
- 每条修改建议消息维护独立的操作快照（`snapshotBeforeApply`），首次应用时记录
- 全局撤销栈（`editHistory`）记录每次操作前的内容，供 header【撤销】按钮使用
- 多条指令独立：连续发送多条指令时，每条独立生成一条修改建议消息，历史消息保留但不可再操作（已应用的修改保留在文书中）

**与"选中段落系统改写"的关系**：保持独立，互不干扰，两类操作都进入全局撤销栈。

# 六、Workflow 编排模块

## 6.1 Workflow 架构概述

### 核心理念

**workflow 就是端到端的 API**，不要把它当 workflow 看。每个 workflow 是一个独立的 API 调用，输入参数进去，输出结果回来。

| 生成方式 | 配置方式                         | 说明                                                  |
| :--- | :--------------------------- | :-------------------------------------------------- |
| 一步生成 | **管理后台配置**（文书类型 → 流程 ID）     | 保留配置页，仅配置流程 ID 与匹配规则；模型由 agentflow 平台 workflow 内部决定 |
| 分步生成 | **V1.1 硬编码前端**（步骤序列不入管理后台配置） | 步骤序列、步骤间依赖等细节暂不搞复杂配置，场景相对固定                         |

### 一步生成与分步生成的本质

- **一步生成**：用户只交互一次，中间过程不可控（不代表只调一次模型，workflow 内部可以分拆处理）
- **分步生成**：中间环节可控、可看、可编辑，本质是"大要件"平台（5 步固定清单）
- 分步生成不等于"材料多才用分步"，而是"用户需要对中间环节把控"

### 文书生成路径层次

V1.1 将文书生成路径明确为三层：

- **材料（一步生成）**：默认路径，全案由全泛化，不做前置 Token 估算，直接调用 workflow。
- **分步生成（大要件）**：仅裁判文书展示，5 步硬编码序列，覆盖民商事五步法，用户逐步选材料、审中间结果、手动输入。
- **要件（可选 Plus）**：提纲挈领地把每个案例重点拎出来进行问答，有则提升上限，无则不影响生成。维护成本大幅下降（不配编目/指令/流程，仅作为"针对某案由的问答 query 清单"），法官自己都可维护。

材料量超限由 workflow 返回异常后提示，用户可选择分步"。

### 内容优化功能本源（原"追问"）

- **内容优化 vs 重新生成**：重新生成会丢失上下文、从头生成；内容优化基于"现有回答 + 原来材料 + 额外优化要求"做增量调整。
- **典型场景**：事实认定中证据冲突时，法官提出"我认哪个证据"的优化要求，AI 基于现有认定 + 材料 + 优化要求调整结果。
- **实现建议**：允许 2-3 轮内容优化即可（原型上限 3 轮）。每步生成结果、要件问答结果都应支持内容优化。

### 分步生成范围

- **仅裁判文书类型**展示分步生成 Tab（裁判文书是整个案件的 ending，用户需要中间把控度）
- 其他文书类型（庭审提纲、财务总结等）**只有一步生成 Tab**

## 6.2 Workflow 配置（管理后台侧）

> 配置入口：管理后台 → 文书类型管理 → 展开某文书类型 → Workflow 子表格
> **V1.1 仅保留一步生成的 Workflow 配置，分步生成的步骤序列硬编码前端，不入配置**

### 内置默认 Workflow

- **每个文书类型默认有且仅有 1 个内置"一步生成型" Workflow**（全兜底，`caseWords=[]`、`causes=[]`），供用户侧"一步生成" Tab 默认调用
- **不生成内置"分步生成型" Workflow**：分步生成的步骤序列由前端 `stepConfigsByOrg` 硬编码提供（仅裁判文书类型有配置），与管理后台 Workflow 配置完全解耦
- 内置 Workflow 可被自定义覆盖（编辑后另存为自定义，原内置保留可恢复）
- 用户侧分步生成匹配逻辑：`getWorkflowsForDocType(org, docTypeKey, 'step')` 返回空数组时，自动回退到 `stepConfigsByOrg[org][docTypeKey]`（仅裁判文书有）

### 功能1：Workflow 新增/编辑（仅一步生成型）

- **功能描述**：为文书类型配置一步生成的 Workflow，设定匹配规则
- **输入**：
  - Workflow ID（下拉单选，数据来自 agentflow 平台已编排的 Workflow 列表，同类型下不可重复）
  - 类型（固定为一步生成型，V1.1 不配置分步生成型）
  - 匹配案由（从当前业务系统案由树中勾选，支持一级、二级、三级节点；留空表示兜底）
  - 匹配案字（多选标签，留空表示兜底；**按已选案由联动过滤**，仅展示已选案由所属大类允许的案字白名单）
- **输出**：Workflow 配置记录
- **交互规则**：
  - 编辑内置 Workflow 时 ID 下拉只读，标题显示"另存为自定义覆盖"
  - 同类型下案字不可重复
  - 同类型下案由字符串不可重复（支持一级/二级/三级节点任意勾选）
  - 选中案由节点高亮显示（`var(--accent-light)` 背景 + `var(--accent-primary)` 边框/文字）
  - **匹配案由选择器位于匹配案字选择器上方**（先选案由再选案字，符合"案由定大类、案字定子类"的决策顺序）
  - **案字白名单联动**：勾选/取消案由时，案字选择器按已选案由所属大类的并集重新渲染
    - 案字选项仅展示当前所有已选案由所属大类允许的案字白名单的并集
    - 未选任何案由时，案字选择器展示当前业务系统的全部案字（不做约束）
    - 已选案字若因取消案由导致不在新白名单内，自动从已选集合中移除（界面同步取消勾选）
    - 已被同类型其他 workflow 占用的案字标记⚠，不可选
- **异常case**：Workflow ID 被同类型其他 Workflow 占用时从下拉中过滤掉

### 功能2：Workflow 匹配逻辑

- **功能描述**：用户侧文书生成时，系统按案字 + 案由双维度 5 级优先级自动匹配 Workflow
- **系统处理逻辑**（用户不感知）：
  1. 案字 + 案由 双精确匹配
  2. 案字精确 + 案由兜底（案由为空）
  3. 案字兜底（案字为空）+ 案由精确
  4. 全兜底（案字和案由均为空）
  5. 取第一个同类型 Workflow
- **输出**：匹配到的 Workflow（其内部模型配置由 agentflow 平台决定，前端不读取 workflow 的 `modelId` 字段）
- **异常case（三种兜底场景）**：
  - **场景1：Workflow 未配置**（该文书类型在管理后台未配置 Workflow）→ 该文书类型在用户侧不展示
  - **场景2：Workflow 存在但都不匹配当前案字+案由**→ 走 5 级优先级最后一级"取第一个同类型 Workflow"
  - **场景3：该文书类型根本没有任何 Workflow**→ 用户侧该文书类型不可选，提示"该文书类型尚未配置生成流程，请联系管理员"

## 6.3 Workflow 消费（用户侧）

### 模型来源与留痕

- 用户侧**不展示模型字段**（降低用户认知负担）
- 模型由匹配到的 Workflow 在 agentflow 平台内部决定，用户无需感知
- 文书版本快照中仍保留 `modelId` 字段供留痕与精修回显（回退默认模型或继承旧版本）
- 无匹配时回退默认模型

### 决定生成方式可用性

- 一步生成 Tab：所有文书类型默认展示
  - 该文书类型无 Workflow 配置 → 提示"该文书类型尚未配置生成流程，请联系管理员"
- 分步生成 Tab：**仅裁判文书类型展示**
  - 其他文书类型不展示分步生成 Tab
  - 裁判文书类型无 Workflow 配置 → 同上提示

### Workflow 入参传递

- 用户在生成文书配置区选择/自动判定的「案件阶段」作为字段传递给 workflow
- workflow 接收案件阶段字段后，由内部判断走哪个分支流程（如一审分支/二审分支）
- 业务端不感知 workflow 内部分支逻辑，仅负责传递字段值
- 案件阶段字段同时决定前端分步步骤序列（一审 5 步 / 二审 6 步），前后端协同

### 分步生成步骤序列（V1.1 硬编码）

- **V1.1 步骤序列硬编码在前端**（法院民商事场景固定 5-6 步，**V1.1.3 起按案件阶段决定**：一审 5 步 / 二审 6 步）
- 步骤名硬编码（如：案件信息、原告诉请、被告抗辩、争议焦点、裁判结果）
- 每步对应一个独立的 API 调用（workflow 作为端到端 API）
- 每步入参从页面表单取值（前端抓值，不查后台）
- 后续场景扩展时复制模块改代码（不做配置化）
- **V1.1.3 案件阶段判断**：步骤序列判断逻辑从"按案字判断"统一改为"按案件阶段判断"。案件阶段来源：有案字时按案字→阶段映射自动判定，无案字时由用户在生成配置区选择（见 5.2 功能2.5）

## 6.4 Token 限制判断

**前端不做 Token 估算和超限判断**，由 workflow 内部处理。

### 处理流程

1. 前端直接调用 workflow，不做前置 Token 估算
2. workflow 内部判断材料量，超限时返回异常
3. workflow 第一步就判断材料量，超限快速返回
4. 前端根据 workflow 返回的异常展示提示

### 异常处理

| 场景          | workflow 返回 | 前端处理                             |
| :---------- | :---------- | :------------------------------- |

# 八、案件状态与流转机制

## 8.1 案件状态表达

案件**不设独立的状态字段**，通过"材料数量 + 文书数"两个派生指标体现当前状态：

| 材料数量 | 文书数 | 用户感知状态 | 列表页视觉标识                 |
| :--- | :-- | :----- | :---------------------- |
| 0    | 0   | 待上传    | 材料数量单元格显示"-"，灰色         |
| >0   | 0   | 待生成    | 材料数量显示数字，正常色            |
| >0   | ≥1  | 已生成    | 材料数量显示数字 + 案件名称后蓝色文书数徽章 |

- **不加状态筛选器**，用户通过材料数量/文书数自行判断
- 材料数量列只表达材料本身状态（无材料/解析中/异常/正常），不混入文书数
- 材料数量包含：已解析材料 + 解析异常材料（异常材料单独标黄）
- 文书数包含：该案件下所有文书类型、所有版本的文书总数，以案件名称后蓝色徽章形式展示
- 点击文书数徽章：打开历史文书弹窗（"更多"下拉也保留"历史文书"入口，两处入口行为一致）

## 8.2 案件状态流转图

```
┌─────────────┐  上传材料  ┌─────────────┐  解析完成  ┌─────────────┐
│  待上传     │ ────────→ │  材料解析中  │ ────────→ │  可生成文书  │
│ (材料数量=0) │           │             │           │ (材料数量>0) │
└─────────────┘           └──────┬──────┘           └──────┬──────┘
                                 │                                │
                                 │ 解析异常                        │ 生成文书
                                 ↓                                ↓
                          ┌─────────────┐                 ┌─────────────┐
                          │  解析异常   │                 │  已生成文书  │
                          │(黄色标签)   │                 │ (文书数≥1)   │
                          └──────┬──────┘                 └─────────────┘
                                 │                                │
                                 │ 重新上传/删除异常材料            │ 继续生成更多文书
                                 └──────────────────────────────────┘
```

**流转规则**：

- "待上传"→"材料解析中"：用户上传文件后立即进入解析中
- "材料解析中"→"可生成文书"：全部文件解析完成
- "材料解析中"→"解析异常"：部分或全部文件解析失败（不阻塞已成功部分）
- "可生成文书"→"已生成文书"：成功生成至少一份文书
- "已生成文书"→"可生成文书"：删除全部文书后回退
- 任意状态均可删除案件

## 8.2.1 主链路按钮可用性约束

基于案件状态流转，主链路关键按钮的可用性规则汇总：

| 按钮            | 可用条件            | 置灰条件              | 置灰提示                               |
| :------------ | :-------------- | :---------------- | :--------------------------------- |
| 生成文书（列表页/详情页） | 案件有材料且全部解析成功    | 无材料（材料数量=0）       | "请先上传材料"                           |
| <br />        | <br />          | 存在解析中材料           | "材料解析中，请稍候"                        |
| 历史文书（列表页/详情页） | 案件文书数 ≥ 1       | 案件从未生成过文书（文书数=0）  | hover 提示"该案件暂无历史文书"                |
| 批量生成（列表页）     | 勾选的案件全部有材料且解析完成 | 勾选案件存在解析中材料       | 单案件置灰，批量栏提示"部分案件材料解析中"             |

> **注**：Token 超限不做前置判断，由 workflow 返回异常后展示提示（见 6.4）

## 8.3 管理后台案件管理状态

管理后台案件管理（admin/cases.html）同样不设独立状态字段，但额外支持：

- **软删除状态**：`isDeleted` 标记，已删除案件显示"已删除"徽章
- 软删除后操作列变为"查看/恢复"，不进入正常列表
- 管理后台案件管理为**可编辑模式**（仅法院业务场景，不支持切换业务系统）：
  - 可编辑案件结构化信息（案件名称、案号、案由、当事人、承办人、案字等）
  - 可增加或更改承办人（独立功能，支持多人协作场景，从已有用户中勾选，按部门树展示用户列表，支持按用户名搜索）
  - 可查看案件材料树（点击文件数弹窗展示分类材料列表，支持预览材料内容）

  - 可删除/恢复案件
  - 支持软删除与恢复
- **列配置**：支持自定义显示列（案号、案由、当事人、承办人、部门、上传日期、案字），默认显示最小列集（案件名称、文件数、文书数、更新时间、操作）

# 九、分步生成步骤数据流

> 步骤序列硬编码前端，不依赖 agentflow SSE 动态返回。

## 9.1 步骤输入输出模型

V1.1 分步生成的步骤序列**硬编码在前端**（法院民商事场景固定 5-6 步）。前端职责是：

1. 按硬编码的步骤序列渲染步骤列表
2. 每步用户手动选择材料、点击"生成"按钮
3. 入参从页面表单取值（前端抓值，不查后台）
4. 每步对应一个独立的 API 调用（workflow 作为端到端 API）

### 输入模型

每个步骤的输入：

- **该步用户选择的材料**（步骤级选择，非全局共享）
- **前序步骤的输出**（从页面表单取值，前端抓值）
- **案件上下文**（案由、案字等基本信息）

```
步骤输入 = f(该步已选材料, [前序步骤输出（从表单取值）], 案件上下文)
```

### 输出模型

每个步骤的输出：

- **文书片段**：文书的一个章节（如"事实查明"段落），最后拼接成完整文书
- 或**结构化数据**：JSON 格式的中间结果，最后由"生成文书"统一渲染

## 9.2 步骤数据流图

### 场景A：片段拼接型（裁判文书分步生成，V1.1 硬编码）

```
材料 ──→ [步骤1: 原告诉请] ──→ 文书片段1（诉请段）
         [该步材料 + 表单取值]        ──→ 文书片段2（抗辩段）
         [步骤2: 被告抗辩]
         [该步材料 + 表单取值]        ──→ 文书片段3（争议段）
         [步骤3: 争议焦点]
         [该步材料 + 表单取值]        ──→ 文书片段4（事实段）
         [步骤4: 事实认定]
         [该步材料 + 表单取值]        ──→ 文书片段5（主文段）
         [步骤5: 裁判结果]
         [该步材料 + 表单取值]
                                    │
                                    ↓
                              [生成文书] ──→ 完整文书
                              (拼接片段1+2+3+4+5)
```

### 场景B：结构化数据型（后续扩展场景）

```
材料 ──→ [步骤1: 证据提取] ──→ 结构化数据1（证据列表JSON）
         [该步材料 + 表单取值]  ──→ 结构化数据2（法条列表JSON）
         [步骤2: 法条匹配]
         [该步材料 + 表单取值]  ──→ 结构化数据3（量刑建议JSON）
         [步骤3: 量刑分析]
                                  │
                                  ↓
                            [生成文书] ──→ 完整文书
                            (用数据1+2+3
                             统一渲染)
```

> V1.1 仅实现场景A（法院民商事裁判文书）。场景B 为后续扩展预留，通过案件类型判断加载不同步骤序列。

## 9.3 步骤执行规则

### 步骤触发

- **手动逐步触发**：不支持一进来自动一步步走，必须手动一个个点（因为每步材料不一样，用户需要审材料）
- **选完材料后不自动触发生成**（用户可能调整材料），需手动点击"生成"按钮
- 每步完成后保留输出快照，用户可查看已完成步骤的结果
- 全部步骤完成后显示"生成文书"按钮，点击后组装最终文书

### 步骤间依赖

- 依赖项从页面表单取值（前端抓值，不查后台）
- 必填依赖项为空时阻止执行，提示"请先完成 XX 步骤"
- 选填依赖项为空时允许执行，传空值
- **V1.1 步骤依赖关系**（后续可能变化）：
  - 步骤1 原告诉请：无前置依赖
  - 步骤2 被告抗辩：无前置依赖
  - 步骤3 争议焦点：**可选**依赖步骤1+步骤2 的返回内容（选填，为空时允许执行）
  - 步骤4 事实认定：依赖步骤3 的返回内容（必填）
  - 步骤5 裁判结果：**仅支持直接输入**（合规要求，不调用 AI 生成，无前置依赖）

### 重新生成

- **当前步重新生成**：仅重新执行当前步骤，覆盖当前步输出，**不影响**已完成的后续步骤（后续步骤需用户手动重新触发才会刷新）
- **递归重置**（PRD登记，暂不实现）：重新生成某步时，递归重置该步及之后所有已完成步骤，用户需重新逐步生成

### Token 超限处理

- **前端不做 Token 估算**，直接调用 workflow
- workflow 返回超限异常时，提示"「步骤名」材料量过大，请减少材料"
- 不阻止该步生成按钮，由 workflow 返回后展示异常

## 9.4 SSE 事件流

正式接入时，步骤序列通过 SSE 事件流动态返回：

```
前端发起 Workflow 执行
        │
        ↓
SSE 事件1: { type: "node_start", nodeId: "step1", panelName: "当事人信息" }
        │
        ↓
（用户在人工交互节点确认/编辑）
        │
        ↓
SSE 事件2: { type: "node_complete", nodeId: "step1", output: {...} }
        │
        ↓
SSE 事件3: { type: "node_start", nodeId: "step2", panelName: "事实查明" }
        │
        ↓
... (循环直到所有节点完成)
        │
        ↓
SSE 事件N: { type: "workflow_complete", finalOutput: {...} }
```

**前端处理规则**：

- 收到 `node_start`：在步骤列表中新增该步骤，展示面板名
- 收到 `node_complete`：保存该步骤输出快照，标记为已完成
- 收到 `workflow_complete`：展示"生成文书"按钮
- 原型阶段用 `stepConfigsByOrg` mock 数据模拟，无真实 SSE

# 十、材料解析状态机

## 10.1 解析状态定义

| 状态   | 标识      | 说明                    |
| :--- | :------ | :-------------------- |
| 上传中  | -       | 文件正在上传至本地存储（原型阶段瞬时完成） |
| 解析中  | spinner | 文件上传完成，正在解析内容         |
| 解析完成 | 绿色对勾    | 解析成功，可参与文书生成          |
| 解析异常 | 黄色标签    | 解析失败，不参与文书生成，需用户处理    |

## 10.2 状态流转图

```
┌─────────┐  上传完成  ┌─────────┐  解析成功  ┌──────────┐
│ 上传中  │ ────────→ │ 解析中  │ ────────→ │ 解析完成  │
└─────────┘           └────┬────┘           └──────────┘
                           │
                           │ 解析失败
                           ↓
                      ┌──────────┐
                      │ 解析异常  │
                      └────┬─────┘
                           │
            ┌──────────────┼──────────────┐
            │              │              │
            ↓              ↓              ↓
      [重新解析]      [重新上传]      [删除文件]
      (原文件重试)   (替换为新文件)  (移出案件)
```

## 10.3 异常类型与处理

| 异常类型        | 表现              | 用户处理路径                           |
| :---------- | :-------------- | :------------------------------- |
| 格式不支持       | 文件名旁黄色标签"格式不支持" | 重新上传支持的格式（PDF/Word/Excel/TXT/图片） |
| 文件损坏        | 黄色标签"文件损坏"      | 重新上传完整文件                         |
| OCR 失败（扫描件） | 黄色标签"OCR失败"     | 重新上传可编辑版（非扫描件）                   |
| 内容为空        | 黄色标签"内容为空"      | 检查文件内容后重新上传                      |
| 文件过大        | 上传时拦截，不进入解析     | 上传符合大小限制的文件                      |

## 10.4 解析进度展示

### 案件列表页

- 材料数量单元格：解析中显示 spinner + 数字，异常材料数单独标黄
- 点击材料数量：打开"文件解析状态"弹窗，展示每个文件的解析状态

### 案件详情页

- **材料树仅展示解析成功的材料**（`parseStatus === 'success'`），解析中和解析异常的材料不在详情页展示
- 用户如需查看全部文件状态（含解析中、异常），请到案件列表页文件解析状态弹窗查看
- 材料树顶部显示解析进度概览："共 N 个文件，已解析 M 个，异常 K 个"（仅在存在未解析完成或异常文件时显示）

## 10.5 交互规则

- **解析触发**：文件上传完成后自动触发解析（原型阶段 mock 延时 2-3 秒模拟异步）
- **解析中不可生成文书**：案件列表页"生成文书"按钮在材料解析中时置灰，提示"材料解析中，请稍候"
- **详情页材料过滤**：案件详情页材料树仅展示 `parseStatus === 'success'` 的文件，解析中和异常文件不展示（详见 5.2 功能1）
- **部分异常不阻塞**：只要存在已解析成功的材料，即可生成文书；异常材料自动排除
- **批量解析**：批量上传时并行解析，互不影响
- **重新解析**：在文件解析状态弹窗中，对异常文件提供"重新解析"按钮

# 十一、文书版本管理

## 11.1 版本管理策略

**保留所有版本，按时间倒序展示。**

- 每次生成文书都保留为新版本，不覆盖已有版本
- 同一案件、同一文书类型可存在多个版本
- 不同文书类型各自独立版本管理

## 11.2 版本数据结构

每个文书版本包含：

| 字段               | 说明                       |
| :--------------- | :----------------------- |
| versionId        | 版本唯一标识（时间戳生成）            |
| docType          | 文书类型                     |
| templateId       | 使用的示例                    |
| promptText       | 使用的指令                   |
| modelId          | 使用的模型                    |
| genMethod        | 生成方式（material/step）      |
| materialSnapshot | 已选材料快照（材料ID列表 + Token估算） |
| content          | 文书正文内容                   |
| stepsSnapshot    | 分步生成时的步骤输出快照（仅分步生成）      |
| createdAt        | 生成时间                     |
| createdBy        | 生成人                      |

## 11.3 版本展示与操作

### 历史文书入口

- 案件列表页：操作栏"更多" → "历史文书"（案件文书数=0 时置灰，hover 提示"该案件暂无历史文书"）
- 案件详情页：顶部"历史文书"按钮（同上置灰规则）

### 历史文书列表

- 按生成时间倒序排列
- 每条记录展示：生成时间、文书类型、生成方式、版本号
- 操作：查看（跳转文书详情 `document-detail.html`）、精修（跳转文书精修页）、下载、删除（二次确认）

### 版本对比（暂不实现，PRD登记）

- 后续可支持两个版本的差异对比

## 11.4 重新配置

- 点击"重新配置"按钮，默认回填**最近一次历史文书快照**的配置（已选材料 + 模型/文书类型/示例/指令/生成方式）

# 十二、非功能需求

## 12.1 权限体系

| 角色    | 菜单权限           | 数据范围                      |
| :---- | :------------- | :------------------------ |
| 普通用户  | 用户侧全部页面        | 仅承办案件（"本人案件"指当前用户为承办人的案件） |
| 法院管理员 | 用户管理、部门维护、案件管理 | 仅本法院                      |
| 超级管理员 | 管理后台全部菜单       | 全部法院                      |

- 管理后台侧边栏菜单按 `adminRolePages` 配置动态过滤显示
- 法院管理员的法院筛选器固定为本法院，新增/编辑数据时法院字段锁定
- **"本人案件"定义**：指当前登录用户为该案件的**承办人**（非创建人、非参与人）
- **多人协作场景**：一个案件可有多个承办人，管理员可通过管理后台案件管理**增加或更改承办人**，让多个用户可处理同一案件
- 普通用户在案件列表页仅能看到自己作为承办人的案件；案件被指派为新承办人后，下次进入页面即可看到

## 12.2 数据存储

- 全部使用 localStorage（按业务系统分组的 JSON 对象）
- 内置数据 + 自定义覆盖语义：自定义一旦存在则整体覆盖内置
- 内置项停用通过 `__builtinDisabled__` 列表/字典管理，保留内置数据不删除
- 指令支持历史版本（最多 10 条快照，一键恢复）

## 12.3 原型文件离线可用

- 纯静态 HTML/CSS/JS，双击 `index.html` 即可运行
- 不依赖任何网络、服务器、构建工具
- 所有资源为本地相对路径引用

## 12.4 数据一致性

### 配置一致性

用户侧配置与管理后台配置的一致性策略：

- **进入页面时加载一次**：用户侧进入案件详情页/配置弹框时从 localStorage 加载最新配置
- **会话期间不实时刷新**：用户在配置生成参数的过程中，管理后台修改了文书类型/示例/指令/要件，用户侧**不做实时刷新**，避免打断用户操作
- **已展开的配置弹框不动态刷新**：下拉选项保持展开时的状态
- **配置变更下次进入才生效**：用户下次进入页面或重新打开配置弹框时加载最新配置
- **不校验配置有效性**：原型阶段简化处理，不校验所选配置是否已被删除（正式版需补充）

### 数据持久化策略

- **前端页面值为准**：用户在页面上看到的值是权威数据源
- **后端留痕**：持久化的目的是记录留痕，作为极端情况的回显兜底，不作为核心数据源
- **失败时提示用户，提供重试入口**：持久化失败不阻塞用户操作（除非失败未重试）
- **持久化失败处理**：展示提示"数据保存失败，请重试"，提供"重试"按钮，用户不重试则继续操作（数据仅留存在前端内存）

## 12.5 异常处理通用模式

| 场景        | 处理方式                    |
| :-------- | :---------------------- |
| 必填项为空     | 弹出错误通知，阻止保存             |
| 删除操作      | 关联校验（是否有下级/用户/案件）+ 二次确认 |
| 空状态       | 显示图标与提示文案               |
| JSON 解析失败 | try-catch 保护，返回空对象/空数组  |
| Token 超限  | 按场景提示切换分步生成或减少材料        |
