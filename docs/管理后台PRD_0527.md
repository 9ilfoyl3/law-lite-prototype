# 二、产品概述

## 2.1 产品背景

AI辅助办案系统管理后台是为系统管理员提供的综合管理界面。作为AI法官助理的核心支撑模块，管理后台承担用户管理、知识库维护、案由配置、风控审计、系统配置等关键职能，确保系统安全、合规、高效运行。

## 2.2 目标用户

- **超级管理员**：负责系统整体配置、用户管理、安全审计
- **系统管理员**：负责用户管理、基础配置、系统监控
- **业务管理员**：负责案由、知识库等业务数据维护

## 2.3 产品定位

管理后台是AI辅助办案系统的核心支撑模块，覆盖以下管理职能：

- 用户全生命周期管理（创建、禁用、角色绑定、用量统计）
- 系统初始化配置（部署时一次性配置，配完锁定）
- 业务数据维护（案由分类体系、知识库分类与文档）
- 风控与审计管理（敏感词库、审计日志）
- 系统运行报告（周报/月报，支持导出PDF）

所有管理操作遵循基于角色的访问控制（RBAC），审计日志不可篡改。

### 2.4 功能审计三原则

每新增一个管理后台功能前，必须通过以下三项检查：

| 原则 | 检查问题 | 判定 |
| :--- | :--- | :--- |
| 频率检查 | 这个操作一个月会做超过一次吗？ | 不会 → 不需要管理后台页面，走配置文件或初始化脚本 |
| 角色检查 | 法院IT有这个专业能力操作吗？ | 不会（如"编辑Prompt"） → 不需要暴露给他 |
| 合规检查 | 不做这个，会被纪检/等保/合规卡住吗？ | 会 → 必须做 |

## 4.3 系统运行报告

**页面路径**：`pages/admin/system-report.html`

### 4.3.1 功能概述

为法院领导汇报提供系统运行情况的静态报告，支持按周/月生成报告并导出PDF。不做实时数据看板，不做交互式图表。

> **定位变更说明**：原"数据仪表盘"定位为实时数据看板，但G端内网系统不存在DAU驱动的运营需求，法院领导需要的是可导出的汇报材料，而非实时折线图。按频率检查原则，领导看报告是周/月频次，不需要实时刷新。

### 4.3.2 报告类型

| 报告类型 | 生成周期 | 说明 |
| :--- | :--- | :--- |
| 周报 | 每周一自动生成 | 覆盖上周数据 |
| 月报 | 每月1日自动生成 | 覆盖上月数据 |
| 自定义报告 | 手动触发 | 选择时间范围生成 |

### 4.3.3 报告内容

报告以文档形式呈现，包含以下章节：

**一、系统运行概况**

| 指标 | 说明 |
| :--- | :--- |
| 报告周期 | 本周/本月 |
| 系统运行天数 | 周期内系统正常运行天数 |
| AI任务总数 | 周期内所有智能体任务总数 |
| 文书生成采纳率 | AI输出被法官直接采用的比例 |
| 平均案件处理时长 | 从收案到结案的平均耗时 |

**二、各模块使用情况**

| 模块 | 任务数 | 采纳率 | 较上期变化 |
| :--- | :--- | :--- | :--- |
| 文书生成 | xx | xx% | ↑/↓ |
| 庭审提纲 | xx | xx% | ↑/↓ |
| 法条适用 | xx | xx% | ↑/↓ |
| 文书评查 | xx | xx% | ↑/↓ |
| 知识问答 | xx | — | ↑/↓ |

**三、部门使用排名**

按部门统计AI使用次数排名（Top5），含部门名称、使用次数、较上期变化。

**四、异常与风险**

| 指标 | 说明 |
| :--- | :--- |
| AI生成失败次数 | 周期内生成失败总数 |
| 敏感词拦截次数 | 周期内风控拦截总数 |
| 系统异常事件 | 周期内系统异常事件列表 |

### 4.3.4 报告操作

| 操作 | 说明 |
| :--- | :--- |
| 查看报告 | 在线预览报告内容 |
| 导出PDF | 导出为PDF文件，文件名格式：`系统运行报告_{类型}_{周期}.pdf` |
| 历史报告 | 查看和导出历史生成的报告 |

### 4.3.5 数据来源

所有数据来源于埋点系统，报告生成时自动聚合计算，不支持手动编辑报告内容。

### 4.4.2 文档管理

#### 文档列表

#### 文档上传

**上传方式**：

**上传弹窗**：

```

│           └─────────────┘           │
│                                     │

│    单个文件最大50MB                 │
│                                     │
├─────────────────────────────────────┤
```

**上传处理流程**：

1. 选择文件→格式校验→显示预览
2. 选择目标知识库
3. 点击上传→显示进度条
4. 文件解析处理→索引构建
5. 上传完成→返回文档列表

**支持格式及图标颜色**：

| 格式 | 图标颜色 |
| :--- | :--- |
| PDF | 红色 |
| Word/Doc/Docx | 蓝色 |
| TXT | 灰色 |
| Markdown | 橙色 |

**文件大小限制**：

- 单个文件最大：50MB
- 批量上传：最多10个文件

#### 文档状态管理

**法条文档**：

- 支持"有效/废止"标记
- 废止法条不参与AI推荐和检索
- 状态变更需二次确认

**案例文档**：

- 支持"上架/下架"操作
- 下架案例不参与类案推荐

**异常处理**：

- 上传未脱敏或包含违规内容的文档，系统应告知风险并拒绝入库
- 文件解析失败时，状态标记为"解析失败"，支持重新解析

#### 文档删除

- 二次确认弹窗
- 提示删除后不可恢复
- 删除后对应的解析文本和索引同步清除

## 4.5 案由管理

**页面路径**：`pages/admin/cause-management.html`

### 4.5.1 功能概述

管理系统案由分类体系，支持三级案由层级结构。案由数据供AI案由明鉴模块和Chat页面用户选择使用。

### 4.5.2 统计卡片

| 指标 | 说明 |
| :--- | :--- |
| 一级案由 | 一级分类数量 |
| 二级案由 | 二级分类数量 |
| 三级案由 | 三级分类数量 |
| 案由总数 | 全部案由合计 |

### 4.5.3 案由树形结构

**层级定义**：

- **一级案由**：大类（如民事案由、刑事案由）
- **二级案由**：中类（如合同纠纷、侵权责任纠纷）
- **三级案由**：具体案由（如买卖合同纠纷、离婚纠纷）

**默认数据示例**：

```
民事案由
├── 合同纠纷
│   ├── 买卖合同纠纷
│   ├── 借款合同纠纷
```

### 4.5.8 案由状态管理（上线/下线）

**功能描述**：每个案由节点支持"上线/下线"状态切换，控制该案由在前端是否可见可用。

**状态定义**：

| 状态 | 说明 | 前端可见性 |
| :--- | :--- | :--- |
| 已上线 | 案由已发布，可供前端用户选择使用 | 可见、可选 |
| 未上线 | 案由未发布或已下线，仅管理后台可见 | 不可见、不可选 |

**操作规则**：

- **上线操作**：点击"上线"按钮，案由状态切换为"已上线"，前端即时生效
- **下线操作**：点击"下线"按钮，需二次确认弹窗提示："下线后，前端用户将无法看到和选择该案由，已关联该案由的案件在前端也将不可见，确认下线？"，确认后状态切换为"未上线"
- **批量操作**：支持对一级/二级案由批量上线/下线，操作时联动其下所有子案由状态同步变更
- **默认状态**：新建案由默认为"未上线"状态，需管理员手动上线后才对前端可见

**数据结构**：

案由数据中每个节点增加 `status` 字段：

```json
{
  "name": "买卖合同纠纷",
  "status": "online",
  "children": []
}
```

- `status` 取值：`"online"`（已上线）/ `"offline"`（未上线，默认）
- 上线/下线操作时同步更新 `adminCauseData` 和 `causeData`

**数据流向**：

```
管理后台（案由管理页面）
  ├── 新增/编辑案由 → 写入 adminCauseData（含status字段）
  ├── 上线/下线操作 → 更新 adminCauseData 中对应节点status
  └── 同步写入 causeData → 前端页面读取
        ├── Chat页面案由选择器 → 仅加载 status=online 的案由
        ├── 案件页面案由筛选器 → 仅加载 status=online 的案由
        └── 首页案由推荐 → 仅展示 status=online 的案由
```

### 4.5.9 边界场景与异常数据处理

**场景1：下线案由下的案件在前端的可见性**

| 场景 | 规则 | 说明 |
| :--- | :--- | :--- |
| 案由下线后，该案由下的已有案件 | 前端不可见、不可搜 | 案件列表和搜索结果均需过滤掉关联案由为"未上线"的案件 |
| 案由下线后，用户搜索案件关键词命中下线案由的案件 | 不返回结果 | 搜索时需校验案件关联案由的上线状态 |
| 案由重新上线后，之前的案件 | 自动恢复可见 | 无需手动操作，案件随案由上线自动恢复展示 |
| 案由下线后，案件详情页的直接访问 | 提示"该案件关联案由已下线" | 防止通过URL直接访问 |

**场景2：数据一致性保障**

| 异常情况 | 处理策略 |
| :--- | :--- |
| 案件的案由字段为空 | 前端不展示该案件，管理后台标记为"案由缺失"待处理 |
| 案件的案由在案由树中不存在（被删除） | 前端不展示该案件，管理后台标记为"案由异常"待处理 |
| localStorage数据被清空 | 前端使用内置默认案由数据兜底，管理后台提示"数据异常，请重新配置" |
| causeData与adminCauseData不同步 | 以adminCauseData为准，管理后台保存时强制同步写入causeData |

**场景3：层级联动规则**

- 一级案由下线 → 其下所有二级、三级案由自动下线（前端均不可见）
- 二级案由下线 → 其下所有三级案由自动下线
- 一级案由上线 → 不自动上线子案由，需逐个手动上线
- 删除案由 → 已关联该案由的案件标记为"案由异常"，前端不展示

**默认预置参数模板**（新建模型时按模型分类自动填充默认参数）：

##### 思考模式配置块（thinkingMode，字段类型：object）

"思考模式"为专用配置块，以独立卡片形式展示在模型参数区域顶部，不作为动态键值对行，而是结构化的 object 字段：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| enabled | Boolean | 是 | false | 是否启用思考模式（深度推理） |
| display_style | String | 否 | "collapsible" | 思考过程展示方式：collapsible（可折叠，默认收起）/ inline（内联展示） |
| token_limit | Number | 否 | 8192 | 思考模式最大思考Token数 |
| filter_english | Boolean | 否 | true | 是否过滤思考输出中的英文内容 |

**交互说明**：

- enabled=false 时，其余字段置灰不可编辑
- enabled=true 时，展开所有配置项
- display_style 选项：
  - `collapsible`：思考过程以可折叠区块展示，默认收起，用户可点击展开查看推理过程
  - `inline`：思考过程直接内联展示在回复内容中
- filter_english=true 时，显示 english_filter_mode 选项
- filter_english=false 时，english_filter_mode 置灰

**思考输出英文过滤规则**（filter_english=true时生效）：

| 规则 | 匹配逻辑 | 处理方式 |
| :--- | :--- | :--- |
| 连续英文句子 | 连续3个以上英文单词的片段 | 按 english_filter_mode 处理（移除或翻译） |
| 英文术语夹杂 | 单个英文词前后有中文 | 保留不动（如"根据PDF文件"、"调用API接口"） |
| 纯英文段落 | 整段无中文字符 | 按 english_filter_mode 处理 |
| 合法英文白名单 | 常见法律术语缩写、当事人英文名、证据编号 | 保留不动（如"DNA鉴定"、"A公司"） |

**英文过滤分层治理方案**：

| 层级 | 策略 | 说明 | 效果 |
| :--- | :--- | :--- | :--- |
| 第1层 | 系统提示词约束 | 在模型system prompt中强制约定"必须使用中文思考和回复，禁止使用英文" | 从源头减少，解决80% |
| 第2层 | 思考输出后处理 | filter_english配置项控制的正则规则过滤 | 精准清洗漏网的英文片段 |
| 第3层 | 展示层兜底 | display_style=collapsible默认折叠思考过程，用户不展开则无感 | 兜底保障 |

**数据结构**：


## 4.10 要件管理

**页面路径**：`pages/admin/element-presets.html`

### 4.10.1 功能概述

维护各业务系统下、按案由分组的标准要件库。标准要件用于文书生成时作为「要件引导」的上下文，与用户侧「我的要件」分层并存：管理员维护的标准要件对所有用户可见，普通办案人员维护的「我的要件」仅对本人可见，文书生成时两者合并展示并分别加「标准」「我的」标识。

按功能审计三原则：要件库维护属于业务数据维护（业务管理员职责），随新案由/新业务调整，符合频率检查；法院IT可操作（选择案由→填写要件名/说明/问题），符合角色检查；不涉及合规强制要求。

### 4.10.2 数据结构

```js
// localStorage.adminElementPresets 结构（按业务系统 × 案由分组）
{
    court: {
        '民间借贷纠纷': [
            { name: '借款合意', desc: '借贷双方是否存在借款协议或借条', question: '借款协议/借条签订时间、地点、金额分别是？' },
            { name: '款项交付', desc: '出借人实际支付借款的凭证', question: '实际出借金额及支付方式？' }
        ],
        '离婚纠纷': [ ... ]
    },
    procuratorate: { ... },
    justice: { ... }
}
```

**覆盖语义**：`adminElementPresets[org][cause]` 一旦存在，**整体覆盖** `elementPresetsByCause[cause]` 内置要件数组（不做字段级合并）。删除某案由的自定义配置即恢复内置。

### 4.10.3 页面结构

页面采用「左侧案由树 + 右侧要件表格」双栏布局。

```
[管理后台 - 要件管理页面]
    │
    ├─ 顶部：页面标题 + 描述 + 业务系统切换按钮组（法院/检察院/司法局，默认法院）
    │
    ├─ 左侧：案由树（3 级结构，与新增案件案由选择器一致，来自 causeTreeDataByOrg）
    │       ├─ 顶部搜索框：输入关键词实时过滤叶子案由，匹配项的父级自动展开；无匹配显示「无匹配案由」
    │       ├─ 置顶分组：常用案由可置顶，集中显示在树顶部「置顶」分组下（按业务系统分组存储 localStorage.adminPinnedCauses）
    │       ├─ 「全部」项：显示当前业务系统案由总数

    │       ├─ level-2 中类（如「婚姻家庭纠纷」）：可选中或展开/折叠
```

### 4.10.4 要件操作

**新增要件**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| 要件名 | 文本 | 是 | 失焦校验非空 |
| 要件说明 | 文本 | 否 | 简要说明该要件的含义 |
| 问题 | 文本域 | 是 | 生成文书前需确认的单一问题 |

**编辑要件**：
- 自定义要件：直接编辑原条目
- 内置要件：编辑后将整条另存为自定义覆盖（弹窗标题为「编辑内置要件（另存为自定义）」），写入 `adminElementPresets[org][cause]`

**删除要件**：
- 自定义要件：二次确认后从 `adminElementPresets[org][cause]` 移除
- 内置要件：删除按钮置灰，不可直接删除；如需删除请先「恢复内置」后重新维护

**恢复内置**：
- 仅当该案由已自定义覆盖时显示
- 二次确认后清除 `adminElementPresets[org][cause]` 整个 key，还原为系统内置要件

### 4.10.5 数据持久化

- 存储 Key：`localStorage.adminElementPresets`（按业务系统 × 案由分组）
- 置顶列表 Key：`localStorage.adminPinnedCauses`（按业务系统分组）
- 内置兜底数据：`case-data.js` 的 `elementPresetsByCause` 常量；案由不在内置表中时回退到通用要件（主体资格/事实认定/法律适用/程序合法/处理结果）

### 4.10.6 用户侧联动

`case-data.js` 的 `getElementPresets(cause, org)` 读取优先级：

1. 若 `adminElementPresets[org][cause]` 存在 → 返回该自定义数组
2. 否则若 `elementPresetsByCause[cause]` 存在 → 返回内置
3. 否则返回通用要件兜底

`getAllElementPresets(cause, org)` 透传 org，在标准要件基础上合并用户侧「我的要件」。调用方（`cases.js`、`case-files.js`）从 `localStorage.getItem('currentBusiness') || 'court'` 取 org 后传入。

| 该类型下仍存在模板（`adminDocTemplates` / `myDocTemplates` / 内置模板中有 `docType === typeKey`） | 「请先迁移或删除该类型下的 N 个模板」 |
| 该类型下仍存在提示词（`adminPromptTemplates` / `myPromptTemplates` / `defaultRequirementTemplates` 中有对应 key） | 「请先清理该类型下的提示词」 |

校验通过后二次确认删除。内置类型删除 = 移除自定义覆盖（恢复内置默认）；删除类型时同步清理该类型下的 workflow 配置。

### 4.11.6 用户侧联动

- `case-data.js` 初始化时调用 `mergeAdminDocTypes(org, system)`，将 `localStorage.adminDocTypes[org]` 合并到 `system.docTypes`（覆盖同名内置 key，不保留 `templates` 数组）
- `getCurrentDocTypes()` 返回合并后的类型映射，用户侧生成文书时「文书类型」下拉选项自动包含自定义类型
- `getDocTypeTemplates(docTypeKey)` 改为反查：遍历 `getCurrentTemplates()` 返回所有 `docType === docTypeKey` 的模板，不再依赖 `type.templates` 数组
- 文书模板管理 / 提示词管理 / 我的模板 / 我的提示词 四个页面的左侧类型列表和下拉选项统一通过 `getAdminDocTypes(org)` 读取合并后的数据源

### 4.11.7 workflow 子配置（内联于文书类型管理页）

**功能描述**：workflow 是系统内部配置，**对用户完全不可见**。其本质是「分步生成模式下，使用哪一套步骤序列」的配置容器，按「业务系统 × 文书类型」分组。用户侧只看到「材料生成 / 分步生成」两个 tab 与带出的步骤序列，不感知 workflow 概念。

workflow **不绑定生成策略**：案件列表页由 token 自动决定模式；案件详情页用户选 tab；只有走「分步生成」时，才根据案件案字匹配 workflow 取其步骤序列。

**配置入口**：不单独开模块、不增加菜单项。在文书类型管理页表格中，每个类型行新增「展开/折叠」按钮（行首 `fa-chevron-right` / `fa-chevron-down`）。点击展开后，在类型行下方显示该类型下的 workflow 子表格，区域标题为「{类型名} 的 workflow」+「新增 workflow」按钮。

**workflow 数据结构**：

```js
// localStorage.adminWorkflows 结构（按业务系统分组）
{
    court: {
        judgment: [
            {
                id: 'wf-judgment-1st',           // workflow 唯一 id
                name: '一审民事判决',             // workflow 显示名（仅后台可见）
                caseWords: ['民初', '民再'],      // 匹配的案字（多选，空数组 = 兜底）
                steps: [                          // 步骤序列（顺序即执行顺序）
                    { id: 'caseInfo', title: '案件信息', icon: 'fa-folder-open' },
                    { id: 'plaintiff', title: '原告诉请', icon: 'fa-user-tie' },
                    ...
                ],
                isBuiltin: true                   // 是否内置（迁移自 stepConfigsByOrg）
            },
            ...
        ],
        trial: [ ... ]
    },
    ...
}
```

**覆盖语义**：`adminWorkflows[org][docTypeKey]` 一旦存在，**整体覆盖** `stepConfigsByOrg[org][docTypeKey]` 的内置步骤数组。删除某类型的全部自定义 workflow 即恢复内置。

**内置数据迁移**：系统首次加载时，若 `adminWorkflows` 为空，`getWorkflowsForDocType` 会将 `stepConfigsByOrg` 的内容包装成内置 workflow（每个 docType 一个默认 workflow，`caseWords: []`，`isBuiltin: true`）。管理员可在此基础上新增「民终」「刑初」等 workflow。

**workflow 子表格结构**：

```
[文书类型行展开后]
    │
    └─ workflow 子表格
        ├─ 表头：workflow 名称 | 匹配案字 | 步骤数 | 来源 | 操作
        ├─ 每行：名称 | 案字标签组（或「兜底」）| 步骤数量 | 内置/自定义 | 编辑/删除
        └─ 顶部「新增 workflow」按钮
```

**新增/编辑 workflow**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| workflow 名称 | 文本 | 是 | 如「一审民事判决」（仅后台可见） |
| 匹配案字 | 多选 checkbox | 否 | 从当前业务系统 `caseWordListByOrg` 取；不选任何案字 = 兜底 workflow |
| 步骤序列 | 步骤编辑器 | 是 | 至少 1 个步骤 |

**案字冲突校验**：同一 docType 下，案字不可在多个 workflow 间重复（保存时校验）。已被其他 workflow 匹配的案字在选项后显示 ⚠ 提示。

**步骤编辑器**：
- 每行包含：步骤 id（必填，如 `caseInfo`）、步骤标题（必填）、图标（从预设图标库选）、操作按钮（上移 / 下移 / 删除）
- 「上移」/「下移」调整步骤顺序，列表实时重排
- 「删除」移除该步骤（至少保留 1 个，否则禁用删除按钮）
- 「+ 添加步骤」在列表底部追加一行空步骤
- 步骤 id 需保证同 workflow 内唯一（保存时校验重复）

**删除 workflow**：
- 内置 workflow 删除 = 移除自定义覆盖（恢复内置默认）
- 自定义 workflow 删除 = 直接移除
- 若该类型下仅剩此一个 workflow，禁止删除并提示「每个文书类型至少需保留 1 个 workflow」

**workflow 用户侧联动（对用户不可见）**：

案件详情页用户选「分步生成」tab 时：

1. 系统从案件 `caseNumber` 中提取案字（正则匹配 `民初/民终/民再/刑初...`）
2. 调用 `getStepsConfigForDocType(docTypeKey, caseWord)`：
   - 优先读 `localStorage.adminWorkflows[org][docTypeKey]`
   - 精确匹配案字 → 返回该 workflow 的 steps
   - 匹配不到 → 返回 `caseWords: []` 的兜底 workflow 的 steps
   - 无兜底 workflow → 返回第一个 workflow 的 steps
   - 该 docType 无任何 workflow → 回退到内置 `stepConfigsByOrg[org][docTypeKey]`
3. 用户在分步视图看到的步骤序列即为匹配结果，**不显示 workflow 名称**

案件列表页生成文书：由 token 自动决定模式（现状不变），不涉及 workflow。案件详情页用户选「材料生成」tab 时：不涉及 workflow（材料生成不分步）。

## 4.12 文书模板管理

**页面路径**：`pages/admin/doc-templates.html`

### 4.12.1 功能概述

维护各业务系统的文书模板，模板与「文书类型 + 案由」双重关联。用户侧生成文书时按当前案件 cause 自动过滤模板。模板数据结构升级为对象（原为字符串映射），支持关联文书类型、案由和模板正文。

按功能审计三原则：模板维护属于业务数据维护，符合频率检查；法院IT可操作（填名称、选类型、勾案由），符合角色检查；不涉及合规强制要求。

### 4.12.2 数据结构

```js
// localStorage.adminDocTemplates 结构（按业务系统分组）
{
    court: {
        'judgment-civil-1st': {
            name: '民事判决书（一审普通程序）',  // 模板显示名
            docType: 'judgment',                  // 所属文书类型 key
            causes: ['合同纠纷', '侵权责任'],     // 关联案由名称数组；空数组 = 通用（所有案由）
            content: ''                            // 模板正文（可选，预设片段）
        },
        ...
    },
    procuratorate: { ... },
    justice: { ... }
}
```

**数据结构升级兼容**：原 `businessSystems[org].docTemplates` 为 `key→字符串` 映射，升级为 `key→对象`。`case-data.js` 加载时做兼容处理：若旧数据为字符串，自动转为 `{name: 旧字符串, docType: '', causes: [], content: ''}`。

### 4.12.3 页面结构

页面采用「左侧文书类型列表 + 右侧模板表格」双栏布局。

```
[管理后台 - 文书模板管理页面]
    │
    ├─ 顶部：页面标题 + 描述 + 业务系统切换按钮组
    │
    ├─ 左侧：文书类型列表（点击筛选右侧模板）
    │       ├─ 全部（默认选中，显示模板总数）
    │       └─ 当前业务系统的文书类型项（来自 getAdminDocTypes，每项后缀显示该类型下模板数）
    │
    └─ 右侧：模板表格
            ├─ 表头：模板名 | 所属类型 | 关联案由 | 操作
            ├─ 每行：模板名+徽章 | 类型名 | 案由标签组或「通用」 | 编辑/删除
            └─ 顶部「新增模板」按钮
```

### 4.12.4 模板操作

**新增/编辑模板**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| 模板名 | 文本 | 是 | 失焦校验非空 |
| 所属文书类型 | 下拉选择 | 是 | 从当前业务系统 `getAdminDocTypes` 取 |
| 关联案由 | 多选 checkbox | 否 | 3 级案由树勾选，从当前业务系统案由树取；不选 = 通用模板 |
| 模板正文 | 文本域 | 否 | 模板预设片段 |

**保存规则**：
- 新增：生成唯一 key（`{docType}-` + 时间戳 base36）
- 编辑自定义：保留原 key 更新
- 编辑内置：使用内置 key 作为自定义覆盖（用户侧 `mergeAdminDocTemplates` 会覆盖），编辑时禁用文书类型切换以避免逻辑歧义

**删除模板**：
- 自定义模板：二次确认后删除
- 内置模板：不可删除（按钮不显示）

### 4.12.5 数据持久化

- 存储 Key：`localStorage.adminDocTemplates`（按业务系统分组）
- 内置兜底数据：`case-data.js` 的 `defaultDocTemplatesByOrg` 常量（字符串映射）
- 合并函数：`mergeAdminDocTemplates(org, system)` 在加载时将自定义模板合并到 `system.docTemplates`，覆盖同名内置 key

### 4.12.6 用户侧联动

`cases.js` 选文书类型后，模板下拉除按类型过滤外，**再按当前案件 `cause` 过滤**：

| 模板 causes | 过滤规则 |
| :--- | :--- |
| 空数组 | 始终显示（通用模板） |
| 包含当前案件 cause | 显示 |
| 不包含当前案件 cause | 不显示 |

若当前案件无 cause 或过滤后无可用模板，显示全部该类型模板作为兜底。`getFilteredDocTypeTemplates(docTypeKey, cause)` 实现此逻辑，过滤后无可用模板时返回全部该类型模板。

## 4.13 提示词管理

**页面路径**：`pages/admin/prompt-templates.html`

### 4.13.1 功能概述

维护「生成需求说明」的内置提示词模板，按业务系统 × 文书类型分组。用户侧生成文书时，提示词以标签形式展示，点击标签将提示词正文填入需求说明输入框。支持恢复默认。

按功能审计三原则：提示词维护属于业务数据维护，符合频率检查；法院IT可操作（选类型、填标签、填正文），符合角色检查；不涉及合规强制要求。

> **与 V1.3 移除的「角色与提示词管理」的区别**：V1.3 移除的是面向「角色」的 Prompt 配置（AI 系统级提示词，属于产品核心逻辑，由产品团队通过配置文件设定）。本节管理的是面向「文书类型」的「生成需求说明」快捷标签（用户侧可见可点的辅助输入项），属于业务数据维护范畴。

### 4.13.2 数据结构

```js
// localStorage.adminPromptTemplates 结构（同 defaultRequirementTemplates）
{
    court: {
        judgment: [
            { name: '支持原告全部诉请', text: '裁判方向：支持原告全部诉讼请求\n• 事实清楚...' },
            { name: '部分支持诉请', text: '...' }
        ],
        trial: [ ... ]
    },
    procuratorate: { ... },
    justice: { ... }
}
```

**覆盖语义**：`adminPromptTemplates[org][docTypeKey]` 数组一旦存在且非空，**整体覆盖** `defaultRequirementTemplates[org][docTypeKey]` 的内置数组。

### 4.13.3 页面结构

页面采用「左侧文书类型列表 + 右侧提示词列表」双栏布局。

```
[管理后台 - 提示词管理页面]
    │
    ├─ 顶部：页面标题 + 描述 + 业务系统切换按钮组 + 「恢复默认」按钮
    │
    ├─ 左侧：文书类型列表（点击筛选右侧提示词）
    │       ├─ 全部（默认选中，显示提示词总数）
    │       └─ 当前业务系统的文书类型项（每项后缀显示该类型下提示词数）
    │
    └─ 右侧：提示词列表
            ├─ 全部视图下按文书类型分组，显示类型分组标题
            ├─ 每项：来源徽章 | 正文预览（超 80 字截断折叠）| 标签名 | 编辑/删除
            └─ 顶部「新增提示词」按钮
```

### 4.13.4 提示词操作

**新增/编辑提示词**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| 所属文书类型 | 下拉选择 | 是 | 从当前业务系统 `getAdminDocTypes` 取 |
| 标签名 | 文本 | 是 | 失焦校验非空 |
| 提示词正文 | 文本域 | 是 | 支持 `\n` 换行；正文为空时需二次确认（用户点击该标签会清空需求说明输入框） |

**保存规则**：
- 新增：追加到 `adminPromptTemplates[org][docType]` 数组
- 编辑自定义（同文书类型）：原地更新对应下标
- 编辑自定义（跨文书类型）：先从原数组移除，再追加到新数组
- 编辑内置：把内置数据全部拷贝为自定义数组，再修改对应项（弹窗标题为「编辑内置提示词（另存为自定义）」），编辑时禁用文书类型切换

**删除提示词**：
- 自定义提示词：二次确认后从数组移除；数组清空时删除整个 docType key（恢复内置）
- 内置提示词：不可删除

### 4.13.5 恢复默认

- 点击顶部「恢复默认」按钮
- 二次确认弹窗：「确定恢复「{业务系统名}」所有提示词为系统默认值吗？自定义内容将丢失。」
- 确认后删除 `localStorage.adminPromptTemplates` 中当前业务系统的整个 key（不影响其他业务系统）
- 刷新页面，所有提示词还原为 `defaultRequirementTemplates` 内置值

### 4.13.6 数据持久化

- 存储 Key：`localStorage.adminPromptTemplates`（按业务系统 × 文书类型分组）
- 内置兜底数据：`case-data.js` 的 `defaultRequirementTemplates` 常量
- 读取函数：`getReqTemplates(org, docTypeKey)` 优先读 admin 自定义，为空回退到内置默认

### 4.13.7 用户侧联动

- `cases.js` 的 `renderReqTemplates` 优先读 `localStorage.adminPromptTemplates`，为空则回退到 `defaultRequirementTemplates` 内置默认值
- `case-files.js` 的 `renderMatReqTemplates` 同步适配
- 用户侧「我的提示词」数据（`localStorage.myPromptTemplates`）在 admin 数据之后追加，标记 `source: 'mine'`，标签加绿色 `.mine` 样式标识

**数据合并优先级（高 → 低）**：

1. 用户侧自定义（`my-` 前缀 / `.mine` 标签）
2. 管理后台自定义（覆盖同名内置）
3. 系统内置默认值（`defaultRequirementTemplates`）
