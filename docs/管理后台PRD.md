# 二、产品概述

## 2.1 产品背景

AI辅助办案系统管理后台是为系统管理员提供的综合管理界面。作为AI法官助理的核心支撑模块，管理后台承担用户管理、知识库维护、案由配置、风控审计、系统配置等关键职能，确保系统安全、合规、高效运行。

## 2.2 目标用户

- **超级管理员**：负责系统整体配置、用户管理、安全审计
- **系统管理员**：负责用户管理、基础配置、系统监控
- **业务管理员**：负责案由、知识库等业务数据维护

## 2.3 产品定位

管理后台是AI辅助办案系统的核心支撑模块，覆盖以下管理职能：

- 用户全生命周期管理（创建、禁用、角色绑定、用量统计）
- 系统初始化配置（部署时一次性配置，配完锁定）
- 业务数据维护（案由分类体系、知识库分类与文档）
- 风控与审计管理（敏感词库、审计日志）
- 系统运行报告（周报/月报，支持导出PDF）

所有管理操作遵循基于角色的访问控制（RBAC），审计日志不可篡改。

### 2.4 功能审计三原则

每新增一个管理后台功能前，必须通过以下三项检查：

| 原则 | 检查问题 | 判定 |
| :--- | :--- | :--- |
| 频率检查 | 这个操作一个月会做超过一次吗？ | 不会 → 不需要管理后台页面，走配置文件或初始化脚本 |
| 角色检查 | 法院IT有这个专业能力操作吗？ | 不会（如"编辑Prompt"） → 不需要暴露给他 |
| 合规检查 | 不做这个，会被纪检/等保/合规卡住吗？ | 会 → 必须做 |

# 四、功能模块详情

## 4.1 控制台

**页面路径**：`pages/admin/dashboard.html`

### 4.1.1 功能概述

展示系统核心数据概览，提供快捷操作入口和系统通知。

### 4.1.2 核心指标卡片

| 指标 | 说明 | 数据来源埋点 | 变化趋势 |
| :--- | :--- | :--- | :--- |
| 今日AI任务数 | 今日所有智能体任务总数 | agent_{module}.task.start (COUNT WHERE date=today) | 较上期 ↑12% |
| 文书生成采纳率 | AI输出被法官直接采用的比例 | agent_doc.step2.requirement_confirm (AVG adoption_rate) | 较上期 ↑3% |

### 4.5.8 案由状态管理（上线/下线）

**功能描述**：每个案由节点支持"上线/下线"状态切换，控制该案由在前端是否可见可用。

**状态定义**：

| 状态 | 说明 | 前端可见性 |
| :--- | :--- | :--- |
| 已上线 | 案由已发布，可供前端用户选择使用 | 可见、可选 |
| 未上线 | 案由未发布或已下线，仅管理后台可见 | 不可见、不可选 |

**操作规则**：

- **上线操作**：点击"上线"按钮，案由状态切换为"已上线"，前端即时生效
- **下线操作**：点击"下线"按钮，需二次确认弹窗提示："下线后，前端用户将无法看到和选择该案由，已关联该案由的案件在前端也将不可见，确认下线？"，确认后状态切换为"未上线"
- **批量操作**：支持对一级/二级案由批量上线/下线，操作时联动其下所有子案由状态同步变更
- **默认状态**：新建案由默认为"未上线"状态，需管理员手动上线后才对前端可见

**数据结构**：

案由数据中每个节点增加 `status` 字段：

```json
{
  "name": "买卖合同纠纷",
  "status": "online",
  "children": []
}
```

- `status` 取值：`"online"`（已上线）/ `"offline"`（未上线，默认）
- 上线/下线操作时同步更新 `adminCauseData` 和 `causeData`

**数据流向**：

```
管理后台（案由管理页面）
  ├── 新增/编辑案由 → 写入 adminCauseData（含status字段）
  ├── 上线/下线操作 → 更新 adminCauseData 中对应节点status
  └── 同步写入 causeData → 前端页面读取
        ├── Chat页面案由选择器 → 仅加载 status=online 的案由
        ├── 案件页面案由筛选器 → 仅加载 status=online 的案由
        └── 首页案由推荐 → 仅展示 status=online 的案由
```

### 4.5.9 边界场景与异常数据处理

**场景1：下线案由下的案件在前端的可见性**

| 场景 | 规则 | 说明 |
| :--- | :--- | :--- |
| 案由下线后，该案由下的已有案件 | 前端不可见、不可搜 | 案件列表和搜索结果均需过滤掉关联案由为"未上线"的案件 |
| 案由下线后，用户搜索案件关键词命中下线案由的案件 | 不返回结果 | 搜索时需校验案件关联案由的上线状态 |
| 案由重新上线后，之前的案件 | 自动恢复可见 | 无需手动操作，案件随案由上线自动恢复展示 |
| 案由下线后，案件详情页的直接访问 | 提示"该案件关联案由已下线" | 防止通过URL直接访问 |

**场景2：数据一致性保障**

| 异常情况 | 处理策略 |
| :--- | :--- |
| 案件的案由字段为空 | 前端不展示该案件，管理后台标记为"案由缺失"待处理 |
| 案件的案由在案由树中不存在（被删除） | 前端不展示该案件，管理后台标记为"案由异常"待处理 |
| localStorage数据被清空 | 前端使用内置默认案由数据兜底，管理后台提示"数据异常，请重新配置" |
| causeData与adminCauseData不同步 | 以adminCauseData为准，管理后台保存时强制同步写入causeData |

**场景3：层级联动规则**

- 一级案由下线 → 其下所有二级、三级案由自动下线（前端均不可见）
- 二级案由下线 → 其下所有三级案由自动下线
- 一级案由上线 → 不自动上线子案由，需逐个手动上线

## 4.9 模型配置与用量管理

**页面路径**：`pages/admin/model-management.html`

> V1.18 重构：本模块由原"多租户 SaaS 计费管控"重构为"多法院私有化部署配置中心"。详见 4.9.1。

### 4.9.1 功能概述

**核心定位**：面向法院私有化部署场景的模型配置中心。系统以中院为单位部署一套，下辖基层法院接入；每个法院独立维护本院实际部署的模型清单、独立总配额，并支持院内部门/用户的精细化用量管控。

**核心能力**：

1. **模型部署清单管理**：每个法院配置本院实际部署的模型（API 地址、Key、参数等），支持集中采购（基层引用上级已部署模型）与各自采购（独立新增）两种模式
2. **场景模型配置**：为各业务场景（对话、文书生成、法条校验等）分别配置默认模型，支持运行时覆盖
3. **配额与用量管控**：法院总额 + 部门/用户分配两级配额，使用率监控告警 + 超限硬管控停服

**与原 PRD 的关键差异**：

| 维度 | 原 PRD（V1.17 及之前） | V1.18 新方案 |
| :--- | :--- | :--- |
| 部署形态 | 未明确，隐含多租户 SaaS | 中院一套系统，基层法院接入 |
| 模型清单 | 全局维护模型池 + 法院授权使用 | 每法院独立维护本院部署清单 |
| 模型表单 | 重（思考模式 + 动态键值对 + 超参组 + 模板分组） | 中等（必填+常用参数，思考模式归入高级配置折叠区） |
| 配额层级 | 仅法院总额 | 法院总额 + 部门/用户分配两级 |
| 基层配额 | 从中院总额扣减（层级关联） | 独立设置（各自预算） |
| Tab 结构 | 4 个 Tab（模型列表/法院授权/Token阈值/对话模块模型） | 3 个 Tab（模型部署清单/场景模型配置/配额与用量） |

### 4.9.2 部署架构与法院层级

**部署形态**：

```

├── 中院本院（模型清单A、独立总配额A、部门A1/A2...）

├── 基层法院2（模型清单C、独立总配额C、部门C1/C2...）
└── ...
```

**权限边界**：

| 管理员角色 | 可管理的法院范围 | 可操作的内容 |
| :--- | :--- | :--- |
| 中院超级管理员/系统管理员 | 所有法院（中院+基层） | 全部法院的模型清单、场景配置、配额、用量 |
| 基层法院管理员 | 仅本院 | 本院的模型清单、场景配置、本院配额、本院用量 |

**集中采购与各自采购**：

**配置规则**：

- 每个场景从该法院已部署且启用的模型中选择默认模型

- "运行时可覆盖"为 ✅ 的场景：用户在用户侧界面可手动切换其他已启用模型（如对话窗口下拉）
- "运行时可覆盖"为 ❌ 的场景：后台自动调用，固定使用默认模型，用户不可切换

## 4.10 要件管理

**页面路径**：`pages/admin/element-presets.html`

### 4.10.1 功能概述

维护各业务系统下、按案由分组的标准要件库。标准要件用于文书生成时作为「要件引导」的上下文，与用户侧「我的要件」分层并存：管理员维护的标准要件对所有用户可见，普通办案人员维护的「我的要件」仅对本人可见，文书生成时两者合并展示并分别加「标准」「我的」标识。

按功能审计三原则：要件库维护属于业务数据维护（业务管理员职责），随新案由/新业务调整，符合频率检查；法院IT可操作（选择案由→填写要件名/说明/问题），符合角色检查；不涉及合规强制要求。

### 4.10.2 数据结构

```js
// localStorage.adminElementPresets 结构（按业务系统 × 案由分组）
{
    court: {
        '民间借贷纠纷': [
            { name: '借款合意', desc: '借贷双方是否存在借款协议或借条', question: '借款协议/借条签订时间、地点、金额分别是？', enabled: true },
            { name: '款项交付', desc: '出借人实际支付借款的凭证', question: '实际出借金额及支付方式？', enabled: true }
        ],
        '离婚纠纷': [ ... ]
    },
    procuratorate: { ... },
    justice: { ... }
}
```

**覆盖语义**：`adminElementPresets[org][cause]` 一旦存在，**整体覆盖** `elementPresetsByCause[cause]` 内置要件数组（不做字段级合并）。删除某案由的自定义配置即恢复内置。

**v1.14 启用/停用状态**：每条要件新增 `enabled` 字段（boolean，默认 `true`）。停用后的要件在用户侧文书生成时**不展示**，但管理后台仍可见并标记「已停用」状态徽章。内置要件通过 `adminElementPresets[org][cause]` 数组中的 `enabled: false` 标记停用（即停用内置要件会自动生成自定义覆盖数组）。

### 4.10.3 页面结构

页面采用「左侧案由树 + 右侧要件表格」双栏布局。

```
[管理后台 - 要件管理页面]
    │
    ├─ 顶部：页面标题 + 描述 + 业务系统切换按钮组（法院/检察院/司法局，默认法院）
    │
    ├─ 左侧：案由树（3 级结构，与新增案件案由选择器一致，来自 causeTreeDataByOrg）
    │       ├─ 顶部搜索框：输入关键词实时过滤叶子案由，匹配项的父级自动展开；无匹配显示「无匹配案由」
    │       ├─ 置顶分组：常用案由可置顶，集中显示在树顶部「置顶」分组下（按业务系统分组存储 localStorage.adminPinnedCauses）
    │       ├─ 「全部」项：显示当前业务系统案由总数
    │       ├─ level-1 大类（如「民事案由」）：可选中或展开/折叠
    │       ├─ level-2 中类（如「婚姻家庭纠纷」）：可选中或展开/折叠
    │       └─ 叶子案由（如「离婚纠纷」）：后缀显示该案由的要件数量；hover 显示「置顶/取消置顶」图钉按钮
    │       └─ 已自定义覆盖的案由项前显示橙色圆点标识
    │
    └─ 右侧：要件表格
            ├─ 表头：要件名 | 说明 | 问题 | 来源 | 状态 | 操作
            ├─ 每行：要件名 | 说明 | 问题 | 内置/自定义徽章 | 已启用/已停用徽章 | 编辑/停用（启用）/删除
            ├─ 顶部「新增要件」按钮（需先在左侧选中某案由）
            └─ 已自定义覆盖时显示「恢复内置」按钮
```

### 4.10.4 要件操作

**新增要件**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| 要件名 | 文本 | 是 | 失焦校验非空 |
| 要件说明 | 文本 | 否 | 简要说明该要件的含义 |
| 问题 | 文本域 | 是 | 生成文书前需确认的单一问题 |

**编辑要件**：
- 自定义要件：直接编辑原条目
- 内置要件：编辑后将整条另存为自定义覆盖（弹窗标题为「编辑内置要件（另存为自定义）」），写入 `adminElementPresets[org][cause]`

**删除要件**：
- 自定义要件：二次确认后从 `adminElementPresets[org][cause]` 移除
- 内置要件：删除按钮置灰，不可直接删除；如需删除请先「恢复内置」后重新维护

**启用/停用要件**（v1.14 新增）：
- 每条要件右侧操作区新增「停用」/「启用」按钮
- 停用后该要件在用户侧文书生成时不展示
- 自定义要件：直接修改 `enabled` 字段
- 内置要件：首次停用时自动生成自定义覆盖数组（保留所有内置要件，仅修改目标项的 `enabled` 为 `false`）
- 重新启用：将 `enabled` 改回 `true`，**保留自定义覆盖**（不自动恢复内置，避免丢失其他编辑）

**恢复内置**：
- 仅当该案由已自定义覆盖时显示
- 二次确认后清除 `adminElementPresets[org][cause]` 整个 key，还原为系统内置要件

### 4.10.5 数据持久化

- 存储 Key：`localStorage.adminElementPresets`（按业务系统 × 案由分组）
- 置顶列表 Key：`localStorage.adminPinnedCauses`（按业务系统分组）
- 内置兜底数据：`case-data.js` 的 `elementPresetsByCause` 常量；案由不在内置表中时回退到通用要件（主体资格/事实认定/法律适用/程序合法/处理结果）

### 4.10.6 用户侧联动

`case-data.js` 的 `getElementPresets(cause, org)` 读取优先级：

1. 若 `adminElementPresets[org][cause]` 存在 → 返回该自定义数组
2. 否则若 `elementPresetsByCause[cause]` 存在 → 返回内置
3. 否则返回通用要件兜底

`getAllElementPresets(cause, org)` 透传 org，在标准要件基础上合并用户侧「我的要件」。调用方（`cases.js`、`case-files.js`）从 `localStorage.getItem('currentBusiness') || 'court'` 取 org 后传入。

## 4.11 文书类型管理

### 4.11.1 功能概述

维护各业务系统下文书类型的分类容器，作为文书模板管理、提示词管理、我的模板/我的提示词四个模块的统一父级分类。类型属性极简（仅名称），运行期偶尔增删。同时承担 workflow 子配置的承载（见 4.11.7）。

### 4.11.2 数据结构

```js

{

```

**覆盖语义**：`adminDocTypes[org][typeKey]` 一旦存在，**整体覆盖** `defaultDocTypesByOrg[org][typeKey]` 的内置配置。内置类型 key 不可重复新增；编辑内置类型时保留原 key，标记 `isBuiltin: false` 后写入自定义覆盖。

**v1.14 启用/停用状态**：每个文书类型新增 `enabled` 字段（boolean，默认 `true`）。停用后的文书类型在用户侧**不出现在文书类型下拉**，但管理后台仍可见并标记「已停用」状态徽章。内置类型通过 `adminDocTypes[org][typeKey]` 中的 `enabled: false` 标记停用（停用内置类型会自动生成自定义覆盖对象）。

**关于 `templates` 字段退役**：自定义类型**不带** `templates` 数组（该字段已退役，模板归属完全由模板自身的 `docType` 字段决定）。内置类型的 `templates` 数组保留在常量中仅作历史快照，运行时不再读取。

**关于 `icon` 字段退役**（v1.8）：文书类型与 workflow 步骤均不再配置 `icon` 字段；`icon` 字段从数据结构中移除。历史数据中的 `icon` 字段保留但运行时不再读取（用户侧文书类型下拉为 `<option>` 不渲染图标；分步生成步骤标题仅展示编号与标题文本）。

### 4.11.7 workflow 子配置（内联于文书类型管理页）

**功能描述**：workflow 是系统内部配置，**对用户完全不可见**。其本质是「节点流程」配置容器，按「业务系统 × 文书类型」分组，包含两种类型：
- **一步生成型**（type='material'）：无人工交互节点，输入参数（材料 + 模板 + 提示词）后直接输出文书结果，用于一步生成 tab
- **分步生成型**（type='step'）：含人工交互节点，用户在分步生成 tab 中按节点逐个确认材料与内容，最终编译为完整文书

> v1.9 命名调整：原「展示型 / 不展示型」改为「分步生成型 / 直接生成型」，内部 type 值仍沿用 'step' / 'material'，保持向后兼容。
> v1.10 命名调整：「直接生成型」改为「一步生成型」，与用户侧 tab 命名「一步生成」对齐；内部 type 值仍为 'material'，函数名/字段名不变。

> v1.11 单 workflow 架构原则（核心设计决策）：
> 1. **一个文书类型对应一个完整闭环 workflow**：从输入到输出是一个闭环，不再支持「一步骤一 workflow」的拆分方式
> 2. **一步生成型与分步生成型本质是同一个 workflow**：区别仅在是否含人工交互节点；材料生成本身也有步骤，只是不需要人工介入
> 3. **不采用多 workflow 拆分的原因**：① 多 workflow 之间步骤存在数据依赖（后步依赖前步输出），拆分后无法跨 workflow 传递；② 编排人员同时管理多个分散 workflow 易混乱；③ 接入适配工作量大、后期扩展麻烦
> 4. **单 workflow 支持指定节点重新生成**：业务侧记录当前卡在哪个节点（或完整生成完后从某节点重新生成），由 agentflow 平台加功能支持；当前原型未实现，PRD 登记
> 5. **「生成文书」作为 workflow 内的最终节点**：不再单独拆为独立 workflow；若该节点渲染慢（约 1-2 分钟），由前端流式输出/思考过程样式缓解体验问题

> v1.11 步骤名数据来源说明：分步生成 tab 中每个步骤的「名称」直接取自 workflow 编排时人工交互节点的**面板名**（如编排时命名为「案件信息」「原告诉请」，前端原样展示）。管理后台不再配置/存储步骤名，前端也不再单独维护步骤序列；用户点击【开始生成】后，前端通过 workflow id 发起执行，SSE 事件流依次返回每个人工交互节点的事件，前端按事件动态渲染步骤列表。原型阶段以 `stepConfigsByOrg` 内置 mock 充当步骤序列，正式接入时由 SSE 事件流动态返回。

workflow **不绑定生成策略**：案件列表页由 token 自动决定模式；案件详情页用户选 tab；走「分步生成」时按案字+案由匹配分步生成型 workflow；走「一步生成」时按案字+案由匹配一步生成型 workflow（仅用于流程选择，不暴露给用户）。

**关键变更（v1.9）**：
1. **workflow id 改为下拉框**：数据来源于 agentflow 平台已编排的 workflow 列表，管理后台仅做选择绑定，不再手动填写
2. **移除步骤序列编辑器**：分步生成型 workflow 的节点序列由 agentflow 平台 workflow 内部决定，管理后台不再配置 steps 字段
3. **新增「匹配案由」字段**：从当前业务系统案由树中选择适用案由（多选），与「匹配案字」配合做精细化匹配

**配置入口**：不单独开模块、不增加菜单项。在文书类型管理页表格中，每个类型行新增「展开/折叠」按钮（行首 `fa-chevron-right` / `fa-chevron-down`）。点击展开后，在类型行下方显示该类型下的 workflow 子表格，区域标题为「{类型名} 的 workflow」+「新增 workflow」按钮。

**workflow 数据结构**：

```js
// localStorage.adminWorkflows 结构（按业务系统分组）
{
    court: {
        judgment: [
            {
                id: 'wf-judgment-1st',           // workflow 唯一 id（来自 agentflow 平台下拉选择，同一 docType 内唯一）
                name: '一审民事判决',             // workflow 显示名（仅后台可见，随 id 自动带出）
                type: 'step',                     // workflow 类型：'step'=分步生成型 | 'material'=一步生成型
                caseWords: ['民初', '民再'],      // 匹配的案字（多选，空数组 = 兜底）
                causes: ['离婚纠纷', '合同纠纷'], // 匹配的案由（多选，空数组 = 兜底，v1.9 新增）
                modelId: 'qwen3.6',              // 使用模型（v1.15 新增）：agentflow 平台 workflow 内部大模型节点的镜像映射，供前端 token 估算
                isBuiltin: true                   // 是否内置（迁移自 stepConfigsByOrg）
                // v1.9: 移除 steps 字段——节点序列由 agentflow 平台 workflow 内部决定
            },
            {
                id: 'wf-judgment-material-default',
                name: '裁判文书-一步生成',
                type: 'material',                 // 一步生成型：无人工交互节点
                caseWords: [],
                causes: [],
                modelId: 'qwen3.6',
                isBuiltin: true
            },
            ...
        ],
        trial: [ ... ]
    },
    ...
}
```

**agentflow 平台 workflow 列表（mock 数据）**：管理后台无法直接调用 agentflow 平台接口，原型中以 `case-data.js` 内置 mock 列表 `agentflowWorkflowList` 模拟返回值。正式接入时替换为真实接口调用。

**覆盖语义**：`adminWorkflows[org][docTypeKey]` 一旦存在，**整体覆盖**内置 workflow 数组。删除某类型的全部自定义 workflow 即恢复内置。

**内置数据迁移**：系统首次加载时，若 `adminWorkflows` 为空，`getWorkflowsForDocType` 会为每个 docType 生成两个内置 workflow：
- 一个分步生成型（`type: 'step'`，`caseWords: []`，`causes: []`，`isBuiltin: true`）
- 一个一步生成型（`type: 'material'`，`caseWords: []`，`causes: []`，`isBuiltin: true`）

**type 字段兼容**：旧数据中 workflow 无 `type` 字段时，按 `type: 'step'` 处理；旧数据中的 `steps` 字段保留但运行时不再读取（v1.9 移除步骤编辑器后，steps 由 agentflow 平台内部维护）。

**workflow 子表格结构**：

```
[文书类型行展开后]
    │
    └─ workflow 子表格
        ├─ 表头：workflow 名称 | 类型 | 使用模型 | 匹配案字 | 匹配案由 | 来源 | 操作
        ├─ 每行：名称 | 类型徽章（分步生成型/一步生成型）| 模型名（如「千问 3.6」）| 案字标签组（或「兜底」）| 案由标签组（或「兜底」）| 内置/自定义 | 编辑/删除
        └─ 顶部「新增 workflow」按钮
```

> 类型徽章样式：分步生成型 = 蓝色，一步生成型 = 紫色。

**新增/编辑 workflow**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| workflow id | 下拉框（单选） | 是 | 从 agentflow 平台已编排的 workflow 列表中选择；选项显示 `id - name`；选中后自动带出 name；编辑内置 workflow 时只读 |
| workflow 名称 | 文本（只读） | 是 | 随 workflow id 选择自动带出，不可手动编辑 |
| workflow 类型 | radio（一步生成型 / 分步生成型） | 是 | 默认分步生成型；类型决定用户侧在哪个 tab 触发该 workflow |
| 使用模型 | 下拉框（单选） | 是 | 从 `AI_MODELS` 中 `deployed=true` 的已部署模型选择（千问 3.6 / DeepSeek v4）；作为 agentflow 平台 workflow 内部大模型节点的镜像映射，供前端 token 估算（v1.15 新增） |
| 匹配案字 | 多选 checkbox | 否 | 从当前业务系统 `caseWordListByOrg` 取；不选任何案字 = 案字兜底 |
| 匹配案由 | 多选 checkbox（案由树） | 否 | 从当前业务系统案由树取（3 级）；不选任何案由 = 案由兜底（v1.9 新增） |

**workflow id 校验**：同一 docType 下 id 不可重复（保存时校验）；下拉框选项过滤掉当前 docType 下已被其他 workflow 占用的 id。编辑内置 workflow 时下拉框只读，原 id 保留以确保用户侧引用稳定。

**匹配规则优先级**（运行时由 case-data.js 执行）：
1. 案字 + 案由 双精确匹配
2. 案字精确 + 案由兜底（causes=[]）
3. 案字兜底（caseWords=[]）+ 案由精确
4. 案字兜底 + 案由兜底（全兜底）
5. 第一个同类型 workflow

**案字/案由冲突校验**：同一 docType 下，同一「案字 + 案由」组合不可在多个**同类型** workflow 间重复（保存时校验）。已被同类型其他 workflow 匹配的案字/案由在选项后显示 ⚠ 提示。

**删除 workflow**：
- 内置 workflow 删除 = 移除自定义覆盖（恢复内置默认）
- 自定义 workflow 删除 = 直接移除
- 若该类型下某类型（分步生成型/一步生成型）的 workflow 仅剩此一个，禁止删除并提示「每个类型至少需保留 1 个分步生成型 workflow」或「每个类型至少需保留 1 个一步生成型 workflow」

**workflow 用户侧联动（对用户不可见）**：

案件详情页用户选「分步生成」tab 时：

1. 系统从案件 `caseNumber` 中提取案字（正则匹配 `民初/民终/民再/刑初...`）
2. 从案件 `cause` 取案由名称
3. 调用 `getWorkflowsForDocType(org, docTypeKey, 'step')` 获取该类型下所有**分步生成型** workflow
4. 按上述「匹配规则优先级」匹配默认分步生成型 workflow
5. 多个分步生成型 workflow 时显示「步骤方案下拉」让用户切换，**不显示 workflow 名称**
6. 节点序列由 agentflow 平台 workflow 内部决定，前端通过 workflow id 调用执行层接口获取

案件详情页用户选「一步生成」tab 时：

1. 系统同样从案件 `caseNumber` 提取案字，从 `cause` 取案由
2. 调用 `getWorkflowsForDocType(org, docTypeKey, 'material')` 获取该类型下所有**一步生成型** workflow
3. 按匹配规则匹配默认一步生成型 workflow（用于确定使用哪一套生成流程），用户侧不感知此匹配
4. 仅 1 个一步生成型 workflow 时不显示任何切换入口

案件列表页生成文书：由 token 自动决定模式（现状不变），不涉及 workflow 选择。

## 4.12 文书模板管理

**页面路径**：`pages/admin/doc-templates.html`

### 4.12.1 功能概述

维护各业务系统的文书模板，模板与「文书类型」直接关联，**不再单独维护案由关联**（v1.12 移除）。模板作为所属文书类型的"下属"，案由匹配通过文书类型 → workflow 链路完成。用户侧生成文书时按当前所选文书类型直接展示该类型下全部模板。

### 4.12.4 模板操作

**新增/编辑模板**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| 模板名 | 文本 | 是 | 失焦校验非空 |
| 所属文书类型 | 下拉选择 | 是 | 从当前业务系统 `getAdminDocTypes` 取 |
| 模板正文 | 文件上传 | 否 | 上传本地文件确定内容（.txt/.doc/.docx），不支持在线编辑；新增/编辑弹窗提供模板示例文件下载 |

**保存规则**：
- 新增：生成唯一 key（`{docType}-` + 时间戳 base36）
- 编辑自定义：保留原 key 更新
- 编辑内置：使用内置 key 作为自定义覆盖（用户侧 `mergeAdminDocTemplates` 会覆盖），编辑时禁用文书类型切换以避免逻辑歧义
- 上传的模板正文以纯文本形式持久化到 `content` 字段，用于后续文书生成时填充占位符；未上传则正文为空

**模板正文操作**：

- **预览**：点击"预览"按钮，在新窗口展示当前保存的模板正文（保留换行与占位符格式）。
- **下载**：点击"下载"按钮，将当前保存的模板正文作为 `.txt` 文件下载到本地。
- **重新上传**：点击"重新上传"按钮，打开编辑弹窗并清空当前正文，唤起文件选择器；选择新文件后覆盖原 `content`，并提示"模板正文已更新"。
- **异常**：未上传过正文的自定义模板，预览/下载按钮置灰或提示"暂无模板正文"；内置模板有系统预置默认正文（含常见占位符格式），支持预览和下载。

**删除模板**：
- 自定义模板：二次确认后删除
- 内置模板：不可删除（按钮不显示）

### 4.12.5 数据持久化

- 存储 Key：`localStorage.adminDocTemplates`（按业务系统分组）
- 内置兜底数据：`case-data.js` 的 `defaultDocTemplatesByOrg` 常量（字符串映射）
- 合并函数：`mergeAdminDocTemplates(org, system)` 在加载时将自定义模板合并到 `system.docTemplates`，覆盖同名内置 key

### 4.12.6 用户侧联动

`cases.js` 选文书类型后，模板下拉直接按所属文书类型展示，**不再按 cause 过滤**（v1.12 移除）。`getFilteredDocTypeTemplates(docTypeKey)` 等价于 `getDocTypeTemplates(docTypeKey)`，保留函数签名以减少调用方变更。模板与案由的关联通过文书类型 → workflow 链路间接实现：文书类型在 workflow 配置中匹配案字+案由决定使用哪一套 workflow，模板直接挂在文书类型下随类型联动。

## 4.13 提示词管理

**页面路径**：`pages/admin/prompt-templates.html`

### 4.13.1 功能概述

维护「提示词」的内置提示词模板，按业务系统 × 文书类型分组。用户侧生成文书时，提示词以标签形式展示，点击标签将提示词正文填入提示词输入框。支持历史版本记录与单条恢复（v1.14）。

按功能审计三原则：提示词维护属于业务数据维护，符合频率检查；法院IT可操作（选类型、填标签、填正文），符合角色检查；不涉及合规强制要求。

> **与 V1.3 移除的「角色与提示词管理」的区别**：V1.3 移除的是面向「角色」的 Prompt 配置（AI 系统级提示词，属于产品核心逻辑，由产品团队通过配置文件设定）。本节管理的是面向「文书类型」的「提示词」快捷标签（用户侧可见可点的辅助输入项），属于业务数据维护范畴。

> **v1.14 移除全局「恢复默认」按钮**：原顶部「恢复默认」按钮过于粗暴（一次性丢失整个业务系统的所有自定义），改为**单条历史版本回滚**机制——每条提示词独立维护历史版本，可单独恢复至任一历史版本。

### 4.13.2 数据结构

```js
// localStorage.adminPromptTemplates 结构（同 defaultRequirementTemplates）
{
    court: {
        judgment: [
            { name: '支持原告全部诉请', text: '裁判方向：支持原告全部诉讼请求\n• 事实清楚...', enabled: true, history: [
                { savedAt: 1690000000000, name: '支持原告全部诉请', text: '旧版本正文...' }
            ] }
        ],
        trial: [ ... ]
    },
    procuratorate: { ... },
    justice: { ... }
}

// localStorage.myPromptTemplates 结构（用户侧）
// v1.14 同步新增 history 字段，结构同上
```

**覆盖语义**：`adminPromptTemplates[org][docTypeKey]` 数组一旦存在且非空，**整体覆盖** `defaultRequirementTemplates[org][docTypeKey]` 的内置数组。

**v1.14 历史版本字段**：每条提示词新增 `history` 数组，保存最近 5-10 条编辑快照。每次保存（编辑模式下）时自动将**编辑前的内容**追加到 `history` 数组头部，超出 10 条时丢弃尾部最旧记录。新增模式下不写 history。

### 4.13.3 页面结构

页面采用「左侧文书类型列表 + 右侧提示词列表」双栏布局。

```
[管理后台 - 提示词管理页面]
    │
    ├─ 顶部：页面标题 + 描述 + 业务系统切换按钮组（v1.14 移除「恢复默认」按钮）
    │
    ├─ 左侧：文书类型列表（点击筛选右侧提示词）
    │       ├─ 全部（默认选中，显示提示词总数）
    │       └─ 当前业务系统的文书类型项（每项后缀显示该类型下提示词数）
    │
    └─ 右侧：提示词列表
            ├─ 全部视图下按文书类型分组，显示类型分组标题
            ├─ 每项：来源徽章 | 正文预览（超 80 字截断折叠）| 标签名 | 编辑/历史/启用/删除
            └─ 顶部「新增提示词」按钮
```

### 4.13.4 提示词操作

**新增/编辑提示词**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| 所属文书类型 | 下拉选择 | 是 | 从当前业务系统 `getAdminDocTypes` 取 |
| 标签名 | 文本 | 是 | 失焦校验非空 |
| 提示词正文 | 文本域 | 是 | 支持 `\n` 换行；正文为空时需二次确认（用户点击该标签会清空提示词输入框） |

**保存规则**：
- 新增：追加到 `adminPromptTemplates[org][docType]` 数组
- 编辑自定义（同文书类型）：原地更新对应下标
- 编辑自定义（跨文书类型）：先从原数组移除，再追加到新数组
- 编辑内置：把内置数据全部拷贝为自定义数组，再修改对应项（弹窗标题为「编辑内置提示词（另存为自定义）」），编辑时禁用文书类型切换

**删除提示词**：
- 自定义提示词：二次确认后从数组移除；数组清空时删除整个 docType key（恢复内置）
- 内置提示词：不可删除

### 4.13.5 历史版本记录（v1.14 新增）

**机制说明**：
- 每条提示词（含自定义与被覆盖的内置）独立维护一个 `history` 数组，保存最近 5-10 条编辑快照
- 每次保存编辑时，**编辑前的内容**自动入栈（追加到 `history` 头部，超出 10 条时丢弃最旧）
- 历史版本弹窗中展示：版本时间、标签名、正文预览（点击展开完整正文）
- 一键恢复：选中某历史版本 → 二次确认 → 用历史版本内容**覆盖当前内容**，同时把当前内容也入栈 history

**入口位置**：
- 每条提示词右侧操作区新增「历史」按钮（带 `fa-history` 图标）
- 历史版本数为 0 时按钮置灰（无历史可恢复）

**与原「恢复默认」的差异**：

| 维度 | 原「恢复默认」按钮（v1.13） | v1.14 历史版本回滚 |
| :--- | :--- | :--- |
| 粒度 | 整个业务系统 | 单条提示词 |
| 数据来源 | 系统内置默认值 | 该条提示词自身的历史快照 |
| 误操作风险 | 高（一次性丢失全部自定义） | 低（仅影响单条，可再次回滚） |
| 入口位置 | 顶部全局按钮 | 提示词旁的「历史」按钮 |

### 4.13.6 数据持久化

- 存储 Key：`localStorage.adminPromptTemplates`（按业务系统 × 文书类型分组）
- 历史版本 Key：内联于每条提示词的 `history` 字段（不单独存储）
- 内置兜底数据：`case-data.js` 的 `defaultRequirementTemplates` 常量
- 读取函数：`getReqTemplates(org, docTypeKey)` 优先读 admin 自定义，为空回退到内置默认
- 用户侧 `localStorage.myPromptTemplates` 同步新增 `history` 字段，结构相同

### 4.13.7 用户侧联动

- `cases.js` 的 `renderReqTemplates` 优先读 `localStorage.adminPromptTemplates`，为空则回退到 `defaultRequirementTemplates` 内置默认值
- `case-files.js` 的 `renderMatReqTemplates` 同步适配
- 用户侧「我的提示词」数据（`localStorage.myPromptTemplates`）在 admin 数据之后追加，标记 `source: 'mine'`，标签加绿色 `.mine` 样式标识

**数据合并优先级（高 → 低）**：

1. 用户侧自定义（`my-` 前缀 / `.mine` 标签）
2. 管理后台自定义（覆盖同名内置）
3. 系统内置默认值（`defaultRequirementTemplates`）

# 五、权限设计

> v1.13 更新：基于 2026/7/27 录音讨论，角色体系由原「超级管理员/系统管理员/业务管理员/普通用户」四档调整为**内置三档**「超级管理员/法院管理员/普通用户」；新增登录入口拆分（业务端+管理端）、法院与部门组织架构管理两节。

## 5.1 角色定义

系统内置三类角色，采用固定逻辑实现，暂不支持自定义角色配置：

| 角色 | 标识 | 权限范围 | 数据范围 |
| :--- | :--- | :--- | :--- |
| 超级管理员 | super_admin | 系统级配置（案由、文书类型、workflow、模板、提示词、要件、模型、系统初始化）+ 全法院数据统一管理 + 法院树维护 + 全部法院用户管理 | 全部法院 |
| 法院管理员 | court_admin | 本法院用户管理 + 本法院部门维护 + 本法院统计数据查看；**无**系统级配置权限 | 仅本法院 |
| 普通用户 | user | 无后台访问权限，仅使用业务端功能 | - |

### 5.1.1 超级管理员职责

- 维护系统级通用配置：案由管理、文书类型管理、文书模板管理、提示词管理、要件管理、模型配置与用量、系统初始化配置（系统名称/Logo）
- 维护法院组织架构树：创建/编辑/停用法院节点（基层/中级/高级），为每个法院分配法院管理员账号
- 统一管理所有法院的用户（跨法院查看、增删改）
- 查看全部法院的统计数据与系统运行报告
- 查看风控与审计日志

### 5.1.2 法院管理员职责

- 仅管理**本法院**用户：增删改本法院用户、为本法院用户分配部门
- 维护**本法院**部门组织：创建/编辑/删除部门（部门仅作人员重名识别标签，不做数据权限划分）
- 查看**本法院**统计数据与系统运行报告
- **不可见**菜单：案由管理、文书类型管理、文书模板管理、提示词管理、要件管理、模型配置、系统初始化配置、风控与审计、法院维护

### 5.1.3 普通用户职责

- 无管理后台访问权限
- 通过业务端（lite）使用案件办理、文书生成等功能

## 5.3 登录入口与前端拆分

### 5.3.1 终态架构（独立部署）

生产部署采用**两个独立前端**，不同端口，共用同一套用户体系：

| 前端 | 端口 | 入口用户 | 主要功能 |
| :--- | :--- | :--- | :--- |
| 业务端（lite） | 端口 A | 普通用户 | 案件办理、文书生成、知识问答、任务管理 |
| 管理端（admin） | 端口 B | 超级管理员、法院管理员 | 系统配置、用户管理、组织架构、数据统计 |

- 用户账号统一存储，登录时按角色路由至对应前端
- 普通用户账号尝试登录管理端时拒绝并提示
- 管理员账号尝试登录业务端时拒绝并提示

### 5.3.2 原型阶段方案（单前端 + 路由区分）

原型阶段保留单前端入口，通过登录类型切换 + 路由区分模拟双前端：

1. **登录页**（pages/login.html）提供两个登录入口标签：
   - 「普通用户」标签：登录后跳转 `pages/chat.html`（业务端首页）
   - 「管理员」标签：登录后跳转 `pages/admin/dashboard.html`（管理端首页）
2. **管理员角色选择器**：切换至「管理员」标签时显示角色选择器（超级管理员 / 法院管理员），登录后角色写入 localStorage
3. **菜单动态隐藏**：管理后台每个页面读取 `adminRolePages`，不在权限列表中的菜单项 `display:none`
4. **数据范围隔离**（原型 mock）：登录时记录当前法院 ID，法院管理员视角的用户管理/案件管理/统计仅展示当前法院数据

## 5.4 法院与部门组织架构管理

### 5.4.1 功能概述

管理法院上下级树与部门组织，支撑用户管理的数据范围隔离与人员归属识别。

- **法院维护**（超管）：维护法院上下级树，为法院分配法院管理员
- **部门维护**（法院管理员）：维护本法院部门，作为用户重名识别标签
- **用户管理联动**：用户管理页面按法院+部门筛选，用户归属法院和部门

### 5.4.2 法院树结构

法院有上下级层级（基层/中级/高级），但**权限平级独立**（上级法院不能管理下级法院的用户与数据）。

```javascript
// 法院树数据结构（localStorage: adminCourtTree）
[
  {
    id: 'court_h',
    name: '某省高级人民法院',
    level: '高级',
    parentId: null,
    adminUserId: 'u_admin_h',  // 分配的法院管理员账号
    status: 'active'
  },
  {
    id: 'court_m1',
    name: '某市中级人民法院',
    level: '中级',
    parentId: 'court_h',
    adminUserId: 'u_admin_m1',
    status: 'active'
  },
  {
    id: 'court_b1',
    name: '某区基层人民法院',
    level: '基层',
    parentId: 'court_m1',
    adminUserId: 'u_admin_b1',
    status: 'active'
  }
]
```

### 5.4.3 部门结构

部门仅作人员重名识别标签，**不做数据权限划分**。同一法院下部门名称唯一。

```javascript
// 部门数据结构（localStorage: adminDepartments）
[
  {
    id: 'dept_001',
    name: '立案庭',
    courtId: 'court_b1',  // 所属法院
    status: 'active'
  },
  {
    id: 'dept_002',
    name: '刑事审判庭',
    courtId: 'court_b1',
    status: 'active'
  }
]
```

### 5.4.4 法院维护页面（pages/admin/court-tree.html）

**入口**：超管登录后可见，位于侧边栏「组织架构」分组下「法院维护」

**功能**：
- 树形展示法院上下级结构（可展开/折叠）
- 新增法院节点：选择上级法院、填写法院名称、选择层级（基层/中级/高级）、分配法院管理员账号
- 编辑法院节点：修改名称、层级、管理员账号
- 停用/启用法院节点
- **删除限制**：法院节点下有用户时不可删除

**法院管理员视角**：不可见此菜单

### 5.4.5 部门维护页面（pages/admin/department.html）

**入口**：法院管理员登录后可见，位于侧边栏「组织架构」分组下「部门维护」；超管登录后也可见（可维护任意法院部门）

**功能**：
- 顶部法院选择器：超管可切换法院；法院管理员固定为当前法院（不可切换）
- 部门列表：展示当前法院下所有部门
- 新增部门：填写部门名称（同法院下唯一）
- 编辑/删除部门：删除时校验部门下是否有用户

### 5.4.6 用户管理页面联动调整

**pages/admin/users.html 调整**：
- 用户数据结构新增 `courtId`（所属法院）、`deptId`（所属部门）字段
- 筛选栏新增「法院」筛选器（超管可切换法院，法院管理员固定当前法院）
- 「部门」筛选器选项按当前所选法院动态加载
- 用户列表/编辑弹窗新增「所属法院」「所属部门」字段
- 法院管理员视角：仅展示本法院用户，不可切换法院筛选器
