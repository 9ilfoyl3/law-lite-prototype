# 二、调整背景与目标

## 2.1 背景

V1.1 现行交互中，"要件答案的日常维护"与"生成文书时的答案确认"是两套割裂的交互：

| 场景 | 现行载体 | 能力 |
| :--- | :--- | :--- |
| 日常维护（材料树「本案要件」入口） | 本案要件抽屉 | 逐条答案展示/编辑、单条重新生成、内容优化（3 轮上限）、优化记录回填、勾选框、一键生成 |
| 生成时确认·有答案（原路径 A） | 大文本框确认弹框 | 整段纯文本编辑；按钮【取消】【不引入要件】【确认生成】 |
| 生成时确认·无答案（原路径 B） | 三步弹框串联 | ① 确认是否引入 → ② 勾选要件 → ③ 大文本框（含预生成加载态） |

## 2.2 现状问题

1. **编辑体验割裂**：同一份要件答案，日常维护用抽屉、生成确认用大文本框，用户需重复学习两套交互
2. **能力不对等**：抽屉具备的单条重新生成、内容优化、优化记录回填在生成确认时不可用；大文本框只能整段手改
3. **脆弱的文本解析**：大文本框确认后需用正则将纯文本按 `【要件名】问题：…答案：…` 拆回结构化数据，用户改动格式后解析易失败
4. **路径 B 链路长**：三连弹框，操作成本高

## 2.3 调整目标

1. 生成确认与日常维护统一复用「本案要件」抽屉，一套交互
2. 要件上下文以结构化数据传递给 workflow，消除纯文本拼接 + 正则解析链路
3. 原路径 B 由"三步弹框"缩短为"轻量询问 + 抽屉"
4. 抽屉内编辑的答案实时持久化，生成前修改的内容留档，日常模式同样可复用

# 四、调整后交互方案（TO-BE）

## 4.1 整体流程

```
点「生成文书」（一步生成 / 分步生成最终按钮）
        │
        ├─ 非判决书 或 无可用要件 ──────────→ 直接开始流式生成
        │
        └─ 判决书 且 有可用要件
                │
        轻量询问弹框（复用现有 preElementConfirmModal）
        「检测到 N 个可用要件…是否引入」
                │
        ┌───────┴──────────────┐
  【引入案由要件】        【直接生成】 / X 关闭
        │                      │
        │               直接生成 / 中止回到配置区
        ▼
   本案要件抽屉 · 生成模式（默认全选）
        │
        ├─ 有答案：直接展示，可编辑 / 单条重新生成 / 内容优化
        ├─ 无答案：手动点「一键生成」预生成（含加载态），再编辑
        │
   底部【确认生成（引入 N 条要件）】
        │
        ├─ N ≥ 1：抽屉自动关闭 → 主界面流式输出开始
        ├─ 勾选了要件但均无答案：toast「尚无答案，建议先生成」，不触发生成
        └─ 未勾选任何要件：toast「请先勾选要引入的要件」，不触发生成
```

## 4.2 轻量询问弹框（前置）

- **复用现有 `preElementConfirmModal`**：样式、文案（共 N 个可用要件（标准 X / 我的 Y / 个案 Z）、引入价值说明、耗时提示）沿用现状
- **触发规则变化**：原"有答案（路径 A）不询问、直接弹大文本框"的行为**取消**；只要满足触发条件（判决书 + 有可用要件），一律先弹轻量询问弹框，有答案/无答案不再影响前置流程
- **按钮**：
  - 【引入案由要件】→ 打开本案要件抽屉（生成模式）
  - 【直接生成】→ 不引入要件，直接开始流式生成
  - X / 遮罩关闭 → 中止本次生成动作，回到配置区

## 4.3 本案要件抽屉 · 生成模式

- **唯一来源**：生成文书 → 轻量询问弹框 → 【引入案由要件】。从材料树「本案要件」入口打开为**日常模式**，底部不显示确认生成按钮，行为与现状完全一致
- **默认勾选**：每次经【引入案由要件】进入生成模式时，重置为全部可用要件勾选（不沿用上次取消勾选的状态）
- **复用抽屉现有能力**：逐条答案展示/编辑、单条【重新生成】、【内容优化】（N/3）、优化记录回填、新增个案要件、勾选统计、三色来源标签、「管理我的要件」链接
- **有答案（承接原路径 A）**：直接展示已有答案，用户可编辑后确认生成
- **无答案（承接原路径 B）**：答案区为空，由用户手动点底部「一键生成」为勾选要件批量预生成答案（含现有加载态），完成后可继续编辑；**系统不自动触发预生成**
- **底部操作条**：生成模式下新增主按钮**【确认生成（引入 N 条要件）】**（主色按钮，置于抽屉底部按钮区）；N 为"已勾选且有答案"的要件数，随勾选与答案状态实时联动刷新文案；日常模式不渲染该按钮
- **一键生成加载期间**：【确认生成】按钮禁用，加载结束恢复

## 4.4 确认生成校验规则

| 校验情形 | 行为 |
| :--- | :--- |
| N ≥ 1（存在勾选且有答案的要件） | 关闭抽屉 → 主界面立即开始流式输出；勾选但无答案的要件不纳入上下文 |
| 勾选了要件但均无答案（N = 0） | toast 提示**「尚无答案，建议先生成」**，不触发生成 |
| 未勾选任何要件 | toast 提示「请先勾选要引入的要件」，不触发生成 |

- **部分有答案 / 部分无答案**：仅引入有答案的 N 条（按钮文案中的 N 即该数量）；如需引入更多，可先「一键生成」或单条【重新生成】补齐答案后再确认

## 4.5 关闭与放弃

- 生成模式下点 X / 遮罩关闭抽屉 = **放弃本次生成**，回到配置区，不触发生成
- 抽屉内已编辑/生成的答案已实时持久化（现有机制），关闭不丢失，下次进入（含日常模式）恢复

## 4.6 生成中状态约束

- 确认生成后**抽屉自动关闭**，再开始流式输出
- 流式输出期间材料树「本案要件」入口**禁用**，hover 提示「文书生成中，暂不可修改要件」；输出结束后恢复

## 4.7 数据传递与持久化

- 引入上下文以**结构化数组**传递给生成流程（name / desc / question / answer），范围 = 勾选 ∩ 已有答案
- 废除"纯文本拼接 + 正则拆解"链路（原大文本框确认逻辑）
- 答案持久化沿用 `localStorage.caseElements_${caseId}`，存储结构不变，历史数据无需迁移

# 六、边界与异常 case

1. **无可用要件**：不弹框直接生成（不变）
2. **历史答案数据**：存储结构未变（caseElementsAnswers 按要件名索引），大文本框时代的既有答案直接可用，无需迁移
3. **流式输出中**：「本案要件」入口禁用，无法打开抽屉
4. **生成模式下新增个案要件**：新增后纳入列表与勾选统计，N 联动刷新
5. **生成模式放弃后再点「生成文书」**：重新走轻量询问弹框；再次进入抽屉时重置为默认全选
6. **一键生成加载中点【确认生成】**：按钮已禁用，无响应；加载完成后自动恢复

# 八、V1.2.1 要件抽屉交互增强

> 本章节为 V1.2.1 增量调整，对应 2026-09-07 演示评审《原型待调整清单》第 6/7/8 项。
> 原则：**不改动现有抽屉 UI 版式与组件样式**，仅调整交互逻辑与状态呈现。

## 8.1 调整背景

| # | 问题 | 现状行为 |
| :--- | :--- | :--- |
| 1 | 一键生成期间操作被整体锁死 | 点击「一键生成」后加载遮罩覆盖整个要件列表，直至全部任务结束；期间已生成答案的要件无法【编辑 / 重新生成 / 内容优化】，与"并行生成、出一个是一个"的目标不符 |
| 2 | 要件无法在个案中移除 | 仅「个案要件」有删除按钮；「标准要件 / 我的要件」从案由模板/个人预设复制到案件后无移除入口，个案不需要的要点只能留在列表中干扰 |

## 8.2 调整 1：一键生成并行化，已答要件操作放开

### 8.2.1 交互方案

- **取消整体加载遮罩**：点击「一键生成」后不再用遮罩盖住要件列表，各要件卡片独立呈现生成状态
- **逐条并行生成**：批量任务按要件逐条完成（原型模拟分批延时填充），每完成一条**立即**展示答案并放开该条操作，无需等全部完成
- **已答要件即时可操作**：批量任务开始前已有答案的要件，以及任务中已完成要件，【编辑】【重新生成】【内容优化（N/3）】全程可用；单条操作与批量任务并行不互斥；批量过程中每完成一条仅就地刷新该条卡片，不打断其他条目正在进行的内联编辑
- **未答要件状态**：任务运行期间答案区显示轻量生成中指示（沿用现有 loading 样式风格）
- **单条【生成答案】按钮**：非批量运行时，未答要件答案区显示【生成答案】按钮（✨ 图标，文案与实际系统一致），点击单独生成该条答案（含单条加载态），完成后展示常规操作按钮；批量运行期间该按钮被生成中指示替代
- **底部按钮**：沿用现状——运行期间「一键生成」禁用并显示加载态、「新增个案要件」禁用；生成模式下【确认生成（引入 N 条要件）】保持禁用（V1.2 4.3 节防半成品确认规则不变）
- **完成汇总**：全部完成后 toast「已为 N 项要件生成答案，可直接在列表中修改」（沿用现有文案），底部按钮恢复

### 8.2.2 保持不变

- 一键生成触发逻辑：对全部要件批量生成、无需勾选、完成后自动勾选已生成要件
- 生成模式「确认生成」按钮加载期间禁用规则（V1.2 4.3）
- 抽屉关闭时清理运行中状态（含未完成计时器，已完成答案保留）

## 8.3 调整 2：标准/我的要件个案移除

### 8.3.1 交互方案

- **入口**：标准要件/我的要件卡片标题行右侧新增删除按钮，**复用个案要件现有删除按钮样式**（垃圾桶图标 `case-elements-item-del-btn`），不新增弹窗或菜单
- **点击行为**：直接移除 + toast「已从本案移除"XX"要件，不影响案由模板」（与个案要件删除行为一致，不弹二次确认）
- **生效范围**：**仅当前案件**——后台案由要件配置（标准）、个人要件预设（我的）不受影响；同案由新案件仍复制全量模板
- **联动清理**：移除时一并清理该要件的答案、内容优化记录、勾选状态；「一键生成」不再覆盖生成已移除要件；标签计数（如"标准 16"）与勾选统计联动刷新
- **数据结构**：`localStorage.caseElementsRemoved_${caseId}` 存储已移除要件名数组，加载案由模板时过滤；个案要件维持现有物理删除逻辑不变

### 8.3.2 恢复默认要件

- **入口**：抽屉底部左侧「管理我的要件」链接旁新增「恢复默认要件」文本链接（含图标，样式对齐现有链接风格）；**仅当本案存在已移除的标准/我的要件时显示**，无移除记录不渲染
- **点击行为**：一次性恢复本案全部已移除要件（清空移除记录并重新加载模板）+ toast「已恢复 N 项默认要件」；恢复的要件答案为空（移除时已清理），需重新单条生成或一键生成
- **运行约束**：批量生成运行期间「恢复默认要件」禁用并 hover 提示「生成中，请稍候」，与底部按钮一致

### 8.3.3 移除语义

- 与演示评审结论一致：移除 = 个案内"不引用"，非物理删除模板；删除按钮 tooltip 文案「从本案移除，不影响案由模板」

## 8.4 边界与异常 case

1. 批量生成运行中关闭抽屉：清理运行状态（含全部未完成计时器），已完成答案保留
2. 批量生成运行中点【确认生成】：按钮已禁用，无响应；全部完成后自动恢复
3. 移除要件后点「一键生成」：过滤已移除项，仅对剩余要件生成
4. 移除后同案由新建案件：全量复制模板，不受影响
5. 生成模式下移除要件：底部【确认生成（引入 N 条要件）】的 N 计数联动刷新
6. 移除"我的要件"：仅本案不引用，个人预设库（跨案件复用）不受影响
7. 批量生成运行中移除某条待生成要件：该条跳过生成（不写入答案），其余照常完成，完成计数照常推进
8. 单条生成运行中移除该要件：跳过写入，清理该条计时器
9. 批量生成运行中恢复默认要件：入口已禁用，无响应；全部完成后恢复可用
10. 恢复默认要件后再次移除：走同一移除逻辑，移除记录可反复增删

# 九、V1.2.2 新建案件流程极简

## 9.1 调整背景

| # | 问题 | 现状行为 |
| :--- | :--- | :--- |

- **上传文件格式/大小校验（V1.2.3 对齐实际系统）**：类型 PDF / DOC / DOCX / JPG / JPEG / PNG / ZIP；单个材料 ≤ 50MB、ZIP 压缩包 ≤ 1000MB，逐文件校验并 toast 报错；文件列表图标按类型区分（压缩包/图片/文档）

- 同步案件弹窗、补充上传弹窗不受影响

## 9.3 调整 2：解析状态提示与信息修改入口（无确认浮层）

> 交互原则：**系统不做打断式确认**——解析状态以页面内提示条呈现，结构化信息的确认与修改由用户通过列表页「编辑」按钮主动完成。

### 9.3.1 列表页表现

- **「新」标识**：上传建案（≥1 文件）成功时，案件名称旁显示「新」小标签
- **材料数量列解析态**：解析中显示「成功数/总数」+ 转圈图标（沿用现有 parsing 态样式），完成后恢复文件图标
- **不做自动弹出任何弹框**

### 9.3.2 详情页提示条（新增，位置：标题栏下方、内容区上方，对齐实际系统截图）

**状态 1 · 解析中**（浅蓝底 + 蓝色 ⓘ 图标，无按钮，纯状态提示）：

> ⓘ 正在从材料中提取案件信息

- 显示条件：当前案件存在 `parseStatus === 'parsing'` 的文件
- 消失时机：全部文件解析完成时自动切换为状态 2

**状态 2 · 解析完成待确认**（浅黄底 + ⚠ 图标，右侧带操作按钮，提示用户确认修改）：

> ⚠ 案件信息已提取，请确认是否准确；如识别有误，可点击"去修改"调整

- 显示条件：首次解析已完成 **且** 用户尚未编辑保存过（`firstParsePending: true`）
- 【去修改】按钮：跳回案件列表页并自动打开该案件的「编辑案件信息」弹框（预填识别结果）
- 消失时机：用户在编辑弹框【保存】后（含从【去修改】跳转或手动从列表进入），标记确认，此后不再显示
- 演示脚本呼应：mock 识别结果刻意演示"案由识别为上级案由"问题（如「房屋租赁合同」→「合同纠纷」，对应会议纪要实际案例），体现"提示确认修改"的价值

### 9.3.3 信息修改入口：列表页「编辑」按钮

- **沿用现有**「编辑案件信息」弹框（editDialog）与字段结构，不做新组件；对齐实际系统截图布局
- **变化：识别结果预填**——首次解析完成后点「编辑」，mock 识别结果自动预填（此前为空）：
  | 字段 | 预填与交互 |
  | :--- | :--- |
  | 案件名称 | 预填默认名（首个文件名），必填；清空后【保存】禁用 |
  | 案由 | 树形选择器（复用现有案由树弹窗），预填 mock 识别结果 |
  | 案号 / 案字 | 案号预填 mock（如「（2026）京0105民初12345号」）；案字下拉预填（如「民初」），按案件大类过滤、与案由联动（沿用现有） |
  | 原告/上诉人 / 被告/被上诉人 | 预填 mock 当事人；标签随案字切换（沿用现有） |
  | 承办人 | 预填当前用户，可改派或增加协作承办人（提示「默认是你本人，可改派或增加协作承办人」） |
  | 上传日期 | 预填建案日期（沿用现有日期控件） |
- **【保存】**：写回案件对象，关闭弹框；若为首次确认则移除「新」标、详情页提示条状态 2 不再显示
- **【取消】/ X**：不写回、不视为确认，「新」标与提示条保留

### 9.3.4 「新」标识生命周期

- **出现**：上传建案（≥1 文件）成功时
- **持续**：解析中 → 解析完成未确认（整个期间均显示，期间进出详情页不影响）
- **消失**：用户点「编辑」并【保存】（即完成信息确认）


## 9.4 数据与流程

```
列表页「新建案件」→ 极简弹窗（仅上传入口）
    ├─ 0 文件：点「上传并解析」→ toast 提示 + 上传区闪烁引导，不建案（V1.2.3：必须 ≥1 文件）
    └─ ≥1 文件：点「上传并解析」→ 建案（默认名 = 首个文件名）
          → 留在列表页，新案件置顶 + 「新」标，材料列转圈
          → 材料逐个「解析中」（每文件独立 2-3 秒 mock）
          → 全部解析完成
          → 列表页：新标保留（待确认）；详情页：提示条切换为「已提取，请确认」
          → 用户点列表页「编辑」（或详情页提示条【去修改】跳转）
          → 编辑弹框识别结果预填 → 修改并【保存】
          → 「新」标消失、详情页提示条消失 → 正常使用
```

- **解析状态改造**：新建案件 files 的 `parseStatus` 由 `'success'` 改为 `'parsing'`，每个文件独立 2-3 秒 mock 解析计时（复用补充上传的 `startMockParsing` 机制），完成后写回 `'success'` 并触发既有 `case-file-parse-updated` 事件
- **解析续接**：列表页与详情页加载时均检测「parseStatus 为 parsing 的文件」并续接 mock 计时（覆盖中途刷新/切换页面场景）
- **案件标记**：建案时 `firstParsePending: true`；编辑【保存】后置 `false`。「新」标与详情页提示条状态 2 均依据该标记
- **mock 识别结果**：建案时生成并挂到案件对象（`parseResult: { caseNumber, caseWord, cause, partyA, partyB }`）；解析完成前点「编辑」不预填（parseResult 尚未"提取"），完成后预填；案由 mock 从当前业务案由库取值
- **【去修改】跳转链**：详情页 → sessionStorage 记录 `openEditCaseId` → 跳转列表页 → 列表页加载检测并自动打开对应编辑弹框

## 9.5 边界与异常 case

1. **0 文件点「上传并解析」**（V1.2.3）：不建案；toast「请先上传至少 1 个材料文件，再上传并解析」+ 上传区橙色闪烁引导 1.5 秒；按钮弱化置灰但可点击（保证有反馈）
2. **解析中刷新或离开列表页再回来**：列表页加载时续接未完成的 mock 解析；「新」标不受影响
3. **解析中点进案件详情页**：详情页续接解析；解析中显示蓝色提示条，完成后切换为黄色确认提示条
4. **解析完成但从未点编辑**：「新」标与详情页提示条持续显示（提醒待确认），不影响其他功能使用
5. **部分文件解析异常**：正常文件解析完成即视为提取完成（识别基于可用材料），异常文件走既有解析异常处理（列表页黄色标识）
6. **编辑保存时名称为空**：【保存】禁用（名称必填），不清空回退
7. **补充上传 / 同步案件创建的案件**：不显示「新」标、无提示条、编辑不预填识别结果（parseResult 不生成）
8. **列表页解析中拦截**：沿用 v2.23 规则——解析中案件的「生成文书」置灰，不受本次调整影响
