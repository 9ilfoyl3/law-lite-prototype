# 二、调整背景与目标

## 2.1 背景

V1.1 现行交互中，"要件答案的日常维护"与"生成文书时的答案确认"是两套割裂的交互：

| 场景 | 现行载体 | 能力 |
| :--- | :--- | :--- |
| 日常维护（页面顶部右侧「本案要件」入口） | 本案要件抽屉 | 逐条答案展示/编辑、单条重新生成、内容优化（3 轮上限）、优化记录回填、勾选框、一键生成 |
| 生成时确认·有答案（原路径 A） | 大文本框确认弹框 | 整段纯文本编辑；按钮【取消】【不引入要件】【确认生成】 |
| 生成时确认·无答案（原路径 B） | 三步弹框串联 | ① 确认是否引入 → ② 勾选要件 → ③ 大文本框（含预生成加载态） |

## 2.2 现状问题

1. **编辑体验割裂**：同一份要件答案，日常维护用抽屉、生成确认用大文本框，用户需重复学习两套交互
2. **能力不对等**：抽屉具备的单条重新生成、内容优化、优化记录回填在生成确认时不可用；大文本框只能整段手改
3. **脆弱的文本解析**：大文本框确认后需用正则将纯文本按 `【要件名】问题：…答案：…` 拆回结构化数据，用户改动格式后解析易失败
4. **路径 B 链路长**：三连弹框，操作成本高

## 2.3 调整目标

1. 生成确认与日常维护统一复用「本案要件」抽屉，一套交互
2. 要件上下文以结构化数据传递给 workflow，消除纯文本拼接 + 正则解析链路
3. 原路径 B 由"三步弹框"缩短为"轻量询问 + 抽屉"
4. 抽屉内编辑的答案实时持久化，生成前修改的内容留档，日常模式同样可复用

# 四、调整后交互方案（TO-BE）

## 4.1 整体流程

```
点「生成文书」（一步生成 / 分步生成最终按钮）
        │
        ├─ 非判决书 或 无可用要件 ──────────→ 直接开始流式生成
        │
        └─ 判决书 且 有可用要件
                │
        轻量询问弹框（复用现有 preElementConfirmModal）
        「检测到 N 个可用要件…是否引入」
                │
        ┌───────┴──────────────┐
  【引入案由要件】        【直接生成】 / X 关闭
        │                      │
        │               直接生成 / 中止回到配置区
        ▼
   本案要件抽屉 · 生成模式（默认全选）
        │
        ├─ 有答案：直接展示，可编辑 / 单条重新生成 / 内容优化
        ├─ 无答案：手动点「一键生成」预生成（含加载态），再编辑
        │
   底部【确认生成（引入 N 条要件）】
        │
        ├─ N ≥ 1：按钮可用 → 点击后抽屉自动关闭 → 主界面流式输出开始
        └─ N = 0：按钮置灰不可点击，按钮上方显示引导提示（实时联动）
                ├─ 已勾选要件但均无答案：「已勾选 N 项，请点击一键生成…」
                └─ 未勾选任何要件：「请勾选要引入的要件，或点击一键生成」
```

## 4.2 轻量询问弹框（前置）

- **复用现有 `preElementConfirmModal`**：样式、文案（共 N 个可用要件（标准 X / 我的 Y / 个案 Z）、引入价值说明、耗时提示）沿用现状
- **触发规则变化**：原"有答案（路径 A）不询问、直接弹大文本框"的行为**取消**；只要满足触发条件（判决书 + 有可用要件），一律先弹轻量询问弹框，有答案/无答案不再影响前置流程
- **按钮**：
  - 【引入案由要件】→ 打开本案要件抽屉（生成模式）
  - 【直接生成】→ 不引入要件，直接开始流式生成
  - X / 遮罩关闭 → 中止本次生成动作，回到配置区

## 4.3 本案要件抽屉 · 生成模式

- **唯一来源**：生成文书 → 轻量询问弹框 → 【引入案由要件】。从页面顶部右侧「本案要件」入口打开为**日常模式**，底部不显示确认生成按钮，行为与现状完全一致
- **默认勾选**：每次经【引入案由要件】进入生成模式时，重置为全部可用要件勾选（不沿用上次取消勾选的状态）
- **复用抽屉现有能力**：逐条答案展示/编辑、单条【重新生成】、【内容优化】（N/3）、优化记录回填、新增个案要件、勾选统计、三色来源标签、「管理我的要件」链接
- **有答案（承接原路径 A）**：直接展示已有答案，用户可编辑后确认生成
- **无答案（承接原路径 B）**：答案区为空，由用户手动点底部「一键生成」为勾选要件批量预生成答案（含现有加载态），完成后可继续编辑；**系统不自动触发预生成**
- **底部操作条**：生成模式下新增主按钮**【确认生成（引入 N 条要件）】**（主色按钮，置于抽屉底部按钮区）；N 为"已勾选且有答案"的要件数，随勾选与答案状态实时联动刷新文案；日常模式不渲染该按钮
- **按钮可用性（V1.2.20：收敛为单点判定）**：**按钮可用 ⇔ N ≥ 1 且非「一键生成」运行中**。N = 0 时按钮**直接置灰、不可点击**——原「按钮可点 → 点击后 toast『尚无答案，建议先生成』」的滞后反馈取消，改为状态前置
- **N = 0 引导提示（V1.2.20 新增）**：按钮置灰时，在其**上方**显示一条黄色引导条（位于生成模式操作条内、【确认生成】按钮之上），引导用户去点底部「一键生成」；文案按勾选状态区分：
  - 已勾选 ≥1 项但均无答案：**「已勾选 N 项，请点击右下角『一键生成』批量生成答案（也可单条点击『生成答案』）」**
  - 未勾选任何要件：**「请勾选要引入的要件，或点击右下角『一键生成』生成答案」**
  - 提示随「勾选变化 / 答案生成 / 答案删除」实时刷新；当 N ≥ 1 或批量生成运行中时自动隐藏
- **一键生成加载期间**：【确认生成】按钮禁用（合并进上条单点判定），加载结束恢复；此时引导提示隐藏（避免与"生成中"状态语义冲突）

## 4.4 确认生成校验规则（V1.2.20 修订）

> 判定统一为**按钮态前置**：能点 = 能生成。N = 0 时按钮置灰，用户无法触发点击，不再依赖"点击后 toast 兜底"。

| 校验情形 | 按钮态 | 行为 |
| :--- | :--- | :--- |
| N ≥ 1（存在勾选且有答案的要件） | **可用**（主色） | 点击 → 关闭抽屉 → 主界面立即开始流式输出；勾选但无答案的要件不纳入上下文 |
| 勾选了要件但均无答案（N = 0） | **置灰** | 不可点击；按钮上方引导提示「已勾选 N 项，请点击右下角『一键生成』…」 |
| 未勾选任何要件（N = 0） | **置灰** | 不可点击；按钮上方引导提示「请勾选要引入的要件，或点击右下角『一键生成』生成答案」 |
| 一键生成批量运行中 | **置灰** | 不可点击（防半成品确认）；引导提示隐藏 |

- **部分有答案 / 部分无答案**：仅引入有答案的 N 条（按钮文案中的 N 即该数量）；如需引入更多，可先「一键生成」或单条【生成答案】/【重新生成】补齐答案后再确认
- **兜底**：置灰按钮不响应点击；`confirmDrawerGenerate` 保留 `answers.length === 0` 守卫（键盘 Enter / 脚本触发等绕过 UI 的场景），toast 文案沿用原规则

## 4.5 关闭与放弃

- 生成模式下点 X / 遮罩关闭抽屉 = **放弃本次生成**，回到配置区，不触发生成
- 抽屉内已编辑/生成的答案已实时持久化（现有机制），关闭不丢失，下次进入（含日常模式）恢复

## 4.6 生成中状态约束

- 确认生成后**抽屉自动关闭**，再开始流式输出
- 流式输出期间页面顶部右侧「本案要件」入口**禁用**，hover 提示「文书生成中，暂不可修改要件」；输出结束后恢复

## 4.7 数据传递与持久化

- 引入上下文以**结构化数组**传递给生成流程（name / desc / question / answer），范围 = 勾选 ∩ 已有答案
- 废除"纯文本拼接 + 正则拆解"链路（原大文本框确认逻辑）
- 答案持久化沿用 `localStorage.caseElements_${caseId}`，存储结构不变，历史数据无需迁移

# 八、V1.2.1 要件抽屉交互增强

> 本章节为 V1.2.1 增量调整，对应 2026-09-07 演示评审《原型待调整清单》第 6/7/8 项。
> 原则：**不改动现有抽屉 UI 版式与组件样式**，仅调整交互逻辑与状态呈现。

## 8.1 调整背景

| # | 问题 | 现状行为 |
| :--- | :--- | :--- |
| 1 | 一键生成期间操作被整体锁死 | 点击「一键生成」后加载遮罩覆盖整个要件列表，直至全部任务结束；期间已生成答案的要件无法【编辑 / 重新生成 / 内容优化】，与"并行生成、出一个是一个"的目标不符 |
| 2 | 要件无法在个案中移除 | 仅「个案要件」有删除按钮；「标准要件 / 我的要件」从案由模板/个人预设复制到案件后无移除入口，个案不需要的要点只能留在列表中干扰 |

## 8.2 调整 1：一键生成并行化，已答要件操作放开

### 8.2.1 交互方案

- **取消整体加载遮罩**：点击「一键生成」后不再用遮罩盖住要件列表，各要件卡片独立呈现生成状态
- **逐条并行生成**：批量任务按要件逐条完成（原型模拟分批延时填充），每完成一条**立即**展示答案并放开该条操作，无需等全部完成
- **已答要件即时可操作**：批量任务开始前已有答案的要件，以及任务中已完成要件，【编辑】【重新生成】【内容优化（N/3）】全程可用；单条操作与批量任务并行不互斥；批量过程中每完成一条仅就地刷新该条卡片，不打断其他条目正在进行的内联编辑
- **未答要件状态**：任务运行期间答案区显示轻量生成中指示（沿用现有 loading 样式风格）
- **单条【生成答案】按钮**：非批量运行时，未答要件答案区显示【生成答案】按钮（✨ 图标，文案与实际系统一致），点击单独生成该条答案（含单条加载态），完成后展示常规操作按钮；批量运行期间该按钮被生成中指示替代
- **底部按钮**：沿用现状——运行期间「一键生成」禁用并显示加载态、「新增个案要件」禁用；生成模式下【确认生成（引入 N 条要件）】保持禁用（V1.2 4.3 节防半成品确认规则不变）
- **完成汇总**：全部完成后 toast「已为 N 项要件生成答案，可直接在列表中修改」（沿用现有文案），底部按钮恢复

### 8.2.2 保持不变

- 一键生成触发逻辑：对全部要件批量生成、无需勾选、完成后自动勾选已生成要件
- 生成模式「确认生成」按钮加载期间禁用规则（V1.2 4.3）
- 抽屉关闭时清理运行中状态（含未完成计时器，已完成答案保留）

## 8.3 调整 2：标准/我的要件个案移除

### 8.3.1 交互方案

- **入口**：标准要件/我的要件卡片标题行右侧新增删除按钮，**复用个案要件现有删除按钮样式**（垃圾桶图标 `case-elements-item-del-btn`），不新增弹窗或菜单
- **点击行为**：直接移除 + toast「已从本案移除"XX"要件，不影响案由模板」（与个案要件删除行为一致，不弹二次确认）
- **生效范围**：**仅当前案件**——后台案由要件配置（标准）、个人要件预设（我的）不受影响；同案由新案件仍复制全量模板
- **联动清理**：移除时一并清理该要件的答案、内容优化记录、勾选状态；「一键生成」不再覆盖生成已移除要件；标签计数（如"标准 16"）与勾选统计联动刷新
- **数据结构**：`localStorage.caseElementsRemoved_${caseId}` 存储已移除要件名数组，加载案由模板时过滤；个案要件维持现有物理删除逻辑不变

### 8.3.2 恢复默认要件

- **入口**：抽屉底部左侧「管理我的要件」链接旁新增「恢复默认要件」文本链接（含图标，样式对齐现有链接风格）；**仅当本案存在已移除的标准/我的要件时显示**，无移除记录不渲染
- **点击行为**：一次性恢复本案全部已移除要件（清空移除记录并重新加载模板）+ toast「已恢复 N 项默认要件」；恢复的要件答案为空（移除时已清理），需重新单条生成或一键生成
- **运行约束**：批量生成运行期间「恢复默认要件」禁用并 hover 提示「生成中，请稍候」，与底部按钮一致

### 8.3.3 移除语义

- 与演示评审结论一致：移除 = 个案内"不引用"，非物理删除模板；删除按钮 tooltip 文案「从本案移除，不影响案由模板」

## 8.4 边界与异常 case

1. 批量生成运行中关闭抽屉：清理运行状态（含全部未完成计时器），已完成答案保留
2. 批量生成运行中点【确认生成】：按钮已禁用，无响应；全部完成后自动恢复
3. 移除要件后点「一键生成」：过滤已移除项，仅对剩余要件生成
4. 移除后同案由新建案件：全量复制模板，不受影响
5. 生成模式下移除要件：底部【确认生成（引入 N 条要件）】的 N 计数联动刷新
6. 移除"我的要件"：仅本案不引用，个人预设库（跨案件复用）不受影响
7. 批量生成运行中移除某条待生成要件：该条跳过生成（不写入答案），其余照常完成，完成计数照常推进
8. 单条生成运行中移除该要件：跳过写入，清理该条计时器
9. 批量生成运行中恢复默认要件：入口已禁用，无响应；全部完成后恢复可用
10. 恢复默认要件后再次移除：走同一移除逻辑，移除记录可反复增删

### 9.3.4 标识生命周期（V1.2.21 拆分语义，V1.2.22 收敛展示面）

**「新」（时间性）——列表页唯一标识**

- **出现**：上传建案（≥1 文件）成功时
- **消失**：**跨自然日自动隐藏**——渲染时比较建案日期（`createdAt`）与当天日期，非当天即不渲染，无需任何用户动作、无需定时任务
- **展示位置**：列表页案件名称旁（蓝色小标签）
- **作用**：配合置顶，帮用户快速定位"我刚建的案子"
- **不因确认而消失**：即使用户当天就确认了信息，「新」在当天内仍然显示

**「待确认」（状态性）——仅由详情页提示条承载，不落列表页（V1.2.22）**

- **承载方式**：详情页黄色提示条（「案件信息已提取，请确认是否准确…」+【信息无误】【去修改】），**列表页不渲染该标识**
- **出现**：首次解析完成（解析中显示浅蓝状态条，不显示确认条）
- **消失**：用户完成确认——两条路径任选其一即可：① 详情页提示条【信息无误】；② 编辑弹框【保存】
- **不因跨天而消失**：即使用户多日未确认，详情页提示条仍持续显示，直至确认

**拆分理由（原单标识的问题）**：原「新」同时承载两个语义——标签字面是"时间性"（刚创建），消失条件却是"状态性"（信息已确认），需 hover 文案才能解释清楚。由此产生两个反例：① **误消**——用户只想改个案件名，顺手【编辑】→【保存】就消了标，但他并未核对案由/当事人；② **永挂**——用户从不点编辑，三个月前的案件仍标「新」，名不副实。

**列表页精简理由（V1.2.22）**：拆分后「待确认」标识与详情页提示条表达的是**同一个状态**，属重复展示；且列表页已承载案由、材料数、文书数、更新日期等多列信息，再加一个状态标会加重视觉负担。故列表页只保留时间性的「新」，状态性提示收敛到详情页——用户点进案件即见，提醒效果不受影响。


## 9.4 数据与流程

```
列表页「新建案件」→ 极简弹窗（仅上传入口）
    ├─ 0 文件：点「上传并解析」→ toast 提示 + 上传区闪烁引导，不建案（V1.2.3：必须 ≥1 文件）
    └─ ≥1 文件：点「上传并解析」→ 建案（默认名 = 首个文件名，写入 createdAt）
          → 留在列表页，新案件置顶 + 「新」标（当天有效），材料列转圈
          → 材料逐个「解析中」（每文件独立 2-3 秒 mock）
          → 全部解析完成
          → 列表页：仅「新」标（不承载状态标）；详情页：提示条切换为「已提取，请确认」
          → 用户确认（两条路径任选其一）：
              ├─ 识别无误 → 详情页提示条【信息无误】直接确认
              └─ 需修改 → 详情页提示条【去修改】或列表页「编辑」（V1.2.10：当前页内弹出公共组件，详见 9.8）→ 预填 → 【保存】
          → 详情页提示条消失 → 正常使用（「新」按当天规则独立到期）
```

- **解析状态改造**：新建案件 files 的 `parseStatus` 由 `'success'` 改为 `'parsing'`，每个文件独立 2-3 秒 mock 解析计时（复用补充上传的 `startMockParsing` 机制），完成后写回 `'success'` 并触发既有 `case-file-parse-updated` 事件
- **解析续接**：列表页与详情页加载时均检测「parseStatus 为 parsing 的文件」并续接 mock 计时（覆盖中途刷新/切换页面场景）
- **案件标记（V1.2.21 拆分 / V1.2.22 收敛展示面）**：
  - `createdAt`：建案时写入建案日期，用于**列表页「新」标识**——渲染时与当天日期比对，非当天即不渲染（跨日自动隐藏，无需定时任务）
  - `firstParsePending`：建案时 `true`，用户确认后（【信息无误】或【编辑→保存】）置 `false`，**仅驱动详情页提示条状态 2**（V1.2.22 起列表页不再渲染该状态）
  - 原「「新」标与详情页提示条状态 2 共用 `firstParsePending`」的耦合取消，列表页标识与详情页提示条各自独立
- **mock 识别结果**：建案时生成并挂到案件对象（`parseResult: { caseNumber, caseWord, cause, partyA, partyB }`）；解析完成前点「编辑」不预填（parseResult 尚未"提取"），完成后预填；案由 mock 从当前业务案由库取值
- **【去修改】跳转链**：详情页 → sessionStorage 记录 `openEditCaseId` → 跳转列表页 → 列表页加载检测并自动打开对应编辑弹框

## 9.5 边界与异常 case

1. **0 文件点「上传并解析」**（V1.2.3）：不建案；toast「请先上传至少 1 个材料文件，再上传并解析」+ 上传区橙色闪烁引导 1.5 秒；按钮弱化置灰但可点击（保证有反馈）
1a. **名称为空点「上传并解析」**（V1.2.4）：不建案；toast「请填写案件名称」+ 输入框聚焦红色闪烁；名称默认自动填充（除非用户手动清空），正常流程不会触发
2. **解析中刷新或离开列表页再回来**：列表页加载时续接未完成的 mock 解析；「新」标（当天）与「待确认」标识均不受影响
3. **解析中点进案件详情页**：详情页续接解析；解析中显示蓝色提示条，完成后切换为黄色确认提示条
4. **解析完成但从未确认**：详情页提示条**持续显示**（提醒待确认），不影响其他功能使用；列表页「新」标则按当天规则自动到期消失
4a. **建案当天即完成确认**（V1.2.21）：「新」标仍在当天内显示（时间性标识不受确认动作影响）
4b. **历史存量案件（无 `createdAt` 字段）**（V1.2.21）：视为非当天，列表页「新」标不显示；`firstParsePending` 为真的案件进详情页仍正常显示确认提示条
5. **部分文件解析异常**：正常文件解析完成即视为提取完成（识别基于可用材料），异常文件走既有解析异常处理（列表页黄色标识）
6. **编辑保存时名称为空**：【保存】禁用（名称必填），不清空回退
7. **补充上传 / 同步案件创建的案件**：不显示「新」/「待确认」标识、无提示条、编辑不预填识别结果（parseResult 不生成）
8. **列表页解析中拦截**：沿用 v2.23 规则——解析中案件的「生成文书」置灰，不受本次调整影响
9. **跨天场景**（V1.2.21）：建案次日刷新列表 →「新」自动消失；若此前未确认，「待确认」仍在（无需任何手动操作，也不用重新建案）

# 十、V1.2.4 文书生成流程重构（法条确认前置）

> 本章节为 V1.2.4 增量调整，对应 2026-09-07 演示评审《原型待调整清单》第 1/2/3/4 项。
> 涉及页面：pages/case-files.html（新增「本案法条」入口与抽屉、渲染样式）；js/case-files.js（生成链路、法条异步任务、渲染函数）。
> 核心决策：**一次动作只允许一次模型调用**。原「点一次生成 = 一次调用直接出全文」拆为「第一次调用出法条 → 用户确认 → 第二次调用出文书」。

## 10.1 调整背景

| # | 问题 | 现状行为 |
| :--- | :--- | :--- |
| 1 | 一次动作内多次模型调用 | 点「生成文书」后由单一流程一次性完成检索法条 + 生成全文，耗时长、过程不可控 |
| 2 | 法条不可见不可改 | 法条由流程内部消化，用户既看不到引用了哪些法条，也无法在生成前干预；存在虚构/错配风险 |
| 3 | 大模型渲染质量差 | 实测耗时约 2 分钟，存在丢内容、篡改话术问题 |
| 4 | 缺少可等待的异步感知 | 用户点生成后只能干等，无任何中间产出可查看 |

## 10.2 调整 1：工作流拆分为「法条确认 → 文书生成」两段

### 10.2.1 新流程

```
案件上传完成（材料解析触发，与结构化信息提取同源）
    └─ 后台异步启动法条检索（mock 4-6s）  ← 不占用用户动作
          │
进入案件详情页 → 检测：未完成则等待 / 已完成则直接可用
          │
点「生成文书」（一步生成 / 分步生成最终「生成文书」）
    │
    ├─ 前置校验（案件阶段 / 材料选择 / 解析状态 / workflow 超限）… 不变
    │
    ├─ 要件引入（仅 judgment 且该案由有可用要件）… V1.2 流程不变
    │     └─ 要件抽屉【确认生成（引入 N 条要件）】
    │
    ▼
本案法条抽屉 · 生成模式（全部文书类型必经）
    ├─ 顶部后果说明：「勾选的法条将写入文书『法律适用依据』章节，未勾选的不写入」
    ├─ 核心依据（2-3 条，默认勾选）/ 可补充依据（默认不勾）/ 手动添加（默认勾选）
    ├─ 法条已就绪 → 直接展示，可改/可增删/可勾选
    ├─ 法条未就绪 → 抽屉内显示「正在检索适用法条…」加载态，完成后自动填充
    └─ 底部【确认法条并生成文书（N 条写入文书）】
          │
          ├─ N ≥ 1：抽屉关闭 → 主界面脚本流式渲染开始（仅写入已勾选法条）
          └─ N = 0：toast「请至少确认 1 条适用法条」，不触发生成
          │
          ▼
    脚本匹配流式渲染（标题 + 统一字体正文、靠左）
```

### 10.2.2 触发规则

- **适用全部文书类型**（判决书、庭审提纲、其他）：点「生成文书」后一律先进入法条确认环节，不再按文书类型区分
- **双入口一致**：一步生成 `generateByMaterial`、分步生成最终 `compileSteps` 均走同一法条确认链路
- **列表页快捷生成**：跳转详情页后自动引入要件并直接进入法条确认，**不自动跳过**（与要件环节处理一致：法条是法律适用依据，必须经用户确认）
- **要件与法条的先后**：要件在前（事实基础）、法条在后（法律依据）。要件抽屉【确认生成】点击后关闭要件抽屉、紧接着打开法条抽屉，用户感知为连续两步

### 10.2.3 保持不变

- 生成前置校验（案件阶段、材料选择、全部文件异常阻拦、workflow 超限弹框）全部不变
- V1.2 要件询问弹框与要件抽屉交互（含 V1.2.1 并行生成、个案移除、恢复默认）完全不变
- 要件答案的结构化数据传递方式不变

## 10.3 调整 2：法条异步预生成

### 10.3.1 触发与状态机

- **触发时机**：**案件上传后**（材料解析启动时，与结构化信息提取同源、同生命周期）即后台异步启动，不弹窗、不阻塞、不占用用户操作；案件详情页 / 列表页加载时仅负责**检测并续接**未完成任务（刷新 / 切页场景），不再作为触发点
- **状态机**：

| 状态 | 含义 | 入口按钮表现 | 抽屉内表现 |
| :--- | :--- | :--- | :--- |
| `idle` | 未启动 | 「本案法条 -」 | — |
| `running` | 检索中 | 「本案法条」+ 转圈图标 | 「正在检索适用法条…」加载态 + 进度文案 |
| `done` | 已完成 | 「本案法条 N」 | 法条清单，可改/增删/勾选 |
| `failed` | 检索失败（mock 不触发，预留） | 「本案法条 !」 | 错误提示 + 【重新检索】按钮 |

- **耗时**：mock 4-6 秒（对齐"等待可感知但不漫长"的演示节奏）
- **持久化**：`localStorage.caseLaws_${caseId}` = `{ status, cause, items: [...] }`
  - `cause` 记录检索时的案由，用于失效判断（见 10.3.3）
- **续接**：页面加载时若 `status === 'running'` 则续接 mock 计时（覆盖中途刷新/切页场景）

### 10.3.2 法条数据来源（mock）

- 按案件**案由关键词**匹配法条库，每次返回 4-8 条：

| 案由关键词 | 法条示例 |
| :--- | :--- |
| 借贷 | 民法典第 667 / 674 / 676 / 680 条，民诉法第 147 / 260 条 |
| 租赁 | 民法典第 703 / 708 / 712 / 722 / 724 条 |
| 买卖 | 民法典第 595 / 626 / 577 条 |
| 劳动 | 劳动合同法第 30 / 38 / 46 / 82 条 |
| 侵权 / 人身损害 | 民法典第 1165 / 1179 / 1183 条 |
| 兜底（其他） | 民法典第 7 条（诚信）、第 577 条（违约责任），民诉法第 67 条（举证责任）、第 147 / 260 条 |

- 每条法条结构：`{ id, name, content, source: 'ai' | 'manual' }`
  - `name` 例：「《中华人民共和国民法典》第六百六十七条（借款合同定义）」
  - `content` 例：「借款合同是借款人向贷款人借款，到期返还借款并支付利息的合同。」
- 默认全部勾选（`selected: true`）

### 10.3.3 失效与重跑

- **案由变更**：详情页修改案由后，若 `caseLaws.cause !== 新案由`，清空**全部法条数据**（含手动添加，因案由已变、原法条不再适用）并自动重新异步检索（对应清单第 10 项"案由识别错导致匹配错"的连锁修复）
- **手动重跑（【重新检索】按钮）**：仅重新生成 **AI 推荐**法条，**手动添加的法条予以保留**。点击有确认提示（文案「重新检索将按当前案由重新生成 AI 推荐法条，手动添加的法条将保留，是否继续？」），避免误触丢失用户已编辑的 AI 推荐内容；完成后新 AI 推荐追加在原有手动法条之后
- **要件/法条的联动**：改案由时**保留要件答案**（用户可能已编辑），仅重跑法条（评审确认方案）

## 10.6 数据与流程

```
案件上传完成 → 后台启动法条异步检索（status: running）
   （与结构化信息提取同源，随材料解析一并触发）

详情页 / 列表页加载（initPage / init）
  └─ 检测 localStorage.caseLaws_${caseId}
        ├─ 无 → 启动异步检索（status: running）
        ├─ running → 续接计时
        └─ done 且 cause 未变 → 直接可用

点「生成文书」
  → 前置校验 → [要件环节（judgment）] → 打开本案法条抽屉（生成模式）
  → 用户确认 → 收集已勾选法条 → 关闭抽屉
  → startStreamingOutput（脚本渲染）

详情页修改案由
  → 比对 caseLaws.cause
     ├─ 一致 → 不动
     └─ 不一致 → 清空 + 重新异步检索 + toast「案由已变更，正在重新检索适用法条」
```

- **数据结构**：
  - `localStorage.caseLaws_${caseId}` = `{ status: 'idle'|'running'|'done'|'failed', cause: string, items: [{ id, name, content, source, selected }] }`
  - 生成上下文以**结构化数组**传递：`[{ name, content }]`，范围 = 已勾选法条
- **历史数据**：无存量，不需要迁移

## 10.7 边界与异常 case

1. **上传后立即点生成**（法条仍在检索）：抽屉显示加载态，主按钮禁用；检索完成后自动填充并恢复按钮
2. **检索中刷新页面**：续接计时，不重复启动
3. **法条全部取消勾选点确认**：toast 提示，不生成
4. **生成模式下关闭抽屉（X / 遮罩）**：放弃本次生成，回到配置区；已编辑法条保留
5. **放弃后再次点生成**：重新打开法条抽屉，保留上次编辑结果
6. **改案由时法条正在检索**：取消原计时器，按新案由重新检索
7. **手动添加法条后点【重新检索】**：仅重建 AI 推荐法条，手动添加的法条保留（确认弹框已说明）
8. **分步生成中途返回**：不影响法条数据（已持久化）
9. **渲染期间点材料树入口**：两个入口均禁用，hover 提示
10. **法条检索 mock 失败**（预留）：状态置 `failed`，抽屉显示错误 + 【重新检索】

## 10.10 V1.2.8 法条分层与默认勾选策略

> 本节为 V1.2.8 增量调整。背景：V1.2.4 起 AI 推荐法条**默认全部勾选**，演示与评审中暴露两个问题——
> **① 后果不可见**：勾选项与生成结果之间缺因果说明，用户不知道"勾选"即意味着"写入文书的法律适用依据章节"，面对一排已勾选的框既不知会发生什么、也不知不勾会怎样；
> **② 精简成本过高**：借贷案由推荐 10 条，用户只要 3 条就得做 7 次取消勾选——默认全选把"减法"变成了主要操作，而做减法比做加法更费劲。

> **注（V1.2.9）：本节的分层 UI 已回退**——原「核心依据 / 可补充依据」分组与标签取消，AI 推荐合并为一组；默认勾选改为**全不选**。回退理由见 10.11.1。本节保留作为决策记录，以 10.11 为准。

### 10.10.1 分层定义

AI 推荐法条按重要度拆为两层，与「手动添加」并列共 **3 个分组**：

| 分组 | 来源 | 默认勾选 | 标签 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| **核心依据** | AI 推荐 | ✅ **勾选** | 核心 | 2-3 条实体法核心条款（如借贷：667 定义 / 676 逾期 / 680 利率限制） |
| **可补充依据** | AI 推荐 | ⬜ 不勾选 | 可补充 | 程序法与通用条款（如举证责任、缺席判决、迟延履行） |
| **手动添加** | 用户从法条库添加 | ✅ 勾选 | 手动添加 | 用户主动添加，默认即为所需 |

- 数据结构新增 `tier` 字段：`'core' | 'optional'`（手动添加项无 tier，`source: 'manual'`）
- **历史数据兼容**：读取时无 `tier` 的 AI 推荐项按 `core` 处理，勾选状态沿用原值

### 10.10.2 后果可见（两项改造）

1. **抽屉顶部后果说明条**（统计条下方，浅灰底 + ⓘ 图标，12px 次要文字）：

   > ⓘ 勾选的法条将写入文书「法律适用依据」章节，未勾选的不写入

2. **确认按钮文案带后果**：由「确认法条并生成文书（N 条）」改为
   **「确认法条并生成文书（N 条写入文书）」**，N 随勾选实时联动

### 10.10.3 推荐数量收敛

- 每条推荐规则拆为 `core`（2-3 条）+ `optional`（≤5 条），**总数 ≤8 条**
- 收敛后各案由推荐量：借贷 8 / 租赁 8 / 买卖 8 / 侵权 7 / 劳动 7 / 交通事故 7 / 离婚 6 / 继承 5 / 医疗损害 5 / 相邻物权 5 / 刑事 4 / 公司 4 / 抵押质押 4 / 高空抛物 4 / 行政 2 / 兜底 5
- 目的：贴近实际裁判文书引用量（通常 3-8 条），直接降低筛选负担

## 10.11 V1.2.9 法条交互回退与入口区分

> 本节为 V1.2.9 增量调整，**覆盖 10.10**。

### 10.11.1 调整背景（三条）

| # | 问题 | 说明 |
| :--- | :--- | :--- |
| 1 | 分层是系统在替用户判断重要性 | 10.10 的「核心依据 / 可补充依据」由系统标注哪些是核心。但**系统认为的核心也许是错的，而用户手动添加的才可能是真正的核心**——重要性应由用户判断，不由系统预设 |
| 2 | 底部按钮文案有歧义 | 「添加法条」「重新检索」用户难以分辨差异；二者本质是**人工** vs **AI** 两种获取方式 |
| 3 | 必办与选办入口 UI 相同 | 本案法条是**生成文书前必须确认**的环节，本案要件是**可选引入**；两者入口并列且样式一致，用户无从分辨轻重（入口位置 V1.2.26 起由材料树顶部迁至中间栏顶部） |

### 10.11.2 取消分层

- 「核心依据 / 可补充依据」合并为 **「AI推荐」** 一组，不再分组、不再打核心/可补充标签
- `tier` 字段**保留但退化**：仅用于推荐结果排序（core 排前），不参与分组、不打标签、不影响默认勾选
- 来源标签恢复为：**AI推荐 = 蓝 / 手动添加 = 橙**
- 抽屉分组由 3 组（核心 / 可补充 / 手动添加）收敛为 2 组（**AI推荐 / 手动添加**）

### 10.11.3 默认全不选 + 全选/清空

- **AI 推荐法条默认全部不勾选**——不替用户预选，由用户自行判断哪些适用
- 统计条右侧提供 **【全选】【清空】** 快捷操作：想直接采用系统推荐则一键全选，想自己挑则逐条勾选
- **手动添加**的法条仍默认勾选（用户主动添加即为所需）

### 10.11.4 已勾选法条置顶

- 组内**已勾选法条置顶展示**、未勾选的在后，同状态下保持原相对顺序
- 已勾选条目加**浅色底标识**，视觉上形成"已选区"
- 勾选 / 取消后列表**即时重排**，用户勾完可立刻在顶部看到自己选了什么，无需在列表中查找
- 手动添加组同样适用（因其默认勾选，通常整体位于组顶）

### 10.11.5 底部按钮文案

| 调整前 | 调整后 | 语义 |
| :--- | :--- | :--- |
| 【添加法条】 | **【手动检索】** | 人工方式：打开法条库弹窗检索并添加 |
| 【重新检索】 | **【AI推荐】** | AI 方式：按当前案由重新生成 AI 推荐法条 |

- 二者构成 **人工 vs AI** 的清晰对立；【AI推荐】按钮 hover 提示「按当前案由重新生成 AI 推荐法条，手动添加的法条将保留」

### 10.11.6 入口区分（必办 vs 选办）

材料树顶部两个入口做视觉权重区分：

| 入口 | 性质 | 样式 | 徽标 |
| :--- | :--- | :--- | :--- |
| **本案法条** | 生成文书**必须确认**（V1.2.25：**已勾选即视为已确认**） | 主色实心边框、主色文字（保持现有强调样式） | 状态徽标：**检索中**（灰转圈）/ **待确认**（橙，一条未勾）/ **已确认 N 条**（绿，勾选 ≥ 1 条） |
| **本案要件** | **可选**引入 | 弱化样式：浅灰底、灰边框、次要文字色 | 固定灰标「**选填**」 |

- 法条徽标状态流转（**V1.2.25 修订**）：进入时若检索中 → 「检索中」；**检索完成后按勾选数判定**——已勾选 ≥ 1 条 → 「已确认 N 条」（绿），一条未勾 → 「待确认」（橙）；案由变更或重新 AI 推荐后清空勾选 → 回到「待确认」
  - **变更理由**：V1.2.25 起"勾选即视为已确认"（见 10.14），徽标判定须与生成流程一致，否则会出现"徽标显示待确认、生成时却不弹抽屉"的自相矛盾
  - `caseLawsState.confirmed` 标记**保留**（记录用户是否点过【确认法条并生成文书】，用于持久化），但**不再参与徽标判定**
- 数据：`caseLawsState.confirmed`（布尔）记录是否已确认，随 localStorage 持久化

- **入口位置（V1.2.26 建立 / **V1.2.27 调整至页面顶部 header**）**：两个入口位于**页面顶部右侧 `.detail-header-right`**，在「历史文书」按钮左侧，其间加一条竖线分隔。V1.2.27 之前曾短暂位于中间栏顶部入口带（与三个生成方式 tab 同行），因观感别扭而调整。

  ```
  ┌─ 案件材料 ─────────────── ⟨本案要件 6⟩ ⟨本案法条 待确认⟩ ┃ [历史文书] ┐
     (2026)…民初12345号
  ```

  - **语义**：三者同属**案件级面板入口组**——要件 / 法条点开为右侧抽屉，历史文书点开为历史面板，性质一致
  - **调整原因**：把"点击弹抽屉"与"点击切换中间栏内容"两类不同行为放在同一行，空间暗示"它们是一类"，形状差异也压不住；且中间栏顶部堆 5 个元素会削弱"生成方式"的主体地位
  - **样式（V1.2.28 修订）**：两个入口本体**统一中性**——灰边 + 浅底 + 次要文字，**hover 时才给主色反馈**（主色边 + 主色浅底 + 主色文字）
    - **修订原因**：V1.2.9 原用"法条主色填充、要件弱化"的静态配色表达轻重，但主色填充在页面上读作**"已选中"**，与相邻 `.gen-tab` 的主色下划线选中态语义冲突，进页面即误以为默认选中了「本案法条」
    - **强调职责改由动态徽标承担**（信息量更高、且不会误读为选中态）：
      - 状态徽标：要件「选填」灰标 / 法条「待确认」橙标 →「已确认 N 条」绿标
      - 法条计数徽标保留主色（条数是必办信息），要件计数为中性灰
    - 入口尺寸按 header 按钮规格缩小
  - **中间栏顶部**：回归纯三个生成方式 tab（AI问答 / 材料生成 / 分步生成），不再混入资料入口
  - **材料树**：顶部固定条 `.material-col-elements-bar` 已于 V1.2.26 整条删除，材料树回归纯材料列表

## 10.12 V1.2.14/V1.2.16 文书排版（清单第 5 项：手动触发全量格式）

> V1.2.14 新增（2026-09-10）；V1.2.16 按实际系统截图调整按钮位置与生成后头部形态。

### 10.12.1 背景

- V1.2.4 渲染方案：弃用大模型渲染，改为脚本匹配流式渲染（标题 + 统一字体正文、整体靠左），**案号/签章/落款日期本期后置**——生成快，但缺正式司法文书格式。

### 10.12.2 入口与按钮状态（V1.2.16 定稿）

- 位置：**生成结果区头部按钮组**，紧跟【文书精修】右侧（对齐实际系统截图；V1.2.14 曾放右上角历史文书旁，已调整）。

- 按钮状态：

| 状态 | 文案 | 提示 |
|---|---|---|
| 无文书内容 | 文书排版（置灰） | 暂无可排版的文书，请先生成文书 |
| 有内容未排版 | 文书排版 | 手动触发全量格式排版（案号/签章/落款），本期默认不自动排版 |
| 排版中 | 排版中（图标旋转、禁用） | 正在排版，请稍候 |

- 左侧：文书名称（`案件名_文书名`）+ 副标题「第 N 版 · 系统管理员 · YYYY-MM-DD HH:mm」；替代原「生成结果」标题。
- 右侧按钮组见 10.12.2；新增顶部【保存】按钮（与编辑器工具栏【保存】等效，保存到历史文书）。
- 版本号规则：生成完成显示"将保存的版本号"（历史文书版本数 + 1），保存成功后按实际版本刷新。
- 一步/分步生成 Tab 在生成后随中栏折叠自然消失（与实际系统一致）。

### 10.12.4 排版规则（脚本匹配，不使用大模型）

排版 = 给 `.result-doc` 加 `doc-formatted` 类 + 补两处结构，样式由 CSS 切换：

1. **案号行** `.doc-format-caseno`：取案件案号，插到标题（h1/h2）之后；无标题则置顶；案号为空不插。
2. **落款签章区** `.doc-format-sign`：追加到文书末尾——「审判员/检察员/复议机关　张XX」「书记员　王XX」、中文落款日期（二〇二六年九月十日）、红色圆形「院印」占位。
3. **样式切换**：标题居中加大（20px/700/字间距 2px）、正文首行缩进 2em、行距 2、宋体（Noto Serif SC / SimSun）；案号行与签章区仅在 `doc-formatted` 下显示（未排版即"后置"）。
4. **幂等**：重复排版（重新排版）不重复插入案号行与签章区；重新排版前二次确认。

### 10.12.5 边界与异常

- 重新生成文书后排版状态重置为「未排版」。
- 无 `result-doc` 包裹的内容自动补一层容器承载排版类。
- 只读模式（管理后台 `?readonly=1`）点击被拦截。
- 排版后内容可直接【保存】到历史文书 / 下载 / 精修，保存的是排版后内容。

# 十一、V1.2.19 管理端用户模板检索（清单第 27 项）

> 本章为 V1.2.19 增量，对应《原型待调整清单-20260909开发对齐》第 27 项。
> 设计过程文档：`docs/原型设计方案-20260910-管理端用户模板检索.md`（v2.0 简化版）

## 11.1 背景与定位

- **原始条目**：用户模板查看——后台仅开放指定用户（法官）检索入口，不做全量展示。
- **用户明确**：admin 账号支持查看所有用户的文书模板、指令、要件；主场景为**推广优秀实践 + 收编官方库**。
- **关键决策（2026-09-10 用户拍板）**：
  - 推广 / 收编动作由管理员**人工完成**（看到好模板 → 手动复制内容 → 到官方库新建公共模板），**系统不提供任何操作按钮**。
  - 砍掉：复制到我的模板 / 下载 / 复制内容 / 设为公共模板 / 推荐到全院 / 转官方库模板 / 审计日志。

  - "不做全量展示" = **不是"打开就展示所有用户模板"，而是按搜索某个法官查看**（搜索驱动，无默认全量列表）。
  - **检索对象 = 法官**（系统主要给法官用）；执行者 = 仅 admin。

## 11.2 页面与交互

- **形态**：新建独立页面 `pages/admin/user-templates.html`（不走弹框，沿用 V1.2.15 教训）。
- **入口**：管理端侧边栏【用户模板检索】（`fa-search`），已挂到 `doc-templates` / `prompt-templates` / `element-presets` 三页；面包屑「首页 / 用户模板检索」。

  1. **搜索区**：法官姓名 / 工号 + 部门筛选 + 搜索 / 重置。
  2. **统计卡 4 张**：建了模板的法官数 · 文书模板总数 · 指令总数 · 要件总数。
  3. **按案由分布**（见 11.4）+ **检索结果**（法官卡片切换 → 三 Tab → 列表 → 右侧抽屉看正文）。

  - 文书模板：名称 · 文书类型 · 案由 · 字数 · 更新时间 · 状态
  - 指令：名称 · 适用文书类型 · 字数 · 更新时间
  - 要件：名称 · 案由 · 关键词 · 更新时间

## 11.4 分布统计与缺口识别（双维度 · v2.1 修正）

> 用户原话："加个按案由分布吧，如果有有些案由我没有官方的标准的模板，可以用法官自己的。"
> **v2.1 修正**：初版做成"模板按案由分布"是**错误的**。用户核对现有功能后指出——模板与指令按**文书类型**建，文书类型上才定义"适配案由"。

### 11.4.1 数据模型（关键）

| 对象 | 组织维度 | 依据 |
| :--- | :--- | :--- |
| 文书模板 | **文书类型**（本身不绑案由） | `case-data.js:9` "v1.33 文书模板移除 causes 字段" |
| 指令 | **文书类型**（可设"通用"） | 同上 |
| 要件 | **案由** | `myElementPresetsByCause` 按案由索引 |
| 文书类型 | 含 `causes`（匹配案由）+ `caseWords` | `case-data.js:284`、`admin-doc-types.js:363` |

**即：模板/指令 → 挂在文书类型下；案由由文书类型承载。**

### 11.4.2 分布区两个子 Tab

- **按文书类型（模板 / 指令）**：`文书类型 · 匹配案由 · 官方模板数 · 法官模板数 · 法官指令数 · 涉及法官 · 状态`
  - 缺口 = `官方模板数 0 且（法官模板 + 法官指令）> 0` → 行高亮 +「无官方模板 · 可收编」
  - **"通用"指令不参与缺口判定**（不限文书类型），官方列显示"—"，状态显示「通用指令」
- **按案由（要件）**：`案由 · 官方要件数 · 法官要件数 · 涉及法官 · 状态`
  - 缺口 = `官方要件数 0 且 法官要件数 > 0` →「无官方要件 · 可收编」

两者均：**缺口排最前**，涉及法官标签可点击跳转检索。

### 11.4.3 交互细节（v2.2）

- **涉及法官列**：只显示「N 名」（可点击），点击弹层列出法官名单（姓名 + 部门 + 工号），点某法官跳转其检索结果。0 名显示"—"。—— 避免 20 名法官时该列撑爆表格。
- **分页**：分布表**每页 10 条**，底部 `共 N 条 · 第 x / y 页` + 上一页 / 下一页；页码越界收敛；≤10 条不显示翻页；切换维度重置到第 1 页。
- **搜索区并入检索面板**：顶部搜索行 + 提示语 + 下方结果区在同一面板，消除割裂。

### 11.4.4 字段澄清：要件 `caseWords` =「适用案字」

- **不是"关键词"**。业务含义为**案号代字（案字）**，决定要件适用哪类案件编号。
- 依据：`admin-element-presets.js:407` 注释「适用案字标签」；`case-data.js:953` 案字全集 `['民初','民终','民再','刑初','刑终','刑再','行初','行终','执','赔','监']`；`case-data.js:962` 民事案由→民初/民终/民再，刑事案由→刑初/刑终/刑再。
- UI 列名与抽屉标签统一为「适用案字」。

覆盖表三套：`DOC_TYPE_CAUSES`（文书类型→匹配案由）、`OFFICIAL_DOCTYPE_COVERAGE`（文书类型→官方模板数）、`OFFICIAL_ELEMENT_CAUSE_COVERAGE`（案由→官方要件数）。真接入由后端按维度聚合。

## 10.14 V1.2.25 法条确认规则变更：已勾选即视为已确认

> 对应《原型待调整清单-20260911》第 6 项。
> ⚠️ **本条是对 V1.2.4「全部文书类型均需先经法条确认」的规则变更**，在此明确登记，非静默调整。

### 10.14.1 变更内容

**原规则（V1.2.4）**：任何文书类型生成前，一律先打开「本案法条」抽屉确认，未确认不得进入文书渲染。

**新规则（V1.2.25）**：

| 情形 | 行为 |
| :--- | :--- |
| **已勾选法条 ≥ 1 条** | **直接沿用已勾选法条、不再弹抽屉**，直接进入文书生成 |
| **已勾选法条 = 0 条** | 仍弹「本案法条」抽屉，由用户勾选确认（保持现状） |

- **判定依据**：**勾选状态本身即代表确认**，不额外要求 `caseLawsState.confirmed` 标记为 true
- **落地方式**：抽统一入口 `proceedToGenerateWithLaws(callback)`，4 处生成前调用点（一步生成·有要件 / 一步生成·无要件 / 列表页快捷生成 / 分步生成最终编译）统一改走它

### 10.14.2 与既有规则的关系

- **保留**：法条仍是"生成文书前必须确认"的环节——只是"已勾选"即视为确认完成，不再重复弹窗打断
- **不变**：V1.2.9 的「AI 推荐法条默认全不选」——因此**默认流程（用户未主动勾选）仍会弹一次抽屉**，只有用户主动勾过法条的案件才会跳过，符合预期
- **保留路径**：`打开抽屉 → 勾选 → 点【确认法条并生成文书】` 仍完整可用（零勾选时进入）
- **徽标同步（V1.2.25 补充修订）**：页面顶部右侧「本案法条」入口的**状态徽标判定同步改为按勾选数**——勾选 ≥ 1 条 → 「已确认 N 条」（绿）；一条未勾 → 「待确认」（橙）。原判定要求 `caseLawsState.confirmed`（即必须点过【确认法条并生成文书】），会出现"**徽标显示待确认、生成时却不弹抽屉**"的界面自相矛盾。详见 10.11

## 12.7 边界与异常 case

1. **案件无材料**：空态显示「本案暂无可检索材料，请先上传」，输入框置灰不可发送

3. **文书生成流式输出中**：AI问答与文书生成**互不阻塞**（不同视图，各自独立）
4. **切走再切回**：对话记录保留（内存），滚动位置回到底部
5. **超长输入**：沿用现有输入框的 maxlength 限制
6. **回答生成中再次发送**：发送按钮置灰，防止并发提问
7. **未生成文书**：不影响提问（与文书精修的核心差异点）
8. **重复点击【存入本案要件】**（V1.2.25）：已存入的回答按钮置为「已存入」态，不重复新建
9. **存入时与已有要件重名**（V1.2.25）：要件答案以「要件名」为索引（`caseElementsAnswers[name]`），**重名会覆盖已有答案**——因此存入时若检测到同名要件，**自动追加序号后缀**（如「本案的争议焦点是什么（2）」）后再新建，避免覆盖
