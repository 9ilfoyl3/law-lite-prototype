### 为什么砍掉操作（用户原话）

> "那些功能按钮没有必要，我完全可以因为你的好用，自己复制一下，作为公共模板就行了。推荐到全院用户侧也没有这个入口。转为官方库模板也是一个复制的操作，没有必要加这几个按钮。其实就是一个数据统计可以查看的功能就可以了。"

**结论**：
- 推广 / 收编动作由管理员**人工完成**（看到好的 → 手动复制内容 → 自己到官方库新建公共模板），系统不提供按钮。
- "推荐到全院"在用户侧无入口，功能本不存在，砍掉。
- 无写操作 → 无审计必要 → 审计日志砍掉。
- 页面定位：**查看 + 统计**，不做任何写操作。

### 需求要点（用户口径确认）

| 项 | 结论 |
| :--- | :--- |
| 主场景 | **推广优秀实践 + 收编官方库**（由人工复制完成，系统不做） |
| 系统定位 | **数据统计 + 只读查看** |
| "不做全量展示"释义 | **不是"打开就展示所有用户模板"**，而是**按搜索某个法官**看他的模板 / 指令 / 要件（搜索驱动，无默认全量列表） |
| 检索对象 | **法官**（系统主要给法官用） |
| 检索执行者 | 仅 admin 可见入口 |

### 1.3 关键交互

| 交互 | 设计 |
| :--- | :--- |
| **默认态** | 仅搜索框 + 统计卡；结果区空态"输入法官姓名开始检索"——**不展示任何用户列表**（守住"不做全量展示"） |
| **搜索** | 按法官姓名 / 工号模糊匹配；可选部门下拉过滤。命中多个 → 结果区顶部横向列出法官卡片供切换 |
| **切换法官** | 更新 Tab 计数并重载列表 |
| **查看详情** | 点击行 → **右侧抽屉**展示正文（长文本用抽屉而非行内展开，避免撑爆表格；短内容同样走抽屉，保持一致） |
| **三 Tab** | 各自渲染（模板 / 指令 / 要件数据结构差异大，不硬凑共用表格） |
| **只读** | 全文展示，**无编辑、无复制按钮**（选中文本由浏览器右键菜单完成，系统不提供） |

### 1.4 分布统计：双维度（v2.1 修正）

> **修正说明**：v2.0 曾设计"按案由分布"，是**基于假设的错误设计**。用户实地核对现有功能后指出：模板与指令是**依据文书类型**建的，文书类型上才定义"适配案由"。代码印证（`js/case-data.js:284` 文书类型含 `causes`；`case-data.js:9` "v1.33 文书模板移除 causes 字段"）。故 v2.0 在 mock 里给模板加 `cause` 是凭空造了系统不存在的字段，v2.1 已删除。

**正确的数据模型**：

| 对象 | 组织维度 | 说明 |
| :--- | :--- | :--- |
| 文书模板 | **文书类型** | 挂在文书类型下，本身**不**关联案由 |
| 指令 | **文书类型** | 同上（可设为"通用"= 不限类型） |
| 要件 | **案由** | `myElementPresetsByCause` 按案由索引 |

**因此分布区做两个子 Tab**：

- **按文书类型（模板 / 指令）**：`文书类型 · 匹配案由 · 官方模板数 · 法官模板数 · 法官指令数 · 涉及法官 · 状态`
  - 缺口 = 该文书类型官方模板数 0，但法官自建模板或指令 > 0
  - **"通用"指令不参与缺口判定**（不限文书类型，不存在"该类型缺模板"的说法），状态列显示「通用指令」
- **按案由（要件）**：`案由 · 官方要件数 · 法官要件数 · 涉及法官 · 状态`
  - 缺口 = 该案由官方要件数 0，但法官自建 > 0

**其余统计**：

- **全院汇总（顶部 4 卡）**：建了模板的法官数 · 模板总数 · 指令总数 · 要件总数
- **单法官（结果区头部）**：`模板 N · 指令 N · 要件 N`

> 近 30 天新增等时间维度本期不做。

### 1.5 交互细节（v2.2 优化）

#### 1.5.1 涉及法官：显示数量，点击查名单

- **问题**：直接罗列法官标签，涉及 20 名法官时该列撑爆、页面不可用。
- **方案**：单元格只显示「N 名」（可点击），点击弹出居中弹层列出全部法官（姓名 + 部门 + 工号），点某法官即跳到其检索结果。
- 0 名时显示「—」，不可点。ESC / 点遮罩 / 点关闭按钮均可退出。

#### 1.5.2 分布表分页

- 文书类型、案由后续可能很多，单页放不下。
- **每页 10 条**，底部右侧分页控件：`共 N 条 · 第 x / y 页` + 上一页 / 下一页。
- 页码越界自动收敛；≤10 条时不显示翻页按钮，仅显示总数。
- 切换分布维度（文书类型 ⇄ 案由）时重置到第 1 页。

#### 1.5.3 搜索区并入检索结果面板

- 原「检索法官」是独立面板，与「检索结果」分离，视觉割裂且占垂直空间。
- **合并为一个面板**：搜索行（姓名/工号 + 部门 + 搜索/重置）→ 提示语 → 结果区（法官卡片 → Tab → 表格）。
- 页面顺序：统计卡 → 分布统计 → 检索面板。

#### 1.5.4 字段澄清：要件的 `caseWords` =「适用案字」

- **不是"关键词"**。该字段业务含义是**案号中的代字（案字）**，决定要件适用于哪类案件编号。
- 依据：`js/admin-element-presets.js:407` 注释「适用案字标签」；`case-data.js:953` 案字全集 `['民初','民终','民再','刑初','刑终','刑再','行初','行终','执','赔','监']`；`case-data.js:962` 民事案由→民初/民终/民再，刑事案由→刑初/刑终/刑再。
- **UI 列名与抽屉标签统一改为「适用案字」**（v2.1 曾误写为"关键词"）。
- mock 值已按案由大类重写：民事要件→`['民初','民终']`，刑事→`['刑初','刑终']`，行政→`['行初','行终']`。

## 二、数据层（落地关键）

### 2.1 现状（问题）

localStorage 只存**当前浏览器用户**一份数据，没有"多用户"概念：

| Key | 结构 |
| :--- | :--- |
| `myDocTemplates` | `{ [org]: { [类目]: { name, docType, content, ... }[] } }` |
| `myPromptTemplates` | `{ [org]: { [typeKey]: { name, content, ... }[] } }` |
| `myElementPresetsByCause` | `{ [cause]: { name, question, caseWords }[] }` |

**→ 要展示"各法官的模板"，原型必须先造 mock 数据**（唯一落地阻塞点）。

### 2.2 需要新增的 mock

在 `js/case-data.js` 或新建 `js/mock-user-templates.js` 中补充：

```js
// 虚拟法官用户（与 adminDepartments / adminUsers 对齐）
const MOCK_JUDGE_TEMPLATES = {
  '王法官': { dept: '民一庭', employeeNo: 'F001',
              templates: [...], prompts: [...], elements: [...] },
  '李法官': { dept: '民一庭', employeeNo: 'F002', ... },
  '张法官': { dept: '民二庭', employeeNo: 'F003', ... },
  // 建议 6-8 名法官，覆盖 3-4 个庭室，每人 2-8 条物料
};
```

- 物料内容复用现有"我的模板 / 指令 / 要件"的示例正文（如 `js/my-templates.js` 里的判决书模板）。
- 保证真实感：模板带 docType / 案由，要件带 question / caseWords。

### 2.3 真接口契约（预留，本期不接）

```
GET /api/admin/judges?q=&dept=&page=&size=        # 法官检索
GET /api/admin/judges/:id/stats                   # 单法官统计
GET /api/admin/judges/:id/items?tab=doc|prompt|element
GET /api/admin/stats/overview                     # 全院汇总 4 卡
```

统一返回：
```json
{ "items": [...], "total": 23, "page": 1, "size": 20 }
```
