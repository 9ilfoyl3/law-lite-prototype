# 计算器功能方案（v1）

> 状态：方案定稿，待编码。本方案为描述"计算器=独立要点，只维护因子（要件，不究格式）+ 公式（规则），让模型算，输出非结构化文本（值+缺失提示）"的落地设计。

---

## 一、背景与定位

计算器是一种**独立要件类型**，与"本案要件""案由要件"平级，挂案件详情页独立抽屉。

与现有要件的本质区别：
- 本案要件 = **提取**（从材料中抽取答案）
- 计算器 = **计算**（基于因子+公式，由模型推算出新值）

核心思想：不在前端写死 JS 计算逻辑，而是维护"因子 + 公式规则文本"，交给模型计算，输出非结构化文本（含计算值与缺失提示）。

---

## 二、核心概念映射

| 描述 | 落地实现 |
|---------|---------|
| 独立要点 | 案件详情页独立抽屉，与本案要件/案由要件平级 |
| 因子（要件，不究格式） | `{名称, 值, 说明}`，值统一字符串，不做类型/格式校验。**管理员在后台维护因子清单，用户在案件页只填值** |
| 公式（规则） | 规则文本（如"依据《民法典》第585条…"），不写死 JS 计算逻辑。**管理员在后台维护，用户侧只读** |
| 让模型算 | 调用模型，输入"因子清单 + 公式规则"，输出计算文本 |
| 输出非结构化文本 | 自然语言文本，含计算值 + 缺失因子提示 |

### 闭环关系（与要件管理对齐）
| 角色 | 维护内容 | 维护位置 |
|------|---------|---------|
| 管理员 | 因子清单 + 公式规则 | 管理后台 `admin-calculators.html` |
| 用户 | 因子值（手填/材料提取/引用要件）| 案件详情页计算器抽屉 |
| 系统 | 计算执行 + 结果输出 | 案件详情页计算器抽屉 |

> 与要件管理完全对齐：管理员维护"要件（因子）+ 问题（公式）"，用户在案件页填答案（值），系统调用模型抽取/计算。计算器的"公式"对应要件的"问题"，都是管理员维护、用户侧只读。

## 五、内置计算器（原型阶段 2 个）

### 1. 逾期违约金/利息计算
- **因子**：债务金额、利率类型（日/月/年利率）、约定利率、开始时间、结束时间
- **公式规则**：逾期违约金=债务金额×逾期期间×约定利率（日/月/年）；年利率=12×月利率=360×日利率。缺失结束时间时按当前日期估算并标注。
- **说明**：与常见利息计算工具保持一致，输出逾期违约金金额和逾期天数。

### 2. 诉讼费计算
- **因子**：案件类型（民事/行政/执行/海事，财产/非财产分类）、诉讼标的额、审理程序（一审/二审/再审）、减半情形（是否适用简易程序/调解结案/撤诉）
- **公式规则**：依据《诉讼费用交纳办法》第13条，财产案件按标的额分段累计（1万以下50元；1-10万2.5%；10-20万2%；20-50万1.5%；50-100万1%；100-200万0.9%；200-500万0.8%；500-1000万0.7%；1000万以上0.5%）。属于简易程序、调解结案或撤诉的，减半收取。

### 3. 未来可扩展：约定违约金计算（暂不实现）
- **因子**：合同金额、约定违约金比例/数额、实际损失、违约起算日、计算截止日
- **公式规则**：依据《民法典》第585条，违约金按约定计算；约定过高（超实际损失30%）提示可申请调整；约定过低可请求增加；缺失实际损失时按约定比例估算并标注。

## 六、交互流程

1. 点【计算器】→ 抽屉滑入，左列表显示内置+自定义计算器
2. 点左列表某项 → 右侧加载其因子表/公式/历史结果
3. 填因子值（三种来源）：
   - **手填**：直接在因子表值列输入
   - **从材料提取**：点因子行【从材料提取】→ 关键词匹配 mock（遍历材料文件名+解析文本，查含因子名称关键词的材料，找到则抽取附近数字作值）
   - **引用要件**：点因子行【引用要件】→ 下拉选本案要件已答的答案（联动 `localStorage.caseElements_${caseId}`）
4. 点【开始计算】→ 模型基于"因子清单+公式"计算 → 结果区流式输出文本（含值+缺失提示，每段 500-900ms，约 3 秒）
5. 结果展示后：
   - 勾选【注入文书生成】→ 该结果文本作为生成依据传给 `generateByMaterial`
   - 历史记录追加一条（可查看/回填/删除）
6. 内置计算器不可删除，自定义计算器可删除

## 七、细化细节（8 项）

### 1. 因子来源设置方式
因子来源**不是**在管理后台预先配置的，而是在案件详情页使用计算器时，由用户针对每个因子逐行选择。来源表示"本次计算中，这个因子的值从哪来"。

三种来源及用户操作：

| 来源 | 用户操作 | 效果 |
|------|---------|------|
| 手填 | 直接在因子表"值"列输入框打字 | `source: 'manual'` |
| 材料提取 | 点因子行【从材料提取】按钮 | 系统从案件材料中关键词匹配抽取，`source: 'extracted'` |
| 引用要件 | 点因子行【引用要件】按钮 | 下拉选择本案要件已填答案，`source: 'element'` |

因子表列设计：
- 列：名称 | 值 | 来源 | 操作
- 内置因子名称只读，自定义因子可编辑；值统一为字符串（不究格式）
- 来源标签三色：手填（灰）/ 材料提取（蓝）/ 要件引用（绿）
- 操作：从材料提取 · 引用要件 · 清空

示例：
```
名称            值           来源            操作
─────────────────────────────────────────────────────
债务金额        22222        [手填]          提取 · 引用 · 清空
利率类型        日利率        [手填]          提取 · 引用 · 清空
约定利率        0.02         [手填]          提取 · 引用 · 清空
开始时间        2026-08-04   [材料提取]      提取 · 引用 · 清空
结束时间        2026-08-11   [手填]          提取 · 引用 · 清空
```

注意：管理员配置公式时**只定义因子名称和说明**，不配置来源。同一案件多次计算时，每次都可以重新选择来源；历史记录会保存当时的因子快照。

### 2. 引用要件交互
- 点因子行【引用要件】→ 下拉列出本案要件已答清单（读 `localStorage.caseElements_${caseId}`）
- 选中 → 因子值=要件答案，来源标"要件引用"，记录 `fromElement`
- 要件答案后续更新，因子值不自动同步（避免破坏已算结果），显示"要件已更新"小标

### 3. 从材料提取（关键词匹配 mock）
- 点【从材料提取】→ 遍历材料文件名+解析文本，查含因子名称关键词的材料
- mock：找到则抽取附近数字作值；找不到提示"未在材料中找到 XX"
- 提取后填值，来源标"材料提取"

### 4. 历史记录回填
- 折叠在结果区下方，每条：时间 + 结果摘要 + 【回填】【删除】
- 【回填】：结果文本 + 因子快照覆盖当前
- 【删除】：移除该条（参照本案要件优化历史管理 UI）

### 5. + 自定义计算器
- 点【+自定义】→ 右侧切换新建表单
- 填：名称、因子列表（可增删行）、公式规则文本（textarea）
- 保存后追加左列表，存 localStorage

### 6. 结果流式输出
- 参照文书生成流式效果（每段 500-900ms，整体约 3 秒）
- 输出期间【开始计算】【注入文书】禁用，结束后恢复

### 7. 注入文书拼接
- `generateByMaterial` 前收集 `injectToDoc=true` 的计算器结果
- 拼接为"【计算结果】逾期违约金：… 诉讼费：…"文本，作为生成上下文一部分（与要件答案并列）
- 生成确认弹框展示"已注入计算器结果"区，可编辑/移除

### 8. 状态徽章与边界
- 左列表圆点：绿（已算无缺失）/ 黄（已算有缺失）/ 灰（未算）
- 顶部【计算器】按钮徽章：已注入文书的计算器数
- 无计算器 → 右详情空状态；因子全缺 → 计算不阻断，结果标注全缺失
- 自定义无因子 → 提示"请添加至少一个因子"
- 与本案要件抽屉独立，可同时打开

## 八、与文书生成的注入关系

- **注入触发**：用户在抽屉内勾选【注入文书生成】
- **注入形态**：文本（如"违约金约 30000 元（实际损失缺失，按约定比例30%估算）"）
- **注入位置**：与本案要件答案并列，作为另一种生成依据，拼接到生成上下文的"计算结果"段
- **生成配置页**：在生成确认弹框中追加"已注入计算器结果"区，展示勾选注入的计算器结果文本（可编辑/移除）
- **缺失提示**：一并注入，让模型在文书中体现不确定性

## 九、管理后台计算器管理模块（核心闭环，与要件管理对齐）

> 与现有「要件管理」（`admin-element-presets.html`）保持一致的设计风格和数据分层架构。管理员维护因子清单 + 公式规则，用户侧只能使用不能创建内置计算器。

### 设计原则
- **闭环要求**：因子和公式由管理员在后台维护，用户在案件详情页只能选/填因子值、触发计算，不能创建或修改内置计算器的公式
- **与要件管理对齐**：UI 风格、数据分层、启用/停用、内置可编辑另存为自定义覆盖等机制完全复用
- **原型阶段范围**：先实现页面 + 内置数据展示 + CRUD，数据源仍写死在 `js/case-data.js`，后续逐步迁移到 localStorage

### 表格字段（与要件管理表格风格一致）
- 名称（含"内置/自定义"徽章）
- 因子数
- 适用案由（多选标签，可选，不选=全部适用）
- 状态（启用/停用切换按钮）
- 操作：编辑 / 删除（内置不可删除）

### 编辑弹框字段
- 名称
- 因子列表（可增删行，每行：因子名称 + 说明 + 是否必填）
- 公式规则文本（textarea，大文本框）
- 适用案由（多选，来自 `causeTreeDataByOrg`）
- 状态（启用/停用）

### 数据分层（与要件管理一致）
| 层级 | 存储位置 | 说明 |
|------|---------|------|
| 系统内置 | `js/case-data.js` 的 `builtinCalculators` | 写死的默认公式 |
| 管理员覆盖 | `localStorage.adminCalculators` | 管理员编辑内置/新增自定义后持久化 |
| 运行时合并 | `getAvailableCalculators(org, cause)` | 系统内置 + 管理员覆盖合并，跳过 `enabled===false` |

### 启用/停用机制
- 停用后用户侧计算器抽屉不展示该计算器
- 内置计算器停用 = 生成 `enabled: false` 的覆盖对象（与文档类型/要件启停逻辑一致）
- 重新启用保留现有覆盖，不恢复内置默认

### 用户侧使用流程（闭环）
1. 管理员在 `admin-calculators.html` 配置计算器（因子 + 公式）
2. 用户在案件详情页打开计算器抽屉
3. 抽屉从 `getAvailableCalculators(org, cause)` 加载可用计算器
4. 用户选择计算器 → 系统加载该计算器的因子清单和公式规则
5. 用户填因子值（手填/材料提取/引用要件）→ 点【开始计算】
6. 模型基于"因子值 + 公式规则"计算 → 输出非结构化文本（值 + 缺失提示）
7. 可选勾选【注入文书生成】→ 结果作为生成依据注入

### 用户侧自定义计算器（保留）
- 用户仍可在抽屉内【+自定义】创建仅本人可见的计算器，存 `localStorage.myCalculators`
- 与管理后台的计算器分层合并展示（参照 my-templates 与 admin-doc-templates 的关系）

### 菜单入口
- 管理后台侧边栏「案件配置」分组下新增「计算器管理」菜单项
- 排序位于「要件管理」之后、「文书示例管理」之前

## 十一、与描述的对应确认

| 描述 | 方案对应 |
|---------|---------|
| 计算器=独立要点 | 案件详情页独立抽屉，与本案要件平级 |
| 只维护因子（要件，不究格式） | 因子 = `{名称, 值, 说明}`，值字符串不究格式 |
| 公式（规则） | 公式 = 规则文本，不写死 JS 计算逻辑 |
| 让模型算 | 调用模型，输入因子+公式，输出计算文本 |
| 输出非结构化文本（值+缺失提示） | 结果文本含计算值 + 缺失因子提示 |
