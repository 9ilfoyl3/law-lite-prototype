### 5.1.1 改造前后对比

```
【改造前】
案件(案由+案字) → 文书类型(下拉) → 系统唯一匹配 workflow → 示例(类型下全量平铺) + 指令(类型下)
问题：类型到流程必须一对一 → 同案由案字下的多流程场景建不进去（民终有维持/改判/新证据，
      民再裁定有五种）；示例停在类型粒度，一审/二审/维持/改判混在同一个下拉里

【改造后】
案件(案由+案字) → workflow 平铺(卡片单选, 按案由案字过滤后约 8 个)
                     → 示例/指令(系统预设按所选 workflow 过滤 + 通用 + 我的平铺)
                     ↘ 未选专属流程时走「通用兜底 workflow」（仅一步生成）
```

一句话概括：**三条配置链（workflow / 示例 / 指令）合一，workflow 是唯一关联节点**。系统预设示例、指令挂 workflow；用户自建内容谁都不挂，只挂归属人。

### 5.1.2 四项核心口径（本版定稿）

| # | 口径 | 说明 |
| :-- | :--- | :--- |
| 1 | **文书类型隐藏不删** | 导航下线、`adminDocTypes` 数据保留不读、代码与页面保留。理由：流程数量超阈值做级联分组时，类型可直接复用为一级分组，不推倒重来（见 5.3） |
| 2 | **workflow 名称即用户端卡片标题，必须业务化** | 命名规范 `文书名（审级·方向）`，如「民事判决书（二审·改判）」。用户侧不出现「workflow / 流程配置」等技术词；另配可选的「流程说明」一句话作卡片副标题（见 5.2） |
| 3 | **通用兜底流程仅一步生成出现** | 分步生成是精细化编排链路，限定裁判文书类 workflow，不需要兜底；通用兜底只解决「现场临时自由生成」，该需求只存在于一步生成（见 5.5） |
| 4 | **存量数据零迁移** | 新增字段缺省即通用（`workflowIds: []` = 通用），旧字段（`docType`、旧对象结构 workflow）保留不读；运行时兜底排在最后一次 `initCaseData()` 之后（见 5.10.1） |

## 5.2 管理后台 · workflow 配置（解除唯一校验 + 独立管理）

> 对应待办 A2。落 PRD 日期 2026-09-19；下游归口：管理后台PRD 4.11.7。

### 5.2.1 为什么必须改（决策依据）

方案一去掉文书类型后，workflow 成为**唯一关联节点**，原「workflow 挂在文书类型下」的嵌套结构必须解绑——否则文书类型模块隐藏（见 5.3）后，管理员没有任何入口能配到 workflow。

会议决策②同时要求解除「相同案由案字下仅允许配置唯一 workflow」的限制：同案由案字下多流程是真实场景（民终有维持/改判/新证据，民再裁定有五种），唯一性限制直接卡死现场配置。

**两个实现方式已由用户拍板（2026-09-19）**：
1. **新建独立管理页 + 扁平存储**（而非沿用嵌套存储只改 UI）——彻底解绑文书类型，用户侧平铺（5.6）可直接复用。
2. **预置分步型内置 workflow**（而非分步 tab 保持现状）——两个 tab 交互语义一致，符合方案设计 4.2。

### 5.2.2 存储结构：扁平化 + 零迁移

```js
// localStorage.adminWorkflows 新结构（按业务系统分组，值为数组）
{
    court: [
        { id: 'wf-judgment-1st', name: '民事判决书（一审）', type: 'step',
          caseWords: ['民初'], causes: [], description: '…', isBuiltin: true }
    ]
}

// 旧结构（值为对象，按 docTypeKey 分组）——继续可读，不迁移
{ court: { judgment: [ {...} ], trial: [ {...} ] } }
```

**读取兼容规则**（`readStoredWorkflows(org)`）：值为**数组** → 直接使用；值为**对象** → 展平其全部 value 数组并按 `id` 去重；两者都没有 → 返回内置列表。

**写入规则**：首次保存时把当前内置 workflow 全量迁入数组再操作（沿用现有「自定义整体覆盖内置」语义）；删除全部自定义项即恢复内置。旧页 `admin-doc-types.js` / `doc-types.html` 代码保留不动，仍按对象结构读写，与新路径互不干扰。

### 5.2.3 数据结构

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `id` | string | 是 | 来自 agentflow 平台下拉选择；**同一 org 内唯一**（原「同一 docType 内唯一」） |
| `name` | string | 是 | 业务化命名，规范 `文书名（审级·方向）`；用户端卡片标题直接用此值 |
| `type` | `'quick'` \| `'material'` \| `'step'` | 是 | 快速生成型 / 材料生成型 / 分步生成型，三选一，见 5.2.7 |
| `caseWords` | string[] | 是 | 匹配案字，空数组 = 兜底 |
| `causes` | string[] | 是 | 匹配案由，空数组 = 兜底 |
| `description` | string | 否 | **新增**：流程说明（一句话），展示在用户端卡片副标题 |
| `isBuiltin` | boolean | — | 内置标记 |
| `isGeneral` | boolean | 否 | 通用兜底流程标记，见 5.5 |

### 5.2.4 校验规则变更（核心：解除唯一性）

| 校验项 | 旧行为 | 新行为 |
| :--- | :--- | :--- |
| 案字冲突（同类型其他 workflow 已占用该案字） | 拦截报错，无法保存 | **解除**；选择器保留 ⚠ 标记作信息提示，仍可勾选保存 |
| 案由冲突（同类型其他 workflow 已占用该案由） | 拦截报错，无法保存 | **解除**；同上 |
| 全兜底唯一（同类型内 `caseWords`+`causes` 均空最多 1 个） | 拦截报错 | **解除** |
| 删除保护（同类型仅剩 1 个一步生成型时禁止删除） | 拦截 | **解除** |
| workflow id 同 org 内唯一 | 拦截报错 | **保留**（id 重复会导致流程无法区分） |
| id 必选 / 名称非空 | 拦截报错 | **保留** |

**新增轻提示**：保存成功后，若该（案字 + 案由 + 生成模式）组合下已有 N > 1 个流程，toast 提示「该案由案字下已有 N 个流程，用户端将并列展示」。提示不阻断。

**生成模式口径（V1.3.9 A15 起）**：新增 workflow 时由管理员在**快速生成型 / 材料生成型 / 分步生成型**中三选一；编辑已有 workflow 时回填原值、保存后保持原类型。详见 5.2.7。

> 该口径取代 V1.3.0~V1.3.8 的「新增固定一步生成型」（见 5.12 口径变更记录）。

### 5.2.9 分步型流程「编辑环节」入口（V1.3.12 A18，只读展示）

> 落 PRD 日期 2026-09-20。用户反馈：管理后台缺少「编辑环节」操作入口（参考编排端截图：分步流程列表每行都有该入口）。

#### 一、入口规则

操作列在**分步生成型**流程行新增「编辑环节」按钮（材料生成型 / 快速生成型不显示——它们没有环节概念）。点击弹出环节弹窗，**只读展示**该流程在 AgentFlow 编排端的环节编排结果。

按钮命名为「编辑环节」而非「查看环节」，是为与编排端界面保持一致（管理员认知中这个入口就叫编辑环节）；弹窗内明确标注只读及原因。

#### 二、弹窗内容（只读）

按编排端截图还原的信息结构，逐环节展示：

| 展示项 | 说明 |
| :--- | :--- |
| 序号 | 环节执行顺序 |
| 环节名称 | 如「原审查明认定」「争议焦点」 |
| 子流程编码 | 平台上对应的子 workflow id（如 `wf_SE3GixHj`）；手动环节显示「手动填写，无外部流程」 |
| 入参 / 出参 | 参数数量 |
| 依赖 | 「依赖 N 个前置环节」，无依赖则不显示 |
| 产出文书 | 末位环节标记「产出文书」 |

弹窗底部固定提示：**环节编排在 AgentFlow 编排端维护，此处只读展示**；并提供「在编排端打开」的说明性提示（原型不实际跳转）。

#### 三、数据说明（原型 mock）

环节数据属**编排端数据**，原型不可能真实同步，故在 `js/admin-workflows.js` 内置 mock（未写入 `case-data.js`，不影响用户侧加载链路）：

- `wf-judgment-2nd`（二审）：采用用户提供的编排端截图**真实数据**，7 个环节（原审查明认定 → 上诉人诉讼 → 被上诉人抗辩 → 争议焦点 → 再审认定 → 裁判结果（手动）→ 文书生成）。
- `wf-judgment-1st`（一审）：**原型 mock**（按二审结构推导的一审语义环节名），弹窗内标注「原型示例数据」。
- 其余分步流程（含再审、管理员自建的分步型）：无环节数据 → 弹窗显示空态「该流程尚未在编排端配置环节」，并提示去编排端配置。

> **环节与步骤的对应关系（用户 2026-09-20 澄清）**：编排端的「环节」与用户侧分步 tab 的「步骤」，在**实际系统中是一一对应**的——编排端配了 N 个环节，法官在分步生成中就按这 N 个环节逐步填写/确认，末位环节产出文书。
> **本原型不做两者的数据联动**（环节 mock 只在管理端弹窗只读展示，用户侧分步 tab 仍按内置步骤配置渲染），这是原型保真度取舍，不是产品口径：演示时讲的是「编排端怎么配、法官就怎么填」，无需解释两套口径的差异。正式版实现时，环节序列即步骤序列。

#### 四、验收要点

1. 材料生成型 / 快速生成型流程行**不出现**「编辑环节」按钮；分步生成型行出现。
2. 点击二审流程「编辑环节」→ 弹窗展示 7 个环节，含子流程编码、入参/出参、依赖、末位「产出文书」。
3. 手动环节（裁判结果）显示为「手动填写，无外部流程」。
4. 点击一审流程 → 展示 mock 环节，并标注「原型示例数据」。
5. 点击再审流程或自建分步流程 → 空态「该流程尚未在编排端配置环节」。
6. 弹窗底部有只读说明；弹窗内**无任何**新增/删除/保存控件（只读）。
7. 环节数据不写入 `localStorage.adminWorkflows`，刷新后流程数据不受影响。

### 5.2.11 要件管理「来源」列删除（V1.3.15 A21）

> 落 PRD 日期 2026-09-20。用户反馈：要件管理表格的「来源」字段没必要，隐藏。

#### 一、为什么是整列删除，而不是隐藏内置标签

与 A17（workflow）、A20（示例 / 指令）不同，本项**删除整列**（表头 + 单元格），理由有三：

1. **同一案由下该列取值必然相同**。`getEffectiveElements()` 的覆盖语义是**整体的**——`adminElementPresets[org][cause]` 一旦存在即整体覆盖内置，返回项全部 `isBuiltin: false`；否则全部 `true`。不存在"同一列表里内置与自定义混排"的情况。
2. **信息已在页面顶部重复呈现**。右栏副标题 `rightSub` 固定显示「共 N 项 · 内置」或「共 N 项 · 已自定义覆盖」，案由级别的整体来源一目了然，比逐行标注更直接。
3. 因此保留该列只会让每行重复一个与顶部相同的词，属纯冗余。

> 注：这也是本项目「信息是否已在界面上重复呈现」判断原则的一次应用——冗余信息优先删除而非弱化。

#### 二、变更内容

| 文件 | 改动 |
| :--- | :--- |
| `pages/admin/element-presets.html` | 删除表头 `<th style="width:7%;">来源</th>` |
| `js/admin-element-presets.js` | 删除 `badge` 变量与对应 `<td>`；`isBuiltin` 字段与全部依赖逻辑不动 |

#### 三、保留不动的部分

`isBuiltin` 仍被三处逻辑依赖，字段与逻辑一律保留：内置要件**可编辑（另存为自定义）、不可删除**（删除按钮置灰并带 title 说明）、停用内置项时自动生成自定义覆盖数组、顶部「恢复内置」按钮仅在已覆盖时显示。

#### 四、验收要点

1. 表格不再有「来源」列（表头无该文字，每行单元格数比其他页数少 1）。
2. 页面不再出现「内置」/「自定义」徽章文字。
3. 顶部副标题仍显示「共 N 项 · 内置」或「· 已自定义覆盖」。
4. 内置要件的删除按钮仍为置灰态，编辑 / 停用行为不变。

### 5.2.12 管理后台标签口径统一（V1.3.19 A25）

> 落 PRD 日期 2026-09-20。用户追问：管理后台刚隐藏了「内置」标签，那文书示例、文书流程管理里的「自定义」「通用兜底」等标签是不是也要隐藏？

#### 一、判断原则：来源标签 ≠ 适用范围标签

此前 A17／A20／A21 三次"隐藏内置标签"的动作，容易让人以为"标签一律该去"。但管理后台的标签实际分两类，性质不同，不能一刀切：

- **来源标签**（内置／自定义）回答的是"这条是谁建的"。它决定的是操作后果——内置项不可删除、编辑时是"另存为自定义覆盖"。而"内置"是系统默认态，不需要被强调，所以隐藏；隐藏后「自定义」成为与之互补的唯一信号（无标签即内置），故保留。
- **适用范围标签**（通用、通用兜底、案字／案由兜底、生成模式）回答的是"这条在哪生效"。它是**配置语义本身**，不是修饰。删掉之后，管理员无法从列表判断一条配置覆盖哪些流程／案字，只能逐条点开编辑弹窗查看——等于把高频信息降级成低频操作，与 A17 精简列表、A15 增加模式下拉的方向相反。

> 一句话口径：**来源可以弱化（默认态不标），适用范围必须留（配置语义不能藏）。**

#### 二、逐项结论

| 页面 | 标签 | 类别 | 结论 |
| :--- | :--- | :--- | :--- |
| 示例／指令／流程管理 | 内置 | 来源 | **隐藏**（A17／A20 已落地） |
| 示例／指令／流程管理 | 自定义 | 来源 | **隐藏**（V1.3.23 A30 推翻 2026-09-20 拍板：与「内置」同源，"无标签即内置"已足够区分，再标属冗余；且会拖出 96px 透明占位 hack，去除后 CSS 更干净） |
| 示例／指令管理 | 通用（关联流程为空） | 适用范围 | **保留**——对应左栏「通用示例／通用指令」筛选，且决定用户侧可见范围 |
| 流程管理 | 通用兜底 | 适用范围 | **隐藏**（V1.3.23 A30：该流程 isGeneral 且恒在、用户侧一步生成恒定展示，配置上本就是兜底，无需再标；不可删行为不变，仅去视觉标签） |
| 流程管理 | 快速／材料／分步生成型 | 适用范围 | **保留**——A15 新增的核心分类 |
| 流程管理 | 案字／案由「兜底」 | 适用范围 | **保留**——匹配范围，A17 筛选即按此维度 |
| 要件管理 | 案字「通用」 | 适用范围 | **保留** |
| 全部页面 | 已启用／已停用 | 状态 | **保留** |

`pages/admin/element-presets.html` 中的 `.tpl-badge`、`.tpl-badge.builtin`、`.tpl-badge.custom` 三条样式在 A21 删除「来源」列后已无人引用（JS 与页面 DOM 均无使用），本次删除。特别说明：该页 `.tpl-badge.custom` 为黄色 `#fef3c7`，而其他三页为绿色 `#d1fae5`，属历史遗留的反向配色，留着极易被后续改动误用。

## 5.2.16 要件管理 · 删除按钮与状态解耦（V1.3.26 A33）

### 一、问题与根因
用户报 bug：「要件状态都是已启用时，没有删除按钮。停用了一个，才有出现删除按钮。」

要件按**案由级覆盖**建模：某案由的自定义数据（`adminElementPresets[org][cause]`）一旦存在即整体替代内置要件集。删除按钮显隐绑定"该条是否属自定义覆盖"（`getEffectiveElements` 对覆盖项标 `isBuiltin:false`、内置项标 `isBuiltin:true`；renderTable 仅对非内置渲染删除）。于是：

- **纯内置案由**（全启用）：整组 `isBuiltin:true` → 全部无删除按钮；
- **「停用」任意一条内置**：`toggleElementEnabled` 为保留其他编辑，把整组内置拷贝为自定义覆盖（baseline）再置停用标志 → 整组转非内置 → **5 个删除按钮同时出现**。

即删除按钮的可得性被"是否对该案由做过自定义动作"绑架，而非跟随要件条目本身，且「停用」动作顺带触发了整组转正，用户感知为"停用才能删"。

浏览器实测复现（法院 / 民间借贷纠纷，5 条内置全启用）：操作前删除按钮 0 个；`toggleElementEnabled(0)` 后删除按钮 5 个、`hasOverride=true`。

### 二、方案（用户拍板：内置也可删）
**删除按钮每行常驻、恒可用，与启用/停用状态、内置/自定义来源彻底解耦。**

- 点击**自定义要件**的删除：行为不变，直接从覆盖数组移除该条。
- 点击**内置要件**的删除：自动生成该案由自定义覆盖（与「停用」同一 baseline 机制）→ 仅移除该条。通知文案提示已转为自定义覆盖、可经「恢复内置」整组还原。
- 误删兜底：右上角「恢复内置」一键清除该案由覆盖、还原为内置要件集（已有能力，不变）。

与示例/指令页的差异说明：示例/指令的内置项是全局模板（删除影响所有关联流程），保持"内置无删除"；要件的内置是**按案由的标准集**，管理动作本就是"对这组标准做覆盖"，删除一条内置＝覆盖语义的自然组成，二者口径各自成立。

1. `deleteElement`：去掉「内置要件不可删除」拦截；内置且无覆盖时先按 `getEffectiveElements` 生成 baseline 写入覆盖，再 splice 移除目标条；确认弹窗与成功通知对内置路径补充"已转为自定义覆盖，可通过「恢复内置」还原"提示。
2. renderTable：删除按钮不再按 `p.isBuiltin` 分支，每行恒渲染。
3. 顶部 A31 相关注释同步更新。

### 5.2.18 第二批：指令页回归文书类型 + 用户侧恢复类型下拉（V1.3.29 / A36）

**一、为什么数据层要先加一层。** 指令不像示例按 key 分组存储，而是扁平数组 `__items__`，并且存在"物化"机制（首次编辑/停用内置项时把内置整体迁入数组）。如果只是把管理端控件改成类型下拉、写 `docType`，那些**上一批已物化过的历史数据**里只有 `workflowIds`、没有 `docType`，会全部退化成"通用指令"——每条指令在每个类型下都出现。因此先定零迁移解析函数 `resolvePromptDocType(org, item)`，四级优先：① 显式 `docType` 字段（含空串＝通用）→ ② 内置 id 前缀（`judgment#0` 取 `judgment`）→ ③ `workflowIds` 首个流程的 `domain` → ④ 通用。管理端与用户侧共用同一函数，避免两处口径漂移。

**二、数据层改动（`js/case-data.js`）。**

* `getTemplatesByDocType(org, docTypeKey)`：返回系统预设示例（`source !== 'mine'`），命中条件 `(t.docType||'') === docTypeKey || (t.docType||'') === ''`——**通用示例在各类型下均可见**，与管理端示例页左栏口径一致。`我的示例` 仍由 `getMyDocTemplatesFlat` 平铺追加。
* `getReqTemplatesByDocType(org, docTypeKey)`：指令三段合并 —— `__items__`（启用过滤 + `resolvePromptDocType` 命中）、未物化时的内置分组（`defaultRequirementTemplates[org]` 的分组 key 本身就是文书类型 key，直接比 `key === docTypeKey`）、旧版分组数据（沿用 A5 口径视为通用）；`我的指令` 平铺追加。
* `countDocTypeUsage` 补全 `templates` / `prompts` 计数：示例、指令既然已按类型关联，管理端删除类型时就要一并拦截并告知占用数。
* **实现陷阱（实测踩到，勿再犯）**：读"旧版分组指令"不能复用 `getFlatPromptItems`——它是**全量平铺**读取器（为兼容用户侧 `myPromptTemplates`，内部同时并入 `__items__`）。用它当旧数据源会让 `__items__` 里的自定义指令被重复并入一次，且绕过 `docType` 过滤出现在每个类型下。正确做法是新增只读分组 key 的 `getLegacyGroupedPromptItems`。

**三、指令管理页（`js/admin-prompt-templates.js` + `pages/admin/prompt-templates.html`）。** 左栏由「各 workflow」改为「全部 / 通用指令 / 各文书类型」（与示例页同版式）；列表第三列由「关联流程」改为「文书类型」（未指定显示「通用」）；编辑弹窗的**流程多选框改为类型单选下拉**（沿用示例页 `tplDocTypeSelect` 版式，不选＝通用指令）；内置项物化 / 编辑保存 / 历史恢复均写入 `docType`。`workflowIds` 字段继续保留在存储里、界面不再展示也不再读写。

**四、用户侧（`pages/case-files.html` / `js/case-files.js`；`js/cases.js`）。** 三个生成表单**首项均为「文书类型」下拉**（材料生成 `#matDocTypeSelect`、分步生成 `#stepDocTypeSelect`、列表页快速生成 `#genDocType`），位置在案由/案字之上——顺序即语义：先定产出什么文书，再谈案由案字与流程。

* **选项来源**：当前生成方式下**可用流程的 `domain` 并集**（剔除空类型），具名类型按管理端 `getAdminDocTypes` 顺序排列，`通用`排末位。**为什么要并集而不是全量类型**：全量会把"该类型下当前案件根本没有可跑流程"的类型也列出来，用户选完拿到一个空流程下拉，等于让用户自己试错；只列有货的是列表价最低的做法。
* **联动**：切换类型 → 流程下拉按（新类型 + 当前方式 + 案字/案由）重过滤并默认选中第一条 → 示例下拉与指令标签按新类型刷新（该类型 + 通用）。
* **容错沿用 A29**：案由或案字缺失时只剩通用兜底流程，此时类型下拉自然只剩「通用」，原有 hint 文案不变。
* **示例与指令的读取改走文章类型口径**（`getTemplatesByDocType` / `getReqTemplatesByDocType`），不再按 `workflowIds` 过滤——上一批管理端已停止写入 `workflowIds`，继续按它过滤会让所有示例退化为通用、失去筛选能力。

## 5.6 用户侧 · 生成表单 workflow 平铺

> 对应待办 A7。落 PRD 日期 2026-09-19；下游归口：用户侧PRD 生成链路 + `docs/交互说明.md` 生成操作小节。

### 5.6.1 为什么必须改

文书类型从用户侧消失后（5.3 + 方案一），生成链路失去了第一个表单项。原链路是「先选文书类型 → 再选该类型下的示例/指令 → 系统内部按案字案由匹配 workflow」，即 **workflow 对用户不可见、由系统猜**。

这与方案一的核心相悖：workflow 是要作为**核心关联节点**被显式选择的。用户手选流程后，示例与指令才有过滤依据——否则 5.4 改挂 workflow 的数据改造在用户侧无从消费。

### 5.6.2 交互变更

| 项 | 改前 | 改后 |
| :--- | :--- | :--- |
| 一步生成第一个表单项 | 「文书类型」下拉（`matDocType`） | 「生成流程」**平铺卡片单选**（`matWorkflowCards`） |
| 分步生成第一个表单项 | 「文书类型」下拉（`stepDocType`） | 「生成流程」**平铺卡片单选**（`stepWorkflowCards`） |
| 「步骤方案」下拉 | 多 workflow 时出现（`stepPlan`） | **移除**——方案即所选流程本身 |
| 卡片内容 | — | 流程名 + 模式徽标（分步生成 / 一步生成）+ 通用兜底徽标 + 流程说明 |
| 选择方式 | 下拉 | 单击卡片，选中态高亮（蓝边 + 浅蓝底） |
| 默认值 | 第一个文书类型 | 列表第一个流程（一步生成）；分步同理 |

卡片形态而非下拉的理由：流程数量是个位数且带说明文字，平铺可零点击看全，下拉会把说明藏起来。

### 5.6.3 过滤与联动规则

- **一步生成 tab**：展示 `type === 'material'` 的流程；通用兜底流程（5.5）恒定在末尾。
- **分步生成 tab**：展示 `type === 'step'` 的流程（裁判文书类），通用兜底不出现。
- 选中流程后联动刷新：示例下拉、指令标签、模型（只读、由流程 `modelId` 决定）、按钮可用态；案由/案字两列与所选流程无关，仅随本案结构化信息呈现（有值 → 值 + 「来自案件信息」标签，缺失 → 下拉补选；V1.3.22 A29 起替代原「案件阶段」行，见 5.16）。
- **两 tab 的流程选择互相独立**，不再互相同步文书类型；仅同步模板与指令文本。

### 5.6.4 文书类型残留口径

文书类型在用户侧**界面层消失**，但流程实体保留 `domain`（文书域）字段，仅用于三处内部判断，**不暴露给用户**：

1. 分步步骤序列取键（`getStepsConfigForDocTypeWithFallback` 按 domain 查 `stepConfigsByOrg`）
2. 要件自动引入判定（仅 `domain === 'judgment'` 才询问引入案由要件）
3. 历史文书版本的归档键（版本快照同时存 `workflowId` + `workflowName` + 归档用的 domain）

版本快照新增 `workflowId` / `workflowName`；旧版本只有 `docType` 时，恢复配置按 `docType → domain` 反查默认流程（零迁移）。

### 5.6.5 验收要点

1. 一步生成 tab 平铺展示全部一步型流程（含末尾「通用文书生成」），无「文书类型」下拉。
2. 分步生成 tab 平铺展示全部分步型流程，无「文书类型」下拉、无「步骤方案」下拉。
3. 单击卡片 → 选中高亮；示例下拉与指令标签随之变化（见 5.7）。
4. 案由/案字两列按本案识别结果呈现：有值默认填充（值 + 「来自案件信息」标签），缺失显示下拉补选；任一缺失时流程下拉仅保留通用兜底流程（V1.3.22 A29 起替代原「案件阶段」行，见 5.16）。
5. 「生成文书」按钮在已选材料 + 已选流程时可点，未选流程时置灰并提示「请先选择生成流程」。

## 5.7 用户侧 · 示例 / 指令下拉两段式 + 我的内容去绑定

> 对应待办 A8（两段式下拉）与 A9（我的示例 / 我的指令去绑定）。落 PRD 日期 2026-09-19。

### 5.7.1 为什么必须改

5.4 把示例与指令改挂到 workflow 后，用户侧必须按**所选流程**过滤，否则管理员在后台配置的关联关系白配。同时用户自建内容（我的示例 / 我的指令）原本要求选类型/流程——那是在替文书类型收尾，文书类型没了，这个强制绑定就没有依据了。

### 5.7.2 示例下拉（A8）

原生 `<select>` 用 `<optgroup>` 分两段：

| 段 | 内容 | 过滤规则 |
| :--- | :--- | :--- |
| 系统预设（前） | 管理后台配置的示例 | `workflowIds` 命中当前流程，**或**为空（通用示例） |
| 我的示例（后） | 用户自建示例 | 不过滤，恒全部展示（`source === 'mine'`） |

- 两段都存在时才渲染 `<optgroup>` 分组标签；只有一段时不加分组标签，避免多余层级。
- 我的示例**不在名称里加后缀**——分组标签已表达来源。

### 5.7.3 指令标签（A8）

指令区仍是标签形式（点击填入文本框），顺序与示例一致：**系统预设（按流程过滤 + 通用）在前，我的指令平铺在后**；两段之间保留竖线分隔，我的指令沿用绿色标签样式。

### 5.7.4 我的示例 / 我的指令去绑定（A9）

| 项 | 改前 | 改后 |
| :--- | :--- | :--- |
| 新建表单字段 | 名称 + 内容 + 类型 / 流程选择 | **仅名称 + 内容** |
| 归属 | 按类型/流程分组 | 仅归属当前用户，不分组、不绑定流程 |
| 可见范围 | 按类型/流程过滤 | 当前用户下**恒全部可见** |

理由：用户自建内容数量少且本人记得住，强制绑定只会增加建内容的摩擦，且在文书类型消失后无从选择。

### 5.7.5 验收要点

1. 选中流程 A → 示例下拉仅含「关联了 A 的预设示例」+「通用示例」+「我的示例」。
2. 切到流程 B → 预设段随之变化，我的示例段不变。
3. 我的示例 / 我的指令新建弹窗无类型、无流程选择项，保存后在本人的下拉中恒可见。
4. 指令标签顺序：系统预设在前、我的指令在后，中间有竖线分隔。
5. 旧数据（示例带 `docType` 无 `workflowIds`）视为通用示例，仍在用户侧可见（零迁移）。

### 5.7.6 我的示例 / 我的指令去掉左栏（A23）

> 落 PRD 日期 2026-09-20。用户原话：「既然我的示例、我的指令没有建分组、平铺展示的，左侧的列表是不是应该去掉，不然都是展示全部，没有意义」。

**验收要点**

## 5.9 要件管理迭代（案字筛选 / 分组 / 组内排序 / 继承）

> 对应待办《原型待办清单-20260916-实施会议》第一节主块 B；落 PRD 日期 2026-09-23。
> 动手前已过 PM 评审，评审意见与遗漏点清单见该文档**第五节**。
> 范围：本版实施 **B1 案字筛选、B2 要件分组、B3 组内排序、B4 继承开关**；**B5 总结要件暂缓**。

### 5.9.0 前置事实与设计前提

动 ANY 改动前先认下四条事实，它们决定了 B4 的效果边界：

1. 内置要件 `elementPresetsByCause`（`js/case-data.js`）**只按叶子案由建 key，每个案由恰好 5 条**，代码中**不存在**顶层（如"民事案由"）或中类（如"合同纠纷"）的内置要件条目。
2. 用户侧 `getElementPresets` 的祖先查找**只对管理端覆盖生效**（读 `adminElementPresets[org][祖先]`），**内置要件不做祖先查找**。
3. 因此 B4 的合并只在「管理员曾在祖先案由上配过要件」时才产生效果。会议所述「16 个公共要件」**经用户 2026-09-24 确认，配在民事一级案由（`民事案由`）下 → B4 场景成立**：子案由开启继承后即可合并到这 16 条公共要件，正是会议诉求（"配完公共要件、子案由不丢"）。核证过程：本机全部浏览器 profile 检索 `adminElementPresets` 无命中（数据在演示环境机器上，本机读不到），故改为**自造同构数据 + 真实页面端到端验证**（16 条公共要件挂 `民事案由`、子案由自身覆盖 3 条），结论见 5.9.7。
4. 优先级自高到低：**子案由覆盖 → 父级覆盖 → … → 顶级覆盖 → 内置要件**。祖先一旦存在覆盖，叶子案由的内置要件即被遮蔽——这是既有行为，本版保留但需在 PRD 明示。

### 5.9.1 B1 案字筛选

工具栏右侧新增筛选下拉，默认「全部案字」。

取值口径是本次的纠偏点：不用全量 `caseWordListByOrg`，改用 **`getAllowedCaseWordsForCause(org, cause)` 白名单**，与页内「适配案字」栏同源——否则民事案由下的筛选列表会冒出"刑初""执""赔"等无关案字，与旁边的适配栏自相矛盾。自定义案由（不在案由树中）白名单为空时回退全部案字。

过滤规则与用户侧 `filterElementsByCaseWord` 同口径：`caseWords` 为空（通用）或包含所选案字的要件保留。四处联动：① 副标题计数变为 `共 N 项（民终 3）`；② 筛出 0 条时空态显示"该案字下暂无要件"；③ 筛选态下点「新增要件」**不预填**当前案字，避免误绑；④ 切换案由时重置为「全部案字」。

与 B4 继承叠加时，筛选作用于**合并后的整表**（先合并、后过滤），祖先继承条同样按其自身 `caseWords` 过滤，保证祖先通用要件的行为与自身要件一致。

### 5.9.2 B2 要件分组

数据层：要素对象新增 `group` 字段（字符串，缺失或空=未分组）。旧数据零迁移，一律视为未分组。

分组取值：单层标签，预设仅 **主体信息 / 程序性信息 / 事实认定**（用户拍板只要这三个，不再多设）；支持管理端自定义新建，作用域为**当前业务系统**、跨案由共享——不做同义组泛滥。行 Render 时 `group` 取值不在已知列表中的，按成员实际值聚合展示即可。

渲染：表格按 `group` 聚合，**未分组置底**，无成员的组不渲染，组内保持数组原序。

归属调整方式是一次评审补强：不给每行套"必须进弹窗改"，而是**每行直接提供分组下拉**——因为存量要件（15×5 条内置 + 演示环境已配要件）全都没有 `group`，若只能逐条点进弹窗去改，分组功能上线当天就是全表"未分组"，等于空转，且配置量正是会议抱怨的低效来源。新增/编辑弹窗同样提供分组下拉。

配套：代码中 15 个叶子案由 × 5 条内置要件**一次性预置 `group`**，避免每个演示环境都由实施人工重标一遍。

已知限制：分组当前**仅管理端可见且决定排序**，用户侧不展示分组标题、不按组聚合；但用户侧要件的**展现顺序**会随组内排序同步变化（B3 改写数组顺序所致），这一传导关系需在用户侧 PRD 明示，避免被误判为 bug。

### 5.9.3 B3 组内排序

存储仍是扁平数组，只是渲染时按 `group` 聚合。**仅支持组内上移/下移，不支持跨组移动**（用户拍板）——跨组归属只能通过改 `group` 字段实现，不引入拖拽库。

组间顺序固定为预设序：主体信息 → 程序性信息 → 事实认定 → 自定义组（按新建先后）→ 未分组。这里相对原始需求做了一次**主动缩减**：会议原始要求是"两级排序（组间+组内）"，组间排序本次不做，用户已确认可接受；后续若影姐要求"程序信息排前"，补一组标题上的上移/下移即可，不需要重构。

两个边界要处理好。一是内置要件排序会触发"该案由转为自定义覆盖"（与停用、删除共用的 baseline 机制），需给出提示文案，且「恢复内置」会连带还原排序。二是**继承行禁止排序**，上移/下移按钮置灰并 hover 提示"继承项请到上级案由调整"——继承行的位置由祖先决定，允许排序会与 B4 的"提升为覆盖"语义打架。

### 5.9.4 B4 要件继承开关

数据：新增独立存储 `adminElementInherit[org][cause] = true/false`，与既有 `adminElementPresets` 覆盖数组**解耦**（不污染覆盖数据），零迁移，存量无该键即视为 false。默认**关**——这样已配了子案由覆盖的存量案由不会在升级后突然多出一堆祖先要件，行为不突变。

显示条件：仅当前案由**存在祖先案由**时才显示（顶级案由无祖先，不展示开关），形态沿用页内「适配案字」栏的样式。

语义上，关即现状（有覆盖用自身、无覆盖继承最近祖先覆盖）。开则合并**全部祖先链**中已配置的要件 + 子案由自身，同名以**近者优先**（子 > 父 > … > 顶级）。管理端视图会把继承来源的行标上**灰色「继承」小标签**，与现有内置/自定义的状态色体系区隔。

继承行的两种操作需要区分对待，这是评审修出的一个逻辑空洞：

- **编辑**——仅提升该条为子案由覆盖（复制一份写入子案由数组后再编辑），其余继承行不受影响；这与现有内置→覆盖的机制一致。
- **删除**——不能走"提升后再删"，否则祖先那份仍在，刷新后又继承回来，表现为删除无效。正确做法是**写入一条同名 `enabled:false` 的屏蔽项**（沿用现有停用机制，不新增概念）。它顺带满足了"子案由想屏蔽某条公共要件"这个真实诉求，且可经「恢复内置」还原。

「恢复内置」需**一并清除**该案由的继承开关，否则会出现"覆盖清了但开关还开着"的不一致状态。

用户侧衔接改造落在 `getElementPresets`：子案由有覆盖且开关打开时，不再直接返回自身，而是返回「祖先链合并 + 自身」的结果，随后**统一**走 `filterElementsByCaseWord` 按案字过滤（先合并、后过滤）。`getAllElementPresets` 无需改动，自动继承这一结果。

### 5.9.5 B5 总结要件（暂缓）

本版**完全不做**，数据结构也**不预加** `isSummary` 字段。理由：一个当下没有任何读取方的字段就是无用字段，而要素对象本身是纯 JS 对象，后续加字段成本很低。总结 → 案件材料 → 生成上下文 → 要件答案的串接逻辑待产品设计后单独排期。

## 5.11 补遗两项：删除流程的关联清理 / 流程卡片按案由案字过滤

> 对应待办 A13 / A14。落 PRD 日期 2026-09-20。这两项是主块 A 收尾时发现的缺陷（原登记在 6.2），已由用户拍板处理方式后落地。

### 5.11.1 A13 · 删除 workflow 时清理关联引用

**问题**：`deleteWorkflow` 只从流程数组移除 id，不动示例/指令的 `workflowIds`。而过滤口径是 `ids.length === 0 || ids.indexOf(workflowId) >= 0`，于是被删流程的关联项既不算通用、也不出现在任何专属列表——**用户侧彻底不可见**，但管理端列表里还躺着，且「关联流程」列显示一个已不存在的流程名。

**处理方式（用户选定方案 A）**：删除时统计关联数 → 写进二次确认文案 → 确认后剔除无效 id，剔除后为空即自动转为通用项。

| 环节 | 规则 |
| :--- | :--- |
| 统计范围 · 示例 | `businessSystems[org].docTemplates` 中 `workflowIds` 含该 id 的项 |
| 统计范围 · 指令 | `adminPromptTemplates[org].__items__` 中 `workflowIds` 含该 id 的项（**仅物化 / 自定义项**） |
| **不统计** · 内置指令 | 内置指令的关联由 `BUILTIN_PROMPT_WORKFLOW_IDS_BY_DOCTYPE` **推导**，不落库；流程删除后自动不再匹配，既无从清理也无需提示「转为通用」 |
| **不统计** · 旧 docType 分组指令 | 零迁移口径下本就视为通用，不受影响 |
| 确认文案 | 在原文案后追加「该流程被 N 个示例、M 个指令关联，删除后这些项将转为通用（对所有流程可见）」；N、M 均为 0 时不追加 |
| 执行 | 从各项 `workflowIds` 中剔除该 id；剔除后数组为空 → 该项成为**通用项**（复用 5.4.2「空=通用」语义，不是新造概念） |
| 通用兜底流程 | 仍不可删，前置拦截不变 |

**实现**：`case-data.js` 新增 `countWorkflowRefs(org, wfId)`（只读统计）与 `purgeWorkflowRefs(org, wfId)`（执行剔除，回写 `businessSystems` 与 `adminPromptTemplates`），`admin-workflows.js` 的 `deleteWorkflow` 串联两者。

**验收要点**：

1. 新建示例 A 关联流程 X，删除 X → 弹窗提示「被 1 个示例、0 个指令关联」，确认后示例 A 的 `workflowIds` 变为 `[]`，用户侧任何流程下都能看到它（= 通用）。
2. 新建示例 B 同时关联 X 和 Y，删除 X → B 的 `workflowIds` 只剩 `[Y]`，仍只在 Y 下可见，未退化成通用。
3. 流程无任何关联项时，确认文案不出现「被 N 个示例…」这句。
4. 管理端示例列表的「关联流程」列不再出现已删除的流程名。
5. 内置指令不受影响（未物化时删除流程，内置指令不会报错、不会变重复）。

### 5.11.2 A14 · 用户侧流程卡片按案字 + 案由过滤

**问题**：`getOrgWorkflowsForView(isSteps)` 只按生成模式过滤，不读案件上下文。后果是「民初」案件也能选到「民事判决书（二审）」，不会报错但会生成审级错误的文书。

**过滤口径（用户 2026-09-20 拍板）**：

| 条件 | 结果 |
| :--- | :--- |
| 流程 `caseWords` 为空 | **兜底**——不限制案字，恒展示 |
| 流程 `caseWords` 非空 | 要求案件案字命中其中任一项 |
| 流程 `causes` 为空 | **兜底**——不限制案由，恒展示 |
| 流程 `causes` 非空 | 要求案件案由命中其中任一项 |
| **案件案号缺失 / 案字解析不出** | **严格只展示兜底 + 通用**，不回落全展示（用户明确选择此口径） |

**两个 tab 的实际影响不同**（内置数据决定，见 5.2.5）：

- **一步生成 tab**：内置 6 条一步型流程的 `caseWords` 全为空（判决书直接生成 / 裁定书 / 调解书 / 庭审提纲 / 材料总结 + 通用），全是兜底 → 无论案件案字是什么，**6 条恒展示**，过滤对现状无可见影响。只有当管理员新增了限定案字的一步型流程时，过滤才开始起作用。
- **分步生成 tab**：内置 3 条分步型流程分别限定民初 / 民终 / 民再，**没有兜底分步流程** → 案号缺失或案字无法识别时，分步 tab **卡片区为空**，展示提示：

  > 当前案件的案号/案由没有匹配的生成流程。请补全案件案号，或在管理后台配置不限制案字案由的流程。

  两个 tab 共用同一空态组件与文案。分步 tab 是**唯一会实际触发**该空态的场景（内置一步型流程全是兜底）；一步 tab 只有在管理员把全部一步型流程都配上案字/案由限制时才可能出现。空态与「一个流程都没配」的空态区分展示，后者文案仍为「当前业务系统暂无可用流程，请先在管理后台『文书流程管理』中配置」。

  这是用户选定的严格口径的直接后果，已充分告知并确认。

> 术语澄清（用户提问）：**「兜底」是匹配规则维度**（`caseWords`/`causes` 为空 = 不设限），**「通用」是流程定位维度**（`isGeneral: true`，就「通用文书生成」这一条）。通用流程自身 `caseWords` 为空，所以**通用 ⊂ 兜底，但兜底不止通用**（内置 6 条兜底里只有 1 条是通用）。

**联动处理**：过滤后若当前选中流程不在新列表中，重置为该列表第一项；列表为空则置空，生成按钮置灰（沿用 5.6.5 第 5 条的置灰口径）。切换案件时流程列表随之重算。

**验收要点**：

1. 案号含「民初」→ 分步 tab 只出现「民事判决书（一审）」；「民终」→ 二审；「民再」→ 再审。
2. 案号为空或案字无法识别 → 分步 tab 为空态提示（文案见上）；一步 tab 仍展示 6 条。
3. 管理端新增一条 `caseWords=['民终']` 的一步型流程 → 民初案件的一步 tab 看不到它，民终案件能看到。
4. 管理端给某流程配 `causes=['民间借贷纠纷']` → 只有该案由的案件能看到该流程。
5. 切换案件后流程列表刷新；原选中流程若被过滤掉，自动切到第一个可用流程，不残留失效选中态。
6. 通用兜底流程在一步 tab 恒在末尾（不受过滤影响，其 `caseWords` 为空）。

**已知限制**：案由过滤依赖案件的 `cause` 字段；案件未填案由时，任何配了 `causes` 的流程一律不展示（含管理端新配的流程）。

## 5.14 用户侧 · 案件列表页快速生成恢复（V1.3.20 A27）

> 落 PRD 日期 2026-09-20。用户推翻 A10 的部分决策：「之前你不是将用户侧案件列表页的快速生成按钮隐藏了吗？你要恢复」。

### 5.14.1 为什么恢复、以及为什么必须顺带改造弹框

A10 下线列表页生成入口的理由中，真正站得住的只有一条：**文书类型消失后，列表页弹框没有流程承载，等于把"选流程"这一步丢掉了**——用户是在盲选。而"两套并行入口增加维护成本"这条，在 A7/A22 把流程选择做成下拉后已弱化：列表页弹框与详情页工作台现在复用同一套"选流程 → 选示例 → 选指令"口径，不再是两套逻辑。

所以恢复不是把 A10 原样回滚，而是**把弹框补上缺失的那一环**：首行由「文书类型」下拉改为「生成流程」下拉。原样回滚会打开一个已被 A3/A7 废弃的表单（文书类型下拉 → 示例下拉），与详情页口径对不上，演示时会自相矛盾。

### 5.14.2 变更内容

| 项 | 处理 |
| :--- | :--- |
| 行内「快速生成」按钮（`quick-gen-btn`） | **恢复渲染**，位置回到「文件上传」按钮之后、「更多操作」之前 |

### 5.14.3 快速生成型流程的口径（用户 2026-09-20 拍板）

| 业务系统 | 新增 | domain |
| :--- | :--- | :--- |
| 法院 | 民事判决书（快速生成）、民事裁定书（快速生成） | `judgment` / `ruling` |
| 检察院 | 起诉书（快速生成） | — |
| 司法局 | 行政复议决定书（快速生成） | — |

### 5.14.4 实现要点

## 5.16 用户侧 · 生成配置「案件阶段」属性拆分（V1.3.22 A29）

> 落 PRD 日期 2026-09-20。用户反馈：「生成文书配置时，案件阶段这个属性不需要了，拆成两个属性，案由、案字，如果某个案子的案由、案字有一个没有获取到数据，就展示出来让用户去选」。

### 5.16.1 背景与口径

- 三种文书生成配置页面（列表页快速生成弹框、详情页材料生成、详情页分步生成）此前均携带用户可见的「案件阶段」选择器（v1.45 引入，仅分步型文书场景显示）。
- 用户定调：**「案件阶段」不再是用户选择的属性**，拆为「案由」「案字」两个案件属性。
- 2026-09-20 补充拍板（配图）：案由、案字作为**两个常显配置项（两列并排）**——先去案件的结构化信息里取值：**有值则默认填充并带「来自案件信息」来源标签**（只读展示）；**没有值则展示下拉选择器让用户补选**。
- **流程联动口径**：案由、案字**任一缺失**时，生成流程下拉**仅保留通用兜底流程**；两属性齐全后恢复 A14 案字/案由过滤的完整流程列表。补全不强制——通用兜底流程本身就是缺值时的可生成保底路径。
- **展示顺序**：案由 / 案字两列**恒置于「生成流程」行之前**——流程选项依赖案由 / 案字联动过滤，属性信息先行（三入口统一）。
- 「案字 → 案件阶段」的判定（`getCaseStageByCaseWord`）属于**内部逻辑**，继续保留：分步步骤序列的渲染、判定文书域分支（`resolveStepsByCaseStage` / `getCurrentCaseStage`）的输入毫无变化，只是用户通过「选案字」间接决定审理阶段，不再直接选阶段。

### 5.16.2 变更内容

| 位置 | 原形态（V1.3.21） | 新形态（V1.3.22 A29） |
| :--- | :--- | :--- |
| 快速生成弹框（`cases.js`） | 「案件阶段」行（欠 judgment 且无法自动判定时显示，选择后参与开始按钮校验） | 移除案件阶段行；新增「案由 / 案字」**两列常显**区（有值 → 值 + 灰字「来自案件信息」标签；缺失 → 下拉补选）；任一缺失时流程下拉仅保留通用兜底流程 |
| 材料生成（case-files `mat` 区） | `matCaseStageRow`（分步型流程时显示） | 替换为「案由 / 案字」两列常显区（同上口径，任一缺失时流程下拉仅保留通用兜底流程） |
| 分步生成（case-files `step` 区） | `stepCaseStageRow` | 替换为「案由 / 案字」两列常显区；任一缺失时分步流程下拉仅保留通用兜底（分步型无兜底 → 空态 + 提示「请先在上方补全案由 / 案字」）；案字缺失时分步步骤区空态文案「请先选择案字，系统将按案字判定审理阶段并展示对应步骤序列（一审 5 步 / 二审 6 步）」 |
| 内部字段 | `caseStage`（quickState）与 `caseStage: getCurrentCaseStage()` 载荷 | 载荷仅保留 `caseStage: getCurrentCaseStage()`（由案字推导，内部字段）；`quickState.caseStage` 删除 |

判定与联动规则：

- **取值**：结构化信息中已取得案由 / 案字 → 该列显示「值 + 灰字『来自案件信息』标签」，只读不选；缺失 → 该列显示对应下拉（案字选项来自 `caseWordListByOrg[org]`，案由选项复用案由树——分类为分组、组名与叶子均可选）。
- **顺序**：三入口的案由 / 案字两列均渲染在「生成流程」行**之前**，流程下拉随两属性联动。
- **回写**：用户选中即写回 `caseItem.cause` / `caseItem.caseWord` 并 `saveBusinessSystems()` 持久化，该列随即转为「值 + 来自案件信息」展示态。
- **流程限制**：案由、案字任一缺失 → 流程列表仅保留 `isGeneral === true` 的通用兜底流程（快速 / 材料模式可见）；两属性齐全后恢复 A14 过滤的完整列表。
- **联动**：补全后三处 UI 均重过滤流程下拉（当前选中流程仍有效则保留、否则回落第一项）；示例 / 指令 / 模型跟随所选流程刷新；分步序列按新案字重解析步骤。
- **提取口径升级**：案字提取函数（`extractCaseWordFromCaseNumber` 及快速弹框的 `resolveWorkflowModelForCase` / `getQuickWorkflows`）**优先读案件已保存的 `caseWord` 字段**，再回退扫描案号——保证用户补选案字后立即生效。

### 5.16.3 强制口径（三入口统一）

- 三处配置页面统一：**案由、案字任一项缺失 → 流程下拉仅可勾选通用兜底流程**（不再有「快速/分步必选阻断、材料不强制」的差异化——兜底流程即缺值时的可生成保底路径，补全不强制）。
- **快速生成弹框**：【开始生成】按钮不再因案由/案字缺失而禁用——缺失时勾选通用兜底流程即可直接生成。
- **分步生成**：分步型无通用兜底流程，案由/案字缺失时分步流程下拉空态 + 提示「请先在上方补全案由 / 案字」，步骤区同示案字指引空态。
- **材料生成**：缺失时流程下拉仅剩通用兜底流程，选中后照常可生成。

## 6.2 曾与方案设计有偏差的两项（V1.3.8 已处理，见 5.11）

> 以下两节的**问题分析与方案取舍保留备查**，处理结论均为「已落地」，实现与验收见 5.11。

### 6.2.1 删除流程后，其关联示例 / 指令变成「悬挂引用」

**方案设计要求**（第六节）：删除 workflow 时提示「被 N 个示例、M 个指令关联，删除后这些项自动转为通用」，确认后清空对应 `workflowIds` 项。

**本版实际行为**：`deleteWorkflow` 只从流程数组中移除该 id，**不触碰示例/指令的 `workflowIds`**。过滤函数 `getFilteredDocTemplatesByWorkflow` 的口径是 `ids.length === 0 || ids.indexOf(workflowId) >= 0`，因此被删流程的关联项：

- `workflowIds` 仍非空 → **不算通用示例**；
- `indexOf(当前流程 id)` 恒为 -1 → **不在任何流程的专属列表中**；

结论：该示例 / 指令在用户侧**彻底不可见**，既不是通用也不是专属——但数据仍在管理端列表里（表格「关联流程」列会显示一个已不存在的流程名）。这是比「自动转通用」更糟的结果。

**用户决策（2026-09-20）**：采用**方案 A**。

**处理结果**：V1.3.8 已落地（A13），见 5.11.1。

### 6.2.2 用户侧流程卡片**未按案由/案字过滤**

**方案设计要求**（4.1）：卡片列表 = 当前案件案由案字**匹配到**的本模式 workflow + 通用兜底。

**本版实际行为**：`getOrgWorkflowsForView(isSteps)` 只按生成模式过滤，**不读案件的案字/案由**，平铺该模式下全部流程。后果：一个「民初」案件的流程卡片里会出现「民事判决书（二审）」「民事判决书（再审）」，法官选了也不会报错，但会拿到审级错误的文书。

**为什么本版没做**：PRD 5.6.3 落地时写的是「展示 `type === 'material'` 的流程」，未把案字过滤写进去；A7 的 14 项 CDP 验证也未覆盖该口径，因此代码与 PRD 一致、与方案设计不一致。

**用户决策（2026-09-20）**：补过滤，且**案字取不到时严格只展示兜底 + 通用**（不采纳「不过滤全展示」）。已知该口径会让分步 tab 在案字缺失时变空态，用户确认接受，空态给明确提示。

**处理结果**：V1.3.8 已落地（A14），见 5.11.2。附带澄清：「兜底」是匹配规则维度、「通用」是流程定位维度，两者不是一回事。

> 补充：管理端保存流程时的轻提示已按（案字 + 案由 + 生成模式）统计数量（5.2.4），说明案字维度在配置侧是有效的，只是用户侧读取未用上。
