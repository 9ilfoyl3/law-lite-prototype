## 一、全局交互规范

### 1.1 页面导航规则

| 动作 | 行为 | 说明 |
|------|------|------|
| 返回聊天 | `location.href = 'chat.html'` | 携带sessionID，保持会话上下文 |
| 切换模式 | 直接跳转对应页面 | 如从chat切换到cases.html |
| 新建任务 | 当前页面刷新重置 | 清空当前任务状态，回到初始态 |
| 浏览器后退 | 弹出确认提示 | 防止误操作丢失未保存数据 |

### 1.2 状态持久化策略

| 阶段 | 存储方式 | 说明 |
|------|----------|------|
| 原型阶段 | JS内存变量 | 最简单，页面刷新丢失 |
| 后续迭代 | sessionStorage / localStorage | 标签页级或跨标签页持久化 |

### 1.3 通用组件交互

#### 模态框（Modal）
- 点击遮罩层关闭
- ESC键关闭（可选配置）
- 确定/取消按钮居右排列
- 表单错误时实时显示提示信息

#### 确认弹窗（Confirm）
- 删除操作必须二次确认
- 批量操作显示具体数量（如"确定删除选中的5项？"）
- 危险操作按钮使用红色样式

#### 通知提示（Toast）
- 位置：页面右上角
- 类型：成功（绿色）、错误（红色）、警告（橙色）
- 自动消失：2.5秒
- 动画：滑入滑出

#### 加载状态
- 页面初始加载：骨架屏（Skeleton）
- AI处理中：进度条 + 步骤列表
- 文件上传：进度环 + 百分比
- 数据保存：按钮Loading旋转
- 页面切换：淡入淡出动画（300ms）

### 1.4 表单验证规则

| 规则 | 说明 |
|------|------|
| 必填校验 | 红色*标识，失焦时触发校验 |
| 格式校验 | 邮箱、手机号等正则验证 |
| 唯一性校验 | 用户名、分类ID等唯一字段实时校验 |
| 长度限制 | 显示剩余可输入字数 |

### 1.5 按钮状态

| 状态 | 样式 |
|------|------|
| 正常 | 标准背景色 |
| Hover | 略深背景色 |
| 禁用 | 灰色背景，不可点击 |
| 加载中 | 显示Loading图标 |

### 1.6 选择项交互

- **未选中**：空心方框 + 灰色边框
- **已选中**：实心勾选 + 蓝色边框 + 蓝色背景
- **禁用后**：降低透明度，不可点击

### 2.3 V1.0 开放任务流程

> **说明**：Chat 页面任务选择器中，仅开放「裁判文书」「庭审提纲」「法条适用」三个办案任务入口。其余任务（类案检索、争议焦点、文本总结、文本润色、票据汇总）做隐藏处理，用户不可选择。
>
> 以下核心场景暂无独立任务页面，通过自然语言交互触发：文书质量评查、案由智能推荐、证据梳理、知识问答。

#### 2.3.1 裁判文书任务（对应核心场景：裁判文书生成）

**标准生成模式（五步法）**：

```
[发起任务]
    │
    ▼
Step 1: 材料上传与解析
    ├─ 上传起诉状/答辩状/证据清单（PDF/Word）
    ├─ 系统解析提取结构化信息
    └─ 显示解析进度
    │
    ▼
Step 2: 要件提取与确认 【检查点】
    ├─ AI自动提取法律要件（当事人信息、诉讼请求、事实理由等）
    ├─ 低置信度项高亮提醒
    └─ 法官逐项确认/修改/补充
    │
    ▼
Step 3: 法条推荐与选择 【检查点】
    ├─ 系统推荐适用法条（按效力层级排序）
    ├─ 标注法条状态（现行有效/已被废止）
    └─ 法官确认或手动替换法条
    │
    ▼
Step 4: 裁判方向笔记
    ├─ 法官输入裁判倾向、争议焦点处理意见
    └─ 支持引用前文已确认的要件
    │
    ▼
Step 5: 文书生成
    ├─ 流式输出判决书初稿
    ├─ 首字≤3秒，完整生成≤30秒
    └─ 附带"辅助生成，请核对"水印
    │
    ▼
[输出结果]
    ├─ 文档预览面板（右侧50%）
    ├─ 溯源功能：点击段落高亮显示来源
    └─ 操作：下载Word/PDF、收藏、转入编辑
```

**快速生成模式**：

```
[发起任务]
    │
    ▼
上传材料 ──▶ AI自动提取要件（无需确认）
    │           │
    │           └─ 法官可事后修改
    │
    ▼
一键生成初稿 ──▶ [输出结果]
```

#### 2.3.3 法条适用任务（对应核心场景：法条检索与校验）

**主动检索模式**：


### 5.1 错误类型与处理

| 错误类型 | 处理方式 | 用户提示 |
|----------|----------|----------|
| 文件上传失败 | 显示错误图标 | "上传失败，请重试" |

| 生成失败 | 显示错误详情 + 重试按钮 | "生成失败：[原因]" |

| 文件大小超限 | Toast提示 | "文件大小超过限制（文档≤50MB，图片≤10MB）" |
| 文件数量超限 | Toast提示 | "最多上传10个附件" |

### 5.2 附件上传前端校验规则

| 校验项 | 规则 | 提示方式 |
|--------|------|----------|

### 5.4 降级策略

| 场景 | 降级行为 |
|------|----------|

### 9.2 生成文书交互（行内触发 → 配置弹框）

**触发路径**：案件列表行 → 操作栏「生成文书」按钮 → 弹出配置弹框

**弹框内容**：
```
弹框标题：「生成文书」
弹框内容：
├─ 当前模型（下拉，可选轻量/标准/旗舰/长文本模型；标签右侧带提示图标，悬停提示「该配置功能为管理后台功能，用户不可见，方便演示展示」）
├─ 案件材料上下文预估（根据当前模型自动计算）
│   ├─ 未超限时："当前案件全部材料预估约 X tokens，未超过 Y 模型安全上限 Z tokens，将默认使用全部材料生成。"
│   └─ 超限时："当前案件全部材料预估约 X tokens，超过 Y 模型安全上限 Z tokens，请进入案件详情页选择核心材料生成文书；如勾选的核心材料仍超限，再使用分步生成。"
├─ 未超限时显示：文书类型、文书示例、指令
└─ 底部主按钮
    ├─ 未超限时：【开始生成】
    └─ 超限时：【前往案件详情页配置】
```

**生成判断与跳转**：

1. 用户选择模型后，系统实时计算案件全部材料的预估 Token 总数 `getAllMaterialsTokens(caseId)` 与当前模型安全上限 `getSafeContextLimit(modelId)`
2. **未超限时**：
   - 弹框展示文书类型（必选）、文书示例（非必填，含「暂无可用示例」）、指令（非必填）
   - 默认选中全部材料作为上下文
   - 若当前案由存在标准要件或我的要件，弹框内显示蓝色提示条"检测到该案由存在 X 个可用要件（标准 X / 我的 X），开始生成后将自动引入全部要件辅助生成"
   - 点击【开始生成】前校验文书类型是否为空；校验通过后弹框关闭，跳转 `pages/case-files.html?caseId=xxx&model=xxx&docType=xxx&template=xxx&requirement=xxx&source=list&autoGen=1&autoIntroduceElements=1`
   - 案件详情页自动应用传入的模型、文书类型、示例、指令，默认全选材料并自动引入全部标准要件与我的要件（由系统预生成答案）后直接生成；生成完成后进入「生成完成态」，左栏材料树占 25%，右栏文书结果占 75%；用户可点击右栏【重新配置】回到配置态（中栏文书设置占 75%，右栏折叠）继续调整
3. **超限时**：
   - 弹框隐藏文书类型、文书示例、指令，仅保留模型与上下文提示
   - 底部按钮变为【前往案件详情页配置】
   - 点击后弹框关闭，跳转 `pages/case-files.html?caseId=xxx`（效果同点击案件名称进入案件详情）
   - 用户在案件详情页选择核心材料并配置文书类型、示例、指令后生成；若勾选的核心材料仍超限，再使用分步生成

**关闭规则**：点击弹框外部 / 关闭按钮 / 取消 → 弹框关闭，回到案件列表

#### 案件阶段选择（v1.45 新增）

#### 分步生成交互优化（v1.46 新增）

> ℹ️ **核心目的**：移除冗余的「开始生成」按钮，让用户进入分步生成视图后直接看到步骤列表，降低操作成本。

- 移除 `startStepsBtn` 按钮及其触发的 `startStepGeneration()` 函数

  - 每步生成仅基于该步已勾选材料
  - 若某步骤预估 Token 总数超过当前模型安全上限，提示「某某步骤预估 x tokens，超出当前模型安全上限 y tokens，请减少材料」

- **步骤输入模式（合规要求）分三类**：
  - **仅材料生成**（默认）：前四步（一审：原告诉请/被告答辩/争议焦点/事实认定；二审：原审查明认定/上诉人诉讼/被上诉人抗辩/争议焦点）**仅展示【生成本步】按钮，不展示【直接输入】按钮**
    - waiting 状态：仅【生成本步】（必填依赖未完成时置灰）
    - done 状态：【编辑】【重新生成】【内容优化】
  - **材料生成 + 直接输入**（`allowDirectInput`）：二审（案件阶段=二审）第 5 步「事实认定」**同时展示【生成本步】+【直接输入】**，用户可选材料调 AI 生成，也可手动输入
    - waiting 状态：【直接输入】+【生成本步】（必填依赖未完成时置灰）
    - done 状态：【编辑】【重新生成】【内容优化】
  - **仅直接输入**（`manualOnly`，合规要求）：最后一步「裁判结果」**waiting 状态直接展示输入框 + 友好提示**，裁判方向属法官主观意识，不调 AI 生成
    - waiting 状态：直接展示输入框（用户打字即交互，无需点击【直接输入】按钮）+ 蓝色友好提示「本步为法官主观判断内容，合规要求不由 AI 生成，请直接在下方输入框填写裁判结果」+【保存】按钮；不展示「关联材料」区域与材料选择建议
    - done 状态：仅【编辑】，不展示【重新生成】【内容优化】
    - 不调用 AI 生成 API，无前置步骤依赖校验
- **重新生成（重新回答）递归重置逻辑（v1.33 PRD 登记，原型暂不实现）**：
  - 当用户在步骤 N（N ≥ 1）点击「重新生成」时，**逻辑上**应同时重置步骤 1 ~ N 的状态（全部回到 waiting）与生成内容（清空 items / materials），即「该步及之前所有已完成步骤一并重新回答」
  - 用户需从步骤 1 开始重新触发逐 step 生成，已重置的步骤不再保留之前的生成结果
  - 设计意图：分步生成步骤之间存在上下文依赖（后一步基于前一步的结果），单独重置某一步会破坏上下文一致性，故采用递归重置
  - 当前原型实现：仅重置当前步（stepStates[index] = 'current'，清空当前步 data 并重新生成）；递归重置逻辑在 PRD 中登记，后续迭代实现
- 全部步骤完成后：
  - 底部按钮显示为【生成文书】
  - 点击后将所有步骤内容合并为完整文书并展示在右栏「生成结果」面板
- **内容优化**（v1.48 链 G 新增）：
  - 分步生成各步骤（manualOnly 步骤除外）完成后，用户可点击【内容优化】按钮对当前步骤的生成结果进行持续优化
  - **轮次限制**：最多 3 轮优化，第 4 次时提示"已达到最大优化轮次（3 轮）"并禁用按钮
  - **展示方式**：上方大文本框始终展示最新正式答案（可编辑），下方折叠展示优化问答历史（除最后一轮外）
  - **语义说明**：优化对话内容仅作参考，最终文书取文本框内的正式答案，不是优化对话内容
  - **操作流程**：点击【内容优化】→ 在输入框中填写优化要求 → 点击「发送」→ AI 返回优化后的内容 → 更新文本框中的正式答案 → 问答历史折叠展示在下方 → 可继续优化直到 3 轮上限
  - **优化历史管理**（v1.50 新增）：折叠展开的每条历史记录下方提供两个操作按钮
    - **【回填】**：将该轮优化的答案覆盖到当前正式答案文本框（写入 `stepData[stepId].items`，仅内存态），重新渲染步骤列表并 toast「已回填第 N 轮优化答案」
    - **【删除】**：移除该条优化历史记录（`followUps.splice(idx, 1)`），重新渲染步骤列表并 toast「已删除第 N 轮优化记录」；删除操作不影响当前正式答案文本框内容

#### 生成结果面板：流式输出与文档编辑器

**文书生成两步流程**（v1.42 新增，对用户不感知）：

1. **第一步·按示例生内容**：AI 按所选文书示例的 `content`（内容参考文本）作为结构指引生成正文，替换原硬编码 4 段结构。示例描述了哪些内容板块/段落（如"原告诉请、被告答辩、争议焦点、事实认定、裁判结果"），AI 据此组织内容。示例 `content` 为空时回退到默认结构。
2. **第二步·套格式骨架**：若该文书类型在管理后台配置了「文书格式约束」（带占位符的格式骨架），将第一步生成的内容按格式骨架套版（填充 `{{courtName}}`、`{{caseNumber}}`、`{{caseName}}`、`{{cause}}`、`{{partyA}}`、`{{partyB}}`、`{{title}}`、`{{body}}`、`{{signer}}`、`{{date}}`、`{{elementHint}}` 等占位符，其中 `{{body}}` 为第一步生成的正文 HTML），最终文书符合排版约束；未配置格式骨架时直接输出第一步内容。占位符映射规则见管理后台 PRD 4.11.8。

**流式输出阶段**：

- 用户触发文书生成（一步生成 / 分步生成编译 / 列表页自动触发）后，右栏「生成结果」面板进入流式输出状态
- 流式输出分两个阶段：
  - **思考过程阶段**：顶部展示「思考过程」区域，逐条呈现 AI 思考文案（阅读材料、分析诉求、审查证据、归纳焦点、匹配法条、组织理由等），每条约 420-800ms 间隔，带闪烁光标
  - **正文渲染阶段**：思考完成后，文书正文按段落逐步渲染，每段约 500-900ms，整体约3秒，模拟真实 AI 流式返回
- 触发生成后立即切换到结果视图（右栏展开），确保用户可见流式输出过程
- 顶部进度条与统计区实时更新：思考中显示「思考中 · N/M」，正文阶段显示「已输出字数 · 预计剩余 · 第 N/M 段」
- **流式输出期间**：右栏顶部【文书精修】【重新配置】按钮置灰禁用，防止用户在生成过程中跳转或重配
- 思考过程文案仅在流式输出阶段展示，不写入文书内容，不影响后续文档编辑器

**文档编辑器阶段**：

- 流式输出完成后，右栏自动切换为文档编辑器，**仅展示最终文书正文内容**（不含思考过程）
- 编辑器提供常用排版工具栏（撤销/重做、加粗、斜体、下划线、标题、对齐、清除格式等）
- 编辑区域采用白色 A4 纸张样式，默认字体为宋体/Noto Serif SC，行距 2 倍，段落首行缩进 2 字符，符合法律文书排版习惯
- 用户在编辑器中的修改会同步到 `resultContent`，点击【保存到历史文书】时保存当前编辑器内容
- **编辑器就绪后**：右栏顶部【文书精修】【重新配置】按钮恢复可用状态
- 组件实现：`js/doc-editor.js` 提供 `DocEditor` 类，案件详情页与文书精修页共用同一编辑器组件，确保视觉与交互一致

#### 引入案由要件流程

> ⚠️ **适用范围（v1.27）**：要件（标准要件 + 我的要件）仅在文书类型为「裁判文书」（judgment）时才会询问是否引入。其他文书类型（庭审提纲、执行文书、材料总结等）生成时**不触发**要件引入流程，也不显示任何要件相关提示。案件列表页跳转、一步生成视图【生成文书】、分步生成视图【确认并编译文书】三个入口均遵守此规则。

在一步生成视图点击【生成文书】后、进入 AI 生成前：

1. 检查当前案件案由是否存在标准要件或用户自定义的“我的要件”
2. 若存在配置，先弹出「生成文书」前置选择弹框：
   - 标题：「生成文书」
   - 显示可用要件总数及分类统计（标准 / 我的）
   - 说明引入案由要件的作用：可让生成的文书更精确，系统会预生成参考答案，用户可在下一步修改
   - 黄色时间提示：引入要件后将增加答案预生成与整合步骤，整体生成时间可能会稍长
   - 底部左侧为【引入案由要件】（次按钮），右侧为【直接生成】（蓝色主按钮）
3. 用户选择：
   - **直接生成**：关闭弹框，仅使用已选材料生成
   - **引入案由要件**：关闭前置弹框，进入「引入案由要件」弹框
4. 「引入案由要件」弹框：
   - 标题：「引入案由要件」
   - 默认已勾选所有可用要件（标准要件 / 我的要件），用户可手动取消不需要的要件
   - 底部为【取消】和【引入要件并生成】（蓝色主按钮）
   - 若用户未勾选任何要件即点击【引入要件并生成】，系统提示"请先勾选要引入的要件"
5. 点击【引入要件并生成】后进入答案确认页：
   - 系统根据每个已勾选要件的问题**AI 预生成参考答案**
   - 用户可对答案进行修改、删除；如需新增自定义要件，点击弹窗内的「管理我的要件」进入 `pages/my-elements.html` 维护
   - 每个要件仅包含一个问题
6. 点击【确认并生成】后，将问题及答案作为生成上下文传入模型，最终文书保持原有文书形态，不直接展示问答内容
7. 若案由无配置要件，不弹窗，直接进入生成流程
8. **一步生成视图**与**分步生成视图**点击最终生成前均执行上述引入要件流程
9. **案件列表页**点击行内【生成文书】并在弹框中点击【开始生成】后，跳转 `case-files.html?source=list&autoGen=1&autoIntroduceElements=1`，默认全选材料；v1.47 调整：到达详情页后弹出要件上下文确认弹框（大文本框预填充问答，用户可修改后确认引入或选择不引入），不再自动跳过弹框
10. **案件详情页（一步生成视图）**点击【生成文书】后仍执行上述前置选择弹框流程，由用户决定是否引入要件

#### 本案要件抽屉（任务 8.6 / 9.4）

> ℹ️ **适用范围**：本抽屉作为案件详情页的常驻入口，聚合展示与当前案件相关的所有要件（标准 / 我的 / 个案三类来源），并支持对单个要件进行问答与答案持久化。抽屉默认收起，不占用主布局空间。

**入口位置**：左侧材料树底部固定一个【本案要件 (N)】按钮，N 为该案件当前可用要件总数（标准要件 + 我的要件 + 个案要件）。点击按钮从右侧滑出抽屉。

**抽屉结构**：
- 标题栏：「本案要件」+ 关闭按钮（×）
- 来源统计条：`标准 X · 我的 Y · 个案 Z`，三种来源用不同颜色标签区分
  - 标准要件：蓝色标签（`#e0e7ff / #3730a3`）
  - 我的要件：绿色标签（`#dcfce7 / #166534`）
  - 个案要件：橙色标签（`#fed7aa / #9a3412`）
- 要件列表：按 来源分组渲染，每项包含【勾选框】+ 要件名 + 来源标签 + 【问答】按钮 + 已答标识（绿点）
- 底部操作区：
  - 【新增个案要件】：在抽屉内联展开表单（名称 / 说明 / 问题），保存至 `localStorage.caseCustomElements_${caseId}`（数组结构）
  - 【一键生成】：对全部要件批量生成答案（无需勾选），用户可在列表中修改；按钮在无可用要件（要件列表为空）时置灰不可点击，hover 提示"暂无要件可生成，请先新增或维护要件"
  - 【管理我的要件】：跳转 `pages/my-elements.html?cause=当前案由`，页面加载后自动选中该案由
  - 【关闭】：收起抽屉

**交互流程**：
1. 用户点击【本案要件 (N)】按钮 → 抽屉从右侧滑入（380px 宽，过渡动画 0.3s）
2. 抽屉展示当前案件全部可用要件，按来源分组并标注不同颜色标签
3. 用户可勾选 / 取消勾选要件（勾选状态决定是否作为文书生成入参）
4. 用户点击要件行的【问答】按钮 → 弹出「要件问答」弹框：
   - 标题：要件名称 + 来源标签
   - 正文：要件问题文本 + 多行文本域（默认填入持久化的答案，无则空）
   - 底部：【取消】、【保存答案】
   - 保存后答案写入 `localStorage.caseElements_${caseId}`（结构：`{ [要件名]: 答案 }`），已答标识显示绿点
   - **内容优化**（v1.48 链 G）：已有答案后，底部出现【内容优化】按钮，点击后展开优化输入框，用户填写优化要求并发送，AI 返回优化后的内容更新到文本域；最多 3 轮，超过后禁用按钮；优化问答历史折叠展示在文本域下方
   - **优化历史管理**（v1.50 新增）：折叠展开的每条历史记录下方提供两个操作按钮
     - **【回填】**：将该轮优化的答案覆盖到当前正式答案文本域（写入 `caseElementsAnswers[name]` 并持久化到 `localStorage.caseElements_${caseId}`），重新渲染要件列表并 toast「已回填第 N 轮优化答案」
     - **【删除】**：移除该条优化历史记录（`caseElementsFollowUps[name].splice(idx, 1)` 并持久化），重新渲染要件列表并 toast「已删除第 N 轮优化记录」；删除操作不影响当前正式答案文本域内容
5. 用户点击【新增个案要件】 → 在抽屉底部内联展开表单，填写名称 / 说明 / 问题后【保存】 → 新个案要件追加到「个案要件」分组，同时持久化到 `localStorage.caseCustomElements_${caseId}`
6. 用户点击【管理我的要件】 → 新窗口打开 `pages/my-elements.html?cause=xxx`
7. 关闭抽屉：点击 × 关闭按钮 / 点击遮罩 / 按 ESC 键

**持久化与恢复**：
- 要件答案：`localStorage.caseElements_${caseId}` = `{ [要件名]: 答案 }`
- 个案要件定义：`localStorage.caseCustomElements_${caseId}` = `[{ name, desc, question, enabled }]`
- 用户再次进入案件详情页时，自动加载并恢复：要件列表（含个案要件）、勾选状态、已答标识、答案内容
- 入口按钮的数字 N 同步反映当前可用要件总数

**与文书生成的关系**：
- 抽屉内勾选且已填写答案的要件，作为可选入参传给 `generateByMaterial(elementAnswers)`（现有逻辑已支持）
- 抽屉的存在不影响原有【生成文书】按钮触发的「引入案由要件」前置选择弹框流程，两者并行可用

#### 我的要件维护页面（pages/my-elements.html）

> ℹ️ **使用范围提醒**：此处维护的「我的要件」仅在生成「裁判文书」类文书时才会询问是否引入辅助生成；其他文书类型（庭审提纲、执行文书、材料总结等）不会触发要件引入。页面顶部以提示条形式展示此说明。

- 页面左侧为**案由树**（3 级结构，与新增案件案由选择器一致，来自 `causeTreeDataByOrg`），右侧为该案由下的个人自定义要件列表

- 左侧支持**置顶**常用案由：hover 叶子案由显示图钉按钮，置顶后集中在树顶部「置顶」分组下（按业务系统分组存储 `localStorage.myPinnedCauses`）
- 顶部提供「法院 / 检察院 / 司法局」业务系统切换按钮组（与「我的示例」「我的指令」一致），切换后左侧案由树随之刷新
- 从案件详情页或引入案由要件弹窗进入时，URL 携带 `cause` 参数，页面自动选中该案由（并展开其所在的大类/中类）并展示其我的要件
- 右侧仅展示「我的要件」，不再展示「标准要件」；标准要件在引入案由要件弹窗中只读展示
- 支持新增、编辑、删除我的要件：点击【新增我的要件】后在列表底部展开编辑表单，填写名称、说明、问题、适用案字后保存
- **案字适配**（v1.26）：选中案由后，右侧要件列表上方显示「适配案字」选择栏（多选标签，来自 `caseWordListByOrg[org]`），标记该案由适配哪些案字；不勾选 = 适配全部案字（通用）。存储于 `localStorage.myCauseCaseWords`（按业务系统 × 案由分组）。
- **要件级适用案字**（v1.26）：新增/编辑要件表单中包含「适用案字」多选标签（优先展示该案由已勾选的适配案字，若未勾选则展示业务系统全部案字）；不选 = 通用（该案由下所有案字适用）。存储于要件对象的 `caseWords` 字段。
- **运行时过滤**：文书生成时 `getAllElementPresets(cause, org, caseWord)` 调用 `filterElementsByCaseWord` 过滤用户自定义要件，返回 `caseWords` 包含该案字或为空（通用）的要件。

### 9.3 批量生成交互（勾选触发 → 全屏面板）

**触发路径**：勾选 ≥1 个案件 → 顶部浮现批量操作栏 → 点击「批量生成」→ cases.html 内切换到全屏批量面板

**全屏面板流程**（橙色主题 #ea580c）：

#### 阶段①：配置
```
面板内容：
├─ 顶部：已选案件清单（显示案件名称，可移除单个，可清空）+ 【返回案件列表】
│   └─ 解析预检：存在 解析失败材料的案件名称后显示黄色「解析异常」徽标
├─ 解析预警面板（仅当存在 解析异常案件时显示）：
│   ├─ 警告文案：「N 个案件存在 解析失败的材料」+ 案件名称列表
│   └─ 策略选择（两个按钮，默认选中「跳过异常案件」）：
│       ├─ 跳过异常案件：批量执行时自动跳过这些案件，标记为「跳过」
│       └─ 仅用已识别材料生成：不跳过，使用该案件中已成功识别的材料生成文书
├─ 配置区：
│   ├─ 文书类型（下拉，按业务系统区分）
│   ├─ 文书示例（下拉，根据文书类型联动过滤，展示内置示例与「我的示例」，我的示例名称后追加「（我的）」标识）
│   ├─ 模型（只读展示，由所选文书类型的一步生成 Workflow 决定，不可修改）
│   ├─ 生成模式说明："批量生成使用一步生成方式，模型由文书类型对应的 Workflow 决定。若某案件材料量过大导致 Workflow 超限，该案件将被排除，请在案件详情页单独处理。"
│   └─ 指令（textarea，可选，含内置示例标签）
└─ 【开始批量生成】主按钮
```

**提交前校验**：
- 系统自动检查每个选中案件的材料量，材料量过大（Workflow 超限）或无可用材料的案件被自动排除
- 全部排除时阻止提交并提示"所选案件全部无法批量生成"
- 部分排除时提示"已排除 N 个无法批量生成的案件"，仅对有效案件提交批量生成

#### 阶段②：异步队列执行
- 提交后关闭全屏面板，返回案件列表页，不阻塞用户操作
- 顶部栏「任务通知」按钮显示处理中数量徽章
- 点击「任务通知」展开进度面板，展示每个批量任务的状态（处理中/已完成）
- **进行中任务**展示「查看进度」按钮，点击重新打开全屏面板查看实时队列进度（案件列表逐个从"排队等待"变为"生成中"再到"已完成"）
- 异步串行执行，逐个处理案件；材料量过大的案件在提交前已被排除

#### 阶段③：结果总览（从任务通知面板进入）
- 任务通知面板中已完成任务展示「查看结果」按钮
- 点击后打开全屏面板展示结果总览：统计卡片（案件总数/成功数/总字数/总耗时）
- 结果明细列表：失败项显示失败原因 + 【去处理】按钮，点击新标签页打开 `case-files.html?caseId=xxx`，由用户在案件详情页单独处理
- 操作：【返回案件列表】

**返回规则**：全屏面板「← 返回案件列表」→ 切回 cases.html 列表视图

### 9.4 状态联动与边界

| 场景 | 行为 |
|------|------|
| 未勾选案件时 | 浮动批量操作栏不显示，无独立「批量生成」入口按钮 |

### 9.5 文书精修交互（v1.10 新增，v1.31 修订，v1.36 更新独立精修页，v1.49 三卡片上下文 + 结构化审查意见）

**触发路径**：

- 案件详情页 → 右栏「生成结果」面板 → 点击【文书精修】按钮

```
点击【文书精修】
  ├─ 新窗口/当前页打开 document-polish.html?caseId=xxx&versionId=xxx
  ├─ 左侧展示当前版本文书正文（可编辑），使用 `js/doc-editor.js` 文档编辑器组件
```

**上下文信息区展示规则**（v1.49 改为三卡片）：

- 不再展示：案件名（含案号）、已选材料名、生成指令等旧式行列表

> ℹ️ **原型简化说明**：原型阶段精修交互统一走 `document-polish.html` 独立页面，左侧文书 + 右侧对话，不单独做弹窗式版本对比 UI。产品化阶段可考虑增加「左侧多轮对话 + 右侧版本对比」的弹窗式精修体验，并在文书对象 `versions` 数组中支持 `revised` 版本留存。

**上传文书入口（v1.49 新增）**：
- header 右侧新增【上传文书】按钮（虚线边框样式）

- 上传模式下选中段落改写与结构化审查意见仍可用，但"定位原文"依赖文本匹配，不依赖案件数据

**选中段落系统改写（v1.1 新增，0811 会议确定）**：

在独立精修页左侧文档编辑器内，用户可选中任意段落或片段，唤起浮动改写工具条，进行单点精准修改。

**触发条件**：
- 仅当编辑器非只读状态时启用
- 用户在文书编辑器内用鼠标拖选一段文本后松开鼠标（`mouseup` 事件）
- 若选区为纯空白或跨段但不连续，则不触发工具条

**浮动工具条交互**：
```
选中文本后松开鼠标
  ├─ 在选区上方/下方弹出迷你工具条
  │   ├─ 图标：✨ 系统改写
  │   └─ 点击后关闭工具条并弹出改写卡片
  └─ 点击编辑器空白处或滚动页面时工具条消失
```

**改写卡片结构**：
卡片标题区：提示"系统改写结果，仅供参考"
- 原文：展示选中的原文片段，不可编辑，仅作锚点确认
- 修改说明：一句话说明改写方向（如"优化表述、补充法条引用"），系统生成
- 修改结果：系统生成的改写文本，默认自动选中
- 操作按钮（从左到右）：
  - 【重新生成】：按默认策略重新生成一次改写结果
  - 【复制】：将修改结果复制到剪贴板
  - 【插入】：将修改结果插入到编辑器当前光标位置（保留原格式模板）
  - 【替换原文】：定位选区原文并替换为修改结果，仅替换文本节点，保留段落原有格式
- 底部输入框：支持用户输入优化指令（如"更正式一些""补充赔偿金额明细"），回车或点击向上箭头后按新指令重新生成

**格式保留规则**：
- 替换原文时，仅替换文本节点的 `textContent`，不修改包裹该段落的 `<p>` / `<h2>` / `<h3>` / `<li>` 等容器标签及其 CSS 样式
- 若修改结果包含多段内容，按原文段落结构拆分后逐段替换；无法一一对应时，以插入方式兜底
- 替换完成后，被替换文本高亮闪烁 0.8 秒提示用户

**边界与异常**：
- 选区跨多个不连续段落：工具条不触发
- 改写结果为空或生成失败：卡片内显示"暂无可用的改写结果，请调整选区或指令后重试"
- 用户修改"修改结果"文本框后点击【替换原文】，使用用户编辑后的文本
- 替换前若原文选区已因用户编辑而失效，提示"原文位置已变化，请重新选中文本"

**右侧多轮对话结构化审查意见（v1.49 新增，0811 会议确定）**：

用户在右侧对话栏发送一条精修指令后，系统返回结构化的审查意见，包含「分析过程」和「审查点列表」两部分。

**交互流程**：
```
用户输入指令（如"将本院认为部分重写"）
  ├─ 右侧出现用户消息气泡
  ├─ 助手消息占位："分析中..." + 加载动画
  ├─ 0.8s 后流式展示分析过程（每步间隔 0.6s）
  │   └─ 分析步骤标题根据指令动态变化（如"梳理历史任务 / 明确用户需求 / 定位与检索 / 起草与完善"）
  ├─ 全部步骤展示完成后，0.5s 后自动折叠分析过程（保留展开入口）
  └─ 0.3s 后展示审查意见区域（顶部批量操作 + N 张审查点卡片，每张卡片间隔 0.3s 出现）
```

**分析过程区**：
- 可折叠面板，标题"已完成分析" + 展开/收起图标
- 步骤标题根据用户指令动态变化，不固定名称
- 流式展示时逐步展开，全部完成后自动折叠

**审查意见区结构**：
- 顶部批量操作：【全部插入】【全部撤销】
- 审查点卡片（当前阶段不分类，全部平铺展示）：
  - 序号 + 标题（如"1. 本院认为部分缺少法律依据"）
  - 风险概述（红色文字）
  - 修改方案（蓝色文字）
  - 修改内容（默认展示"修订版"，可切换"清洁版"）
    - 修订版：以 `<del>` 红色删除线 + `<ins>` 绿色高亮展示差异
    - 清洁版：仅展示修改后的最终文本
  - 操作按钮：【定位原文】【撤销修订】【忽略】【插入】

**单点操作语义**：
- 【定位原文】：在左侧编辑器中查找 `originalAnchor` 文本，滚动到位置并高亮闪烁；找不到时按钮置灰，hover 提示"原文位置已变化，无法定位"
- 【插入】：查找原文锚点，找到则替换（保留原格式）；找不到则按当前光标位置插入并提示；插入后卡片变绿、显示"已应用"标签
- 【撤销修订】：恢复到该条消息操作前的快照，再重新应用其他已应用的审查点；撤销后卡片恢复正常状态
- 【忽略】：卡片置灰，显示"已忽略"标签，不可再操作

**批量操作语义**：
- 【全部插入】：依次应用所有未忽略的审查点；部分锚点失效时按光标处插入兜底，汇总提示"N 项成功插入，M 项因原文变化已插入到光标处"
- 【全部撤销】：恢复到该条消息所有操作前的快照，清除所有已应用标记（忽略的不恢复）

**状态管理**：
- 每条审查消息维护独立的操作快照（`snapshotBeforeApply`），首次应用时记录
- 全局撤销栈（`editHistory`）仍记录每次操作前的内容，供 header【撤销】按钮使用
- 多条指令独立：连续发送多条指令时，每条指令独立生成一条审查消息，历史消息保留但不可再操作（已应用的修改保留在文书中）

**边界与异常**：
- 审查意见为空：分析过程后显示"未识别到需要修改的内容，请尝试更具体的指令"
- 原文锚点找不到：【定位原文】按钮置灰；【插入】按光标处插入并提示
- 用户手动编辑后锚点失效：操作时实时校验，失效则按上述策略处理
- 与"选中段落系统改写"保持独立，互不干扰，两类操作都进入全局撤销栈

**数据规则**：
- 每个文书对象保存 `versions` 数组，支持 `original`（初稿）与 `polish`（精修）版本；`polish` 版本记录 `polishedFrom` 指向原版本
- 版本 `config` 中保存 `materialIds`、`prompt`、`docType`、`template`、`modelId`、`stepsSnapshot` 等生成配置，用于精修页恢复上下文
- 旧入口仍保留：无 `versionId` 时尝试从 `localStorage.refineContext` 读取兼容展示；`refineContext` 中同时携带 `materialIds` 与 `prompt`，精修页优先从版本 `config` 读取，无版本时 fallback 到 `refineContext`
- 产品化阶段可扩展 `revised` 版本，记录修订时间、对话消息快照

## 十八、案件删除交互（v1.7 新增，v1.8 优化文案与版本号）

### 18.1 功能定位

支持在案件列表中对单个或多个案件执行删除操作，并在确认时选择删除范围。

### 18.2 入口

| 类型 | 入口 |
|------|------|
| 单个删除 | 案件列表操作栏 → 删除图标按钮（🗑️） |
| 批量删除 | 勾选案件后，顶部浮动批量操作栏 → 「批量删除」按钮 |

### 18.3 删除范围确认

点击删除后弹出确认弹窗，提供三种范围：

- **删除案件及全部材料（不可恢复）** —— 默认选中：将选中案件从当前业务系统案件列表中硬删除，原始材料及已生成文书均删除。
- **仅清空原始材料，保留已生成文书**：清空选中案件的 `files` 材料列表，案件本身及已生成文书保留在系统中。
- **仅删除案件记录，保留所有文件和文书**：软删除机制。将案件标记为 `isDeleted=true` 并记录 `deletedAt`，**不从数据数组中移除**。用户侧案件列表不可见，管理后台案件管理可见且带「已删除」标签，管理员可恢复。

### 18.4 交互流程

```
点击删除按钮
  ├─ 弹出删除范围确认弹窗
  │   ├─ 选择「删除案件及全部材料」/「仅清空原始材料」/「仅删除案件记录」
  │   └─ 点击「删除」执行
  ├─ 若选择删除案件及全部材料：
  │   ├─ 从当前业务系统 cases 数组中移除选中案件
  │   └─ 清空已选案件勾选状态
  ├─ 若选择仅清空原始材料：
  │   ├─ 清空案件 files 数组
  │   ├─ fileCount 置为 0
  │   └─ updatedAt 更新为当前日期
  ├─ 若选择仅删除案件记录（软删除）：
  │   ├─ 标记 c.isDeleted = true
  │   ├─ 记录 c.deletedAt = 当前日期
  │   ├─ 保留 files / documents / 所有结构化字段不动
  │   ├─ 用户侧 renderCaseList 过滤 isDeleted=true 的案件
  │   ├─ 管理后台 applyFilters 不过滤 isDeleted，行内显示「已删除」标签
  │   └─ 管理后台提供「恢复」入口（清除 isDeleted/deletedAt 字段）
  └─ 重新渲染案件列表并提示结果
```

### 18.5 边界规则

- 批量删除仅作用于当前业务系统可见的已选案件。
- 删除案件后，关联的历史文书弹窗、解析弹窗等不再展示该案件数据。
- 操作完成后显示通知提示删除结果。

| 字段 | 必填 | 说明 |
|------|------|------|

```
  ├─ 支持搜索过滤
  ├─ 选中后回填到编辑弹框的隐藏字段与显示文本
  └─ 关闭案由树弹窗

点击「保存」
  ├─ 校验案件名称非空
  ├─ 更新 caseItem 字段：caseName/caseNumber/caseWord/cause/type(partyA/partyB/handler/handlers/date/updatedAt)
  ├─ type 通过 getCauseType(cause, currentBusiness) 自动推导

  ├─ 重新加载数据并刷新表格
  ├─ 关闭弹框
  └─ 显示成功通知

```

- 若该示例被 case.docTypes[x].templates 引用，仅删除示例数据，不自动清理 docTypes 引用（下次加载时 getDocTypeTemplates 自动过滤不存在的 key）

### 20.6 启用/停用交互

- 每行示例在操作栏提供「启用/停用」按钮，按钮文案随当前状态切换：当前为启用时显示「停用」，当前为停用时显示「启用」
- 「状态」列同步显示徽章：启用=绿色「已启用」，停用=灰色「已停用」
- 点击「停用」即时切换 `enabled=false` 并持久化，无需二次确认；点击「启用」同理切换为 `true`
- **停用效果**：用户侧文书生成时，被停用的示例不展示在下拉列表中（`mergeAdminDocTemplates` 合并时过滤 `enabled === false` 的项）
- 内置示例同样支持停用：内置示例被停用时，用户侧不再展示该内置项
- 兼容性：旧数据无 `enabled` 字段时视为启用

## 第二十三章 管理后台 - 要件管理

> 设计原则：标准要件按「业务系统 × 案由 × 案字」分组维护；案由可选顶级（大类/中类/叶子），要件按案字维度分组，子级案由继承父级配置并可覆盖。
> ℹ️ **使用范围提醒（v1.27）**：此处维护的标准要件仅在生成「裁判文书」类文书时才会询问是否引入辅助生成；其他文书类型（庭审提纲、执行文书、材料总结等）不会触发要件引入。页面顶部以提示条形式展示此说明。
> 数据持久化：`localStorage.adminElementPresets`（按业务系统分组），用户侧 `getElementPresets(cause, org, caseWord)` 优先读此 key，为空则按继承规则向上查找祖先案由，最后回退到内置要件；案件无案由时返回空数组（标准要件绑案由，无案由不展示）。
> 案字适配：`localStorage.adminCauseCaseWords`（按业务系统分组），标记每个案由适配哪些案字；空/不存在 = 适配全部案字。
> 与用户侧「我的要件」的关系：标准要件（本章）由管理员维护，对所有用户可见；用户侧「我的要件」由普通办案人员维护，仅对自己可见。文书生成时两者合并展示，分别加「标准」「我的」标识。

### 23.1 页面入口

- 入口位置：admin 侧边栏「主菜单」中，位于「案由管理」下方、「文书示例管理」之上，新增「要件管理」链接
- 页面标题：要件管理；副标题：维护各业务系统的标准要件，按案由分组
- **业务系统切换**：页面标题右侧提供「法院 / 检察院 / 司法局」三按钮切换组（与其他管理页一致），默认选中「法院」；切换后仅展示该业务系统下的要件配置


## 第二十五章 管理后台 - workflow 配置（挂在文书类型下）

> 设计原则：workflow 是系统内部配置，**对用户完全不可见**；用户侧只看到「一步生成 / 分步生成」两个 tab，不感知 workflow 概念。
> workflow 的本质是「节点流程」配置容器，按「业务系统 × 文书类型」分组，包含两种类型（v1.34 重命名）：
> - **一步生成型**（type='material'）：无人工交互节点，输入参数（材料 + 示例 + 指令）后直接输出文书结果，用于一步生成 tab
> - **分步生成型**（type='step'）：含人工交互节点，用户在分步生成 tab 中按节点逐个确认材料与内容，最终编译为完整文书
> 数据持久化：`localStorage.adminWorkflows`（按业务系统分组），用户侧 `getWorkflowsForDocType` 优先读此 key，为空回退内置默认。
> 与生成策略的关系：workflow **不绑定生成策略**。案件列表页由 token 自动决定模式；案件详情页用户选 tab；用户选「分步生成」时按案字+案由匹配分步生成型 workflow；用户选「一步生成」时按案字+案由匹配一步生成型 workflow。

> v1.35 单 workflow 架构原则（核心设计决策）：
> 1. **一个文书类型对应一个完整闭环 workflow**：从输入到输出是一个闭环，不再支持「一步骤一 workflow」的拆分方式
> 2. **一步生成型与分步生成型本质是同一个 workflow**：区别仅在是否含人工交互节点；材料生成本身也有步骤，只是不需要人工介入
> 3. **不采用多 workflow 拆分的原因**：① 多 workflow 之间步骤存在数据依赖（后步依赖前步输出），拆分后无法跨 workflow 传递；② 编排人员同时管理多个分散 workflow 易混乱；③ 接入适配工作量大、后期扩展麻烦
> 4. **单 workflow 支持指定节点重新生成**：业务侧记录当前卡在哪个节点（或完整生成完后从某节点重新生成），由 agentflow 平台加功能支持；当前原型未实现，PRD 登记
> 5. **「生成文书」作为 workflow 内的最终节点**：不再单独拆为独立 workflow；若该节点渲染慢（约 1-2 分钟），由前端流式输出/思考过程样式缓解体验问题

> v1.32 关键变更：
> 1. **workflow id 改为下拉框**：数据来源于 agentflow 平台已编排的 workflow 列表（原型中以 `case-data.js` 内 `agentflowWorkflowList` mock），管理后台仅做选择绑定
> 2. **移除步骤序列编辑器**：分步生成型 workflow 的节点序列由 agentflow 平台 workflow 内部决定，管理后台不再配置 steps 字段
> 3. **新增「匹配案由」字段**：与「匹配案字」配合做精细化匹配

> v1.34 命名调整：「直接生成型」改为「一步生成型」，与用户侧 tab 命名「一步生成」对齐；内部 type 值仍为 'material'，函数名/字段名不变。

### 25.5 删除 workflow 交互

- 点击「删除」→ 二次确认弹窗
- 内置 workflow 删除 = 移除自定义覆盖（恢复内置默认）
- 自定义 workflow 删除 = 直接移除
- **删除前校验**：若该类型下某类型（分步生成型/一步生成型）的 workflow 仅剩此一个，禁止删除并提示「每个类型至少需保留 1 个分步生成型 workflow」或「每个类型至少需保留 1 个一步生成型 workflow」

### 25.6 用户侧联动

- 案件列表页生成文书：由 token 自动决定模式（现状不变），不涉及 workflow 选择
- 案件详情页用户选「分步生成」tab 时：
  1. **文书类型下拉仅展示存在分步生成型 workflow 的类型**，无分步生成型 workflow 的类型不出现
  2. 系统从案件 `caseNumber` 中提取案字（正则匹配 `民初/民终/民再/刑初...`）
  3. 从案件 `cause` 取案由名称
  4. 调用 `getWorkflowsForDocType(org, docTypeKey, 'step')` 获取该类型下所有**分步生成型** workflow
  5. 按匹配规则优先级匹配默认分步生成型 workflow（案字+案由双精确 → 案字精确+案由兜底 → 案字兜底+案由精确 → 全兜底 → 第一个）
  6. **步骤方案下拉**（仅当该类型下有 2 个及以上分步生成型 workflow 时显示）：
     - 位于分步配置区，文书类型与文书示例之间
     - 选项为 workflow 的业务化名称（如「一审民事判决步骤」「二审民事判决步骤」），**不出现"workflow"一词**
     - 默认选中案字+案由自动匹配的分步生成型 workflow
     - 用户可手动切换
     - 仅 1 个分步生成型 workflow 时不显示此下拉
  7. **节点序列与步骤名由 workflow 运行时动态返回**（v1.35 明确）：
     - 节点序列由 agentflow 平台 workflow 内部决定，前端不再单独配置/存储步骤名
     - 每个步骤的「名称」直接取自 workflow 编排时人工交互节点的**面板名**（如编排时命名为「案件信息」「原告诉请」，前端原样展示）
     - 用户点击【开始生成】后，前端通过 workflow id 发起执行，SSE 事件流依次返回每个人工交互节点的事件
     - 前端按 SSE 事件动态渲染步骤列表：收到节点事件即新增一个步骤面板，标题为该节点的面板名
     - 已完成的节点以快照形式保留展示，新节点逐个出现
     - 原型阶段以 `stepConfigsByOrg` 内置 mock 充当步骤序列（含固定步骤名），正式接入时由 SSE 事件流动态返回
- 案件详情页用户选「一步生成」tab 时：
  1. 系统从案件 `caseNumber` 提取案字，从 `cause` 取案由
  2. 调用 `getWorkflowsForDocType(org, docTypeKey, 'material')` 获取该类型下所有**一步生成型** workflow
  3. 按匹配规则匹配默认一步生成型 workflow，用于确定使用哪一套一步生成流程
  4. 一步生成型 workflow 无节点序列，用户侧仅感知「材料 + 示例 + 指令 → 生成文书」的表单交互，不暴露 workflow 概念
  5. 仅 1 个一步生成型 workflow 时不显示任何切换入口
  6. **文书类型下拉展示全量类型**（用于匹配示例与指令）

### 25.7 与其他模块的关系

| 模块 | 关系 |
|------|------|
| 文书类型管理（第24章） | workflow 挂在文书类型下，类型删除时同步清理该类型下所有 workflow（含分步生成型与一步生成型） |
| 文书示例管理 / 指令管理 | 无直接关系，示例/指令仍挂文书类型下，不按 workflow 区分 |
| 案件详情页分步生成 | `getWorkflowByCaseWord` 按案字+案由匹配**分步生成型** workflow；**文书类型下拉仅展示有分步生成型 workflow 的类型**；节点序列通过 workflow id 从 agentflow 平台获取 |
| 案件详情页一步生成 | `getMaterialWorkflowByCaseWord` 按案字+案由匹配**一步生成型** workflow，仅用于流程选择，不暴露给用户；文书类型下拉展示全量类型 |
| 生成策略 | workflow 不绑定策略；策略仍由 token（列表页）或用户选 tab（详情页）决定 |
| agentflow 平台 | workflow id 与 name 数据来源；节点序列维护；执行层接口由后端封装统一调用 |

## 第二十六章 workflow 执行快照存储机制（v1.38 新增）

### 26.1 功能定位

**业务端在 SSE 事件透传过程中加一层快照存储**，用于记录 workflow 执行过程中每个人工交互节点的输入参数与返回结果，支持节点级回溯、重新配置回填、断点续跑等场景。

> ℹ️ **实现说明**：此项为**后端实现逻辑**，PRD 中登记即可，原型阶段**无需实现**。前端仅消费后端提供的快照数据（如「重新配置」时的历史快照回填，见 9.2a 节），不负责快照的写入与存储。

### 26.2 快照触发时机

| 时机 | 触发事件 | 存储内容 |
|------|----------|----------|
| 节点开始 | 人工交互节点开始事件 | 输入参数快照（含案件上下文、已选材料、示例、指令、模型等） |
| 节点结束 | 人工交互节点结束事件 | 返回结果快照（含节点输出内容、用户确认/编辑后的结果） |

### 26.3 快照数据结构

每个步骤一条 JSON 记录，同时包含输入与输出：

```json
{
  "caseId": "case-001",
  "workflowId": "wf-judgment-1st",
  "workflowExecutionId": "exec-20260728-001",
  "nodeId": "plaintiff",
  "nodeName": "原告诉请",
  "nodeType": "manual_interaction",
  "input": {
    "caseContext": { "caseName": "...", "caseNumber": "...", "caseWord": "...", "cause": "..." },
    "selectedMaterials": ["file-1", "file-2"],
    "docType": "judgment",
    "template": "tpl-001",
    "prompt": "...",
    "modelId": "qwen3.6"
  },
  "output": {
    "content": "生成的文书片段内容...",
    "userEdited": false,
    "confirmedAt": "2026-07-28T10:30:00Z"
  },
  "snapshotTime": "2026-07-28T10:30:00Z"
}
```

### 26.4 快照存储规则

- **存储层级**：业务端（非 agentflow 平台），在 SSE 事件透传过程中加层存储
- **触发节点**：仅人工交互节点触发快照，自动节点（如大模型节点、条件判断节点）不单独存储
- **每步一条**：每个步骤对应一条 JSON 记录，同时包含输入与输出
- **事件结束触发**：节点结束事件触发时写入完整快照（输入已在开始时暂存，结束时合并输出）
- **历史保留**：同一节点多次执行时保留最新一条快照（重新生成覆盖旧快照）

### 26.5 快照消费场景

| 场景 | 消费方式 | 关联章节 |
|------|----------|----------|
| 重新配置回填 | 用户点击「重新配置」时，回填最近一次历史文书的快照数据（模型/类型/示例/指令/已选材料/生成方式） | 9.2a 节 |
| 指定节点重启 | 用户选择某节点重启生成时，读取该节点输入快照作为起点 | 2.10 节（待实现） |
| 断点续跑 | workflow 中断后恢复时，从最后完成的节点快照继续 | 后端逻辑 |
| 审计追溯 | 查看每个节点的输入与输出，用于问题定位与质量审计 | 后端逻辑 |

### 26.6 与 agentflow 平台的关系

| 职责 | 归属 |
|------|------|
| workflow 编排与节点序列管理 | agentflow 平台 |
| workflow 执行与 SSE 事件推送 | agentflow 平台 |
| SSE 事件透传过程中的快照存储 | **业务端**（本章描述） |
| 快照数据的消费与展示 | 业务端前端（原型阶段仅消费「重新配置」回填场景） |
